jj-vfs-poc architecture

A detailed, source-linked map of how jj-vfs-poc (the crate jjfsd) works inside: a read-only FUSE file system that shows a jj repository's commits and workspaces as directories, from the kernel's request down to jj-lib's store.

Upstream calls this a proof of concept, and promises no completeness, performance or API stability. These pages say plainly what it doesn't do yet. For jj's own internals (commits, trees, conflicts, the working copy), see the jj architecture reference. That reference describes its own pinned jj version, which can differ from the jj-lib {{ upstream.jj_lib_version }} this crate builds against.

The layers

Kernel and fuser

main.rs takes a mountpoint and a workspace root, loads the repository at its current operation, and calls fuser::spawn_mount with the options RO and FSName("jjfs"). It then waits for SIGINT, SIGTERM or SIGHUP. The fuser crate talks to the kernel and calls methods on a Filesystem implementation. See starting and mounting.

The FUSE adapter

JjFuse implements six of those methods: {% for op in fuse_ops %}{{ op }}{% if not loop.last %}, {% endif %}{% endfor %}. Every one except init turns the inode into a path with InodeMap, spawns the work onto the tokio runtime, and replies from inside the task. See the FUSE adapter and inodes.

The virtual file layer

VirtualFilesystem is the path-based interface JjFuse calls: attributes, read, read a directory, and read a link. Its one implementation, PathMappedVfs, asks a PathMapper for a VirtualFile and calls one method on it. See the virtual file layer.

The namespace

AllCommitsPathMapper decides what exists: commits/<id>/… and workspaces/<name>/…, served by three small directory types and CommitTreeFile, which presents a commit's tree. See the mount's namespace and commits as directory trees.

jj-lib

Everything below that is jj-lib {{ upstream.jj_lib_version }}. The crate reads the repo's view (wc_commit_ids), evaluates the all() revset, loads commits from the Store, and reads trees, files and symlinks through MergedTree and the Store. It never writes, and never starts a transaction.

Status and limitations

The README says it plainly: this is a proof of concept, "beginning life as an intern project", with "no guarantee of completeness, performance, or API stability". At the pinned commit:

  • The mount is read-only, and implements only lookup, attributes, directory listing, reads and symlinks.
  • The repository is loaded once. The mount is a snapshot of the operation that was current at mount time.
  • Conflicted paths can't be read, and submodules show as unreadable files.
  • There are no timestamps, executable bits or real ownership: epoch times, 0644/0755, uid and gid 1000.
  • Performance shortcuts: sizes and reads at an offset read the file from the start, listings aren't paginated, and inodes are never freed.

Each is sourced on the namespace page's limitations table.
