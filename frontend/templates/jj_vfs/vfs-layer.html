The virtual file layer

The three traits between FUSE and jj: VirtualFilesystem (what JjFuse calls), PathMapper (which file a path names) and VirtualFile (what a file can do), plus the one adapter, PathMappedVfs, that joins them.

In short: the FUSE adapter speaks in paths, and asks a VirtualFilesystem for attributes, bytes, directory entries or a link target. The only implementation, PathMappedVfs, turns every one of those calls into two steps: ask the PathMapper for the VirtualFile at that path, then call one method on it. A VirtualFile is created fresh for each request and dropped afterwards. Nothing in this layer caches.

1. VirtualFilesystem

VirtualFilesystem is described as the "middle-layer filesystem abstraction representing inode-based VFS operations", between the FUSE layer and the path mapper. It is an async_trait, and every method takes a relative &Path (the root is the empty path) and returns Result<_, JjError>.

get_attributes(&self, path: &Path) → Result<FileAttributes, JjError>Size, type and timestamps for lookup and getattr.vfs.rs
read(&self, path: &Path, offset: u64, size: u32) → Result<Box<[u8]>, JjError>Up to size bytes starting at offset. Fewer bytes means end of file.vfs.rs

There is no write, create, rename or remove method. The trait itself makes the mount read-only, not just the mount option.

2. PathMapper

PathMapper "represents the VFS mountpoint structure by mapping a given absolute path to a VirtualFile". It has a single method, async fn get_entry(&self, path: &Path) → Result<Box<dyn VirtualFile>, JjError>, and requires Send + Sync. Despite the doc's "absolute", every caller passes a path relative to the mount root. The only implementation is AllCommitsPathMapper, described on the mount's namespace. The point of the trait is that another layout (for example one showing a single workspace) would only need a new mapper.

3. VirtualFile

VirtualFile is "a file in our virtual file system. This can either be a normal file you can read from or for example a directory". It "is not meant to be created by the user, but instead returned by a PathMapper". Three of its five methods have default implementations that fail, so each implementor only overrides what makes sense for it.

ItemType/SignatureDefaultSource

5. PathMappedVfs

PathMappedVfs<P: PathMapper> holds the mapper in an Arc and implements each VirtualFilesystem method in two lines: resolve, then delegate. get_attributes calls attributes, read_directory calls list, read_link calls read_link, and read calls read and then cuts the requested window out of the stream. Errors from either step pass through unchanged, and I/O errors become JjError::IO, which FUSE reports as EIO.

Serving reads

FUSE asks for a byte window (offset, size), but a VirtualFile only offers a stream from the beginning. PathMappedVfs::read bridges the two with futures::io::AsyncReadExt:

  1. Open the stream with virtual_file.read().
  2. Wrap it in take(offset) and copy that into futures::io::sink(), which reads and discards the first offset bytes ("TODO: handle proper seek()").
  3. Unwrap the original reader with into_inner(), wrap it in take(size), and read_to_end into a buffer pre-sized to size.
  4. Return the buffer as Box<[u8]>.

If the file ends before offset, step 2 simply stops early and step 3 returns nothing, which the kernel reads as end of file. The cost is that every read starts from byte 0: reading a file in chunks of c bytes costs about n²/2c bytes of decoding for a file of n bytes, on top of the full file read that getattr already does to find the size.
