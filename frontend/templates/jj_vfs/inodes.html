Inodes

The kernel names files by inode number, while everything below JjFuse names them by path. InodeMap translates between the two: a tree of entries, one per path ever seen, keyed by a counter that only goes up.

In short: inode 1 is the mount's root. The first time a name is looked up or listed under a directory, get_ino gives it the next number and records its parent and name. To serve a request, get_path walks parent links back to the root to rebuild the path. One mutex guards the whole map. Nothing is ever removed: forget isn't implemented, so the map holds every path the kernel has asked about since the mount, including names that turned out not to exist.

This page covers src/inode_map.rs. Its only user is the FUSE adapter, which owns one map per mount. Paths go from there to the virtual file layer.

Names are Ustrs from the ustr crate (Cargo.toml): interned strings, so each distinct name is stored once and compared cheaply. The crate's own docs note that interned strings are never freed (ustr source).

How numbers are allocated

get_ino(parent, name) interns the name, takes the lock and finds the parent's entry. An unknown parent is JjError::NotFound. If the parent's children already has the name, that number is returned. Otherwise it takes the next number with next_inode.fetch_add(1, Relaxed), adds it to the parent's children, inserts a new Entry for it, and returns it.

  • Numbers follow request order. They count up from 2 in the order names are first seen, so the same file can get a different number on another mount (each JjFuse creates its own map, fuse.rs).
  • One number per path, not per object. The key is (parent, name), so the same file reached through commits/<id>/ and workspaces/<name>/ has two inodes, and nlink is always 1 for files (fuse.rs).
  • No checks against the file system. get_ino doesn't know whether the name exists or whether the parent is a directory. lookup calls it before asking for attributes (fuse.rs), so a lookup that fails with ENOENT still leaves an entry behind.
  • Never reused. Nothing is removed and the counter never goes down, so within one mount a number names one path. lookup always replies with generation 0 (fuse.rs).

How a number becomes a path

get_path(ino) holds the lock while it walks from the inode up to ROOT_INODE, collecting each entry's name; an unknown number on the way is NotFound. It then sizes a PathBuf for the names and separators and pushes the names root-first. The cost is one hash lookup per level. The root's empty path is what AllCommitsPathMapper treats as the top directory.

get_parent_ino(ino) returns the entry's parent. Because new makes the root its own parent (L28), the root's .. is the root.

Every get_path failure is logged at error level and answered with ENOENT, the errno for NotFound (L44, L231). With nothing ever removed, that can only happen for a number the map never handed out.

Worked example

Derived from the code, not recorded from a mount: say the kernel's first requests after mounting are a listing of the root, then a lookup of commits, then a lookup of a name that doesn't exist. The root lists commits then workspaces (source), so readdir(1, 0) sends . as 1, .. as 1 and allocates 2 and 3. The lookup of commits finds 2 already in the root's children. The lookup of nope allocates 4 and then fails with ENOENT, but entry 4 stays.

Lifetime: nothing is forgotten

The kernel sends forget when it drops an inode from its cache, and fuser's documentation says a file system "may ignore forget calls, if the inodes don't need to have a limited lifetime" (fuser source). JjFuse relies on that default, and InodeMap has no removal method at all. So the map, and the interned names, grow with every distinct (parent, name) pair seen during the mount: each entry listed by readdir, each successful lookup and each failed one. Listing commits/ allocates a number for every commit it sends.

Because entries are never removed, a number the kernel holds always still resolves. Because the repository snapshot is fixed when the mount starts (see namespace), a path keeps naming the same content for the life of the mount, so the map never needs invalidating.

Concurrency

  • JjFuse shares the map as an Arc<InodeMap> and clones it into every task reply_async! spawns on the tokio runtime (fuse.rs), so calls can come from several threads at once.
  • Every method takes the single Mutex around the whole HashMap and releases it before returning. They are synchronous, so the lock is never held across an await.
  • The counter is only incremented inside get_ino while the lock is held (L72), so two threads looking up the same new name get the same number. The atomic adds nothing the lock doesn't already give.
  • Each method calls lock().unwrap(), so a poisoned lock panics instead of returning an error (L45, L62, L72).
