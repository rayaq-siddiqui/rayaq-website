The FUSE adapter

JjFuse is the only code that talks to fuser. It implements six Filesystem methods, turns each inode number back into a path, and runs the actual work on a tokio runtime. Results come back as FileAttrs, bytes, directory entries or errnos.

In short: fuser calls a JjFuse method on its session thread. The method clones what it needs, and the reply_async! macro spawns a task on the tokio runtime and returns straight away. The task resolves the inode to a path with InodeMap::get_path, awaits the matching VirtualFilesystem call, and replies. Errors become errnos: ENOENT, ENOTDIR, EISDIR, EINVAL, or EIO for everything else. Every method JjFuse doesn't implement falls back to fuser's default. The mount is read-only (MountOption::RO).

This page covers src/fuse.rs and src/jj_error.rs. The layer beneath, VirtualFilesystem and PathMappedVfs, is on vfs-layer. How inode numbers are handed out is on inodes.

JjFuse

JjFuse<FS: VirtualFilesystem> holds three things. fs is the virtual file system behind an Arc. inode_map is an Arc<InodeMap>, created fresh in new, so inode numbers start over at every mount. rt_handle is a tokio::runtime::Handle. main.rs passes the runtime's handle and an Arc of the PathMappedVfs (source).

The async bridge and reply_async!

fuser's methods are synchronous and take &self, while the VirtualFilesystem is async. reply_async! bridges the two. Its arguments are self, the reply object, the inode, a path => async body pair and a value => success body pair. It then:

  1. clones the inode map and runtime handle, and spawns a task on the runtime. The FUSE method returns immediately, and the reply object moves into the task.
  2. In the task, resolves the inode with inode_map.get_path(ino). On failure it logs at error level and replies with the errno.
  3. Awaits the body with the path bound mutably (lookup pushes the child's name onto it).
  4. On Ok, runs the success body, which sends the reply. On Err, logs at debug level with the path, and replies with err.into().

Because replies are sent from tokio tasks, several requests can be in flight at once. init requests FUSE_ASYNC_READ and FUSE_PARALLEL_DIROPS so the kernel will send them that way (source). Every method also carries #[tracing::instrument(level = "debug")].

One read, end to end

How PathMappedVfs::read serves an offset, by reading and discarding the first offset bytes every time, is on vfs-layer (source). Before any read, the kernel has already looked the path up and opened it with fuser's default open.
