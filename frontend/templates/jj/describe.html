How jj describe works

jj describe sets the description of one or more commits, from -m, from stdin, or in your editor. It rewrites each commit with the same tree and change ID and a new message, and reparents its descendants onto the rewritten versions without touching their contents.

In short: jj resolves the revisions (default @), refuses if any is immutable, and builds the new descriptions. With one commit and no -m/--stdin, it opens one file in your editor. With several, it opens one file with a JJ: describe <id> section per commit. Commits whose description didn't change are dropped. The rest go through transform_descendants, which writes each described commit and reparents every descendant. Everything is one operation, describe commit <id>. If nothing changed, no operation is recorded at all.

The command is cmd_describe. Building and parsing the editor text lives in description_util.rs, which jj new, commit, squash and others share. The default alias desc comes from misc.toml.

5. Transaction and operation

  • Transaction: one, started after the revisions are resolved and checked (source).
  • Operation description (source): describe commit <id> for one commit, or describe commit <id> and <n> more for several. <id> is the full hex ID of the first commit in evaluation order, which is the newest, since revsets evaluate children first. It is computed from all resolved targets, including any whose description ends up unchanged.
  • Commits created or rewritten: one new commit per target whose description changed, plus one per descendant of those targets. Descendants are reparented, not rebased: their trees are kept, so describing can never introduce conflicts.
  • Nothing changed: if every new description equals the old one, no commit is rewritten. finish sees no view change, prints Nothing changed. and records no operation (source). The hidden temporary commits don't count, because they never enter the view.
  • Working copy: snapshotted at the start, so the commits you describe include your latest edits. If @ was rewritten, the new @ is checked out after the operation commits.
  • jj undo restores the previous view: the old commits become visible again with their old descriptions, and the rewritten ones are hidden.

6. Algorithm and invariants

Building each description

  1. Start from the existing description. rewrite_commit copies the stored commit (for_rewrite_from). It clears predecessors, sets the committer to you, now, and fills in an empty author name or email from the committer. If the old commit was discardable (empty, with no description) and you are its author, the author timestamp is reset to now as well. .detach() turns it into a DetachedCommitBuilder that holds the draft without touching the repo.
  2. Apply -m or --stdin to every builder, if given (source).
  3. Add trailers if templates.commit_trailers is non-empty. They are skipped for a builder whose description is still empty and no editor will open. The source comment explains why: the first trailer would become the subject line, and an empty description is what lets an untouched working-copy commit be discarded (source). Trailers already present aren't repeated, and a new trailer paragraph is separated by a blank line (add_trailers_with_template).
  4. Edit, if use_editor. For one commit, edit_description appends a blank line and JJ: Lines starting with "JJ:" (like this one) will be removed., then writes a temporary .jjdescription file. The cursor goes to the first line that isn't a JJ: comment. For several, edit_multiple_descriptions writes one file. It has a header, then a JJ: describe <12-hex commit id> ------- section per commit in topological order (parents first), each filled from the draft template.
  5. Clean up what the editor returns (cleanup_description_lines). Lines starting with JJ: are dropped, everything from JJ: ignore-rest onwards is dropped, and leading and trailing blank lines are trimmed. A non-empty result ends in exactly one newline.

Parsing the bulk file

parse_bulk_edit_message starts a new section at each line beginning JJ: describe . It strips trailing whitespace and dashes from the rest of that line to get the commit ID prefix. Before the first section, only blank lines and JJ: lines are allowed. Each section is matched to a commit by its exact 12-character short ID, and the IDs are then validated: any commit with no section, any section repeated, or any unknown ID is an error, and nothing is written (source). The order of sections in the file doesn't matter.

Rewriting

Unchanged descriptions are filtered out first, so descendants aren't rewritten for nothing (source). The source comment explains why it then uses transform_descendants rather than rewriting each target and calling rebase_descendants. When one target descends from another, the later approach would rewrite it twice and add an extra predecessor link. transform_descendants visits each commit in the descendants of the targets exactly once, parents first (transform_commits). It hands each one a CommitRewriter whose new parents already account for rewrites made earlier in the walk (source):

  • a target: reparent(), set the edited description, write(), and count it as described;
  • any other descendant: reparent() and write(), and count it as rebased.

Note that the final commits come from a fresh rewrite_commit inside reparent(). Only the description text is taken from the draft builders. Then bookmarks and working-copy pointers move to the new commits. Updated N commits. is printed only when N > 1, and Rebased N descendant commits. whenever a non-target was rewritten.

Invariants: trees never change, so no conflicts can arise; change IDs are kept, so every rewritten commit is the same change; and each commit is rewritten at most once per invocation.

Edge cases: an empty -m "" clears the description, and makes an empty commit discardable again. The bulk-file header warns that a syntax error loses your text. That's because the temporary file is deleted as soon as the editor exits successfully, before the text is parsed (edit_str). Describing the same commit through two revsets is fine, since the targets are a set.

8. Worked example

This is upstream's own test (test_describe_multiple_commits). It starts from a chain of three empty, undescribed commits on the root, with @ at the top, and describes the top and the bottom in one go: jj describe -r@ -r@-- -m "description from CLI".

The command prints, on stderr:

Updated 2 commits.
Rebased 1 descendant commits.
Working copy  (@) now at: kkmpptxz 4c3ccb9d (empty) description from CLI
Parent commit (@-)      : rlvkpnrz 650ac8f2 (empty) (no description set)

All three commits get new IDs, because each one's parent changed or its own description did. The middle commit only got a new parent, so its description and tree are untouched. The operation is describe commit 3cd3b246e098… and 1 more, naming the old @ in full. Running the same command again prints Nothing changed. and records nothing.
