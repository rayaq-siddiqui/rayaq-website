How jj file edit works

jj file edit opens one file from any mutable revision in your text editor, then saves the result back into that revision and rebases its descendants. Your working copy is never used; the file is checked out into a throwaway directory.

In short: jj resolves -r (default @), refuses it if it is immutable, and checks the path is a file, absent, or a conflict of files. It builds a temporary working copy whose sparse patterns contain only that path, checks the commit's tree out into it (conflicts become markers), and runs the editor on the file. It then snapshots the temporary copy. If the tree is unchanged it prints Nothing changed.; otherwise it rewrites the commit, rebases or reparents descendants, and records edit file <path> in commit <id>.

The command is cmd_file_edit. Its help text: "Edit the contents of a file in a revision. The file is opened with the contents from the given revision. After the editor exits, the file is saved back to the revision and descendants are rebased on top of the updated commit. If the file does not yet exist in the revision, a new file will be created. If the file is conflicted, the conflict markers are materialized in the editor. Editing the conflict markers can resolve the conflict." (source). It is the Edit variant of FileCommand (source, dispatch).

5. Transaction and operation

  • Transaction: one, started only after the editor has exited and the snapshot differs (source). The editor runs outside any transaction.
  • Operation description: edit file <path> in commit <full hex id>, using the repo-internal path and the commit's id before the rewrite (source).
  • Commits rewritten: the target, then its descendants through rebase_or_reparent_descendants, which prints Rebased N descendant commits. only when N is above zero, adding (while preserving their content) when reparenting.
  • No change, or editor failure: no transaction and no operation; upstream's tests check the operation ID is unchanged in both cases (test, test).
  • jj undo restores the previous view, bringing back the old content in the target and its descendants.

6. Algorithm and invariants

What can be edited

The path's value in the commit's tree decides (source). A regular file or no value at all is fine; a missing path becomes a new file only if the editor saves it (test). A directory, symlink or Git submodule is refused. A conflict is accepted only if every term is a file or absent, which to_file_merge() checks.

A one-file working copy

Rather than writing a temporary file, the command creates a full TreeState in a temporary directory, with wc as the working copy and state for its state files, and narrows its sparse patterns to the single path before checking out the commit's tree (source). The file therefore sits at its real relative path, so an editor can detect its type from its name (test), and checkout and snapshot handle the executable bit and conflict markers the same way the real working copy does; upstream tests that an executable script stays executable (test).

Saving back

After the editor exits, the temporary copy is snapshotted with no ignore rules, tracking everything and no size limit (source). Since only the one path is in the sparse patterns, only that path can change. The new tree is compared with the commit's by tree IDs (source).

Conflicted files

The editor sees exactly what file show prints for the conflict (test). Changing a side inside the markers keeps the file conflicted with the new side, and the command reports New conflicts appeared in 1 commits (test). Replacing the markers with plain text resolves the conflict (test).

Descendants

By default rebase_descendants replays each descendant's own diff, so a descendant that never touched the file picks up the edit. With --restore-descendants, reparent_descendants keeps each descendant's tree, so it keeps the old content. file delete uses the same pair.

Invariants: only one path in the target's tree can change, and never its identity or metadata. Your real working copy is not used for editing. If the editor fails or the file is unchanged, nothing is recorded.

8. Worked example

From upstream's test_file_edit. base adds file (containing base), dir/file and an executable script.sh; child, the working-copy commit, only adds other. The editor replaces file's content with modified, with and without --restore-descendants:

Upstream's snapshot for the plain edit (source):

$ jj file edit -r=base file
Rebased 1 descendant commits.
Working copy  (@) now at: mzvwutvl d2c70bd0 child | child
Parent commit (@-)      : rlvkpnrz 6b6a8e3b base | base
Added 0 files, modified 1 files, removed 0 files

With --restore-descendants the first line becomes Rebased 1 descendant commits (while preserving their content). and there is no Added … removed … line, since @'s tree is unchanged (source).
