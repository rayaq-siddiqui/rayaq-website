How jj bookmark set works

jj bookmark set points bookmarks at a commit by name. It creates the ones that don't exist and moves the ones that do. By default a move must go forward: the new target has to descend from the old one.

In short: jj resolves the target (default @). For each name it decides whether the bookmark is new or moved, and refuses a backwards or sideways move unless --allow-backwards is given. It warns if the target is empty. In one transaction it points every named bookmark at the target. New bookmarks are auto-tracked on matching remotes, just like bookmark create. The operation is point bookmark <names> to commit <id>.

The command is cmd_bookmark_set. Its help text sums it up as "Create a new bookmark, or update an existing one by name" (source). The create-only form is jj bookmark create. To move bookmarks selected by where they point, rather than by name, see jj bookmark move. Bookmark storage is on the view page.

3. End-to-end flow

Every name is checked in one loop before the transaction starts, so one refused name means nothing is changed.

5. Transaction and operation

  • Transaction: one, after every name passed the fast-forward check (source).
  • Operation description: point bookmark <name1, name2, …> to commit <full hex id> (source). This is the same text bookmark move uses.
  • Commits created or rewritten: none.
  • Working copy: snapshotted at the start, and otherwise untouched.
  • No-op names: a bookmark already at the target is still written, and still named in the operation description. It just isn't counted in the status line.

6. Algorithm and invariants

Classification (source): a name is new when there's no local bookmark and no tracked remote bookmark of that name. A deleted bookmark that still tracks a remote is being resurrected, and counts as moved, as the source comment says. Otherwise the name counts as moved unless it is already a normal bookmark pointing at the target.

The fast-forward rule (is_fast_forward): an absent old target always passes. A present one passes if any of its added commits is an ancestor of the new target. For a conflicted bookmark, that lets you resolve the conflict by pointing it at a descendant of one side. Strictly "all" sides would have to be ancestors, but jj deliberately allows "any". An old target equal to the new one passes, since a commit is its own ancestor.

Invariants: never rewrites a commit. Never moves a bookmark backwards or sideways without -B. Either every named bookmark is updated, or none is. Auto-tracking only touches bookmarks this run created.

8. Worked example

From upstream's test_bookmark_multiple_names. Bookmarks foo and bar sit on e8849ae1, and @ is its child 0e555a27. Then jj bookmark set -r@ bar baz moves bar forward and creates baz:

Upstream's snapshot, followed by a second run that names all three:

$ jj bookmark set -r@ bar baz
Warning: Target revision is empty.
Created 1 bookmarks pointing to zsuskuln 0e555a27 bar baz | (empty) (no description set)
Moved 1 bookmarks to zsuskuln 0e555a27 bar baz | (empty) (no description set)

$ jj bookmark set -r@ foo bar baz
Warning: Target revision is empty.
Moved 1 bookmarks to zsuskuln 0e555a27 bar baz foo | (empty) (no description set)

In the second run only foo changes. bar and baz were already there, so they aren't counted. Moving back is refused, as test_bookmark_move shows with jj bookmark set -r@- foo: Error: Refusing to move bookmark backwards or sideways: foo, which then succeeds with --allow-backwards.
