How jj diffedit works

jj diffedit opens a diff editor on one commit's changes and makes whatever you leave on the right-hand side that commit's new tree. It is the general way to touch up a commit's content by hand, without checking it out.

In short: jj picks a target commit and a base. That is -r (default @) against the merge of its parents, or --to against --from, each defaulting to @. It refuses an immutable target. The diff editor gets the base on the left and the target's tree on the right, and returns the right side as edited. If that tree equals the target's, jj prints Nothing changed. and records nothing. Otherwise it rewrites the target, keeping its change ID and description, then rebases its descendants, which can conflict, or reparents them with --restore-descendants. The operation is edit commit <id>.

The command is cmd_diffedit. Its help text points to jj restore for moving whole files between revisions and to jj squash -i for moving changes between them (source). Unlike those commands and jj split, it calls the diff editor directly rather than through the shared DiffSelector.

5. Transaction and operation

  • Transaction: started before the editor opens, so the instructions can format the target's summary, but committed only if the edited tree differs from the target's. Otherwise jj prints Nothing changed. and the transaction is dropped without recording an operation (source).
  • Operation description: edit commit <full hex id of the target before the rewrite> (source).
  • Commits created or rewritten: the target, plus every descendant. Descendants are handled straight after the write because, as the source comment says, the new commit would otherwise "always have a conflicted change id at this point" (source).
  • Working copy: snapshotted at the start. If @ changed, its new tree is checked out.
  • jj undo restores the previous view, bringing back the target's old tree and the old descendants.

6. Algorithm and invariants

Choosing the two sides

There are two shapes (source). With --from or --to, the target is --to and the base is the single --from commit, each defaulting to @, so jj diffedit --to @- shows @ on the left and edits its parent. Otherwise the target is -r and the base is all of its parents. merge_commit_trees returns a single parent's tree as is and merges several, resolving what it can, so for a merge commit you edit its changes relative to the merged parents (source). Either way only the target is rewritten; the base commits are only read. The instructions say which commit you are editing and, for --from/--to, what it is compared with (source).

Loading the editor

diff_editor uses --tool by name if given, and ui.diff-editor otherwise. :builtin is the only built-in diff editor. Any other name is looked up in [merge-tools.<name>], and an unknown name is run as a program with the default arguments (DiffEditTool, with_name). An external tool without edit arguments is rejected before anything opens (source).

An external editor

edit_diff_external does this:

  1. It lists the paths that differ between the two trees under the matcher. Only those are checked out, as sparse patterns, so unchanged files never appear (source).
  2. It checks the base tree out into left and the target tree into right, each a temporary TreeState under a jj-diff- directory. If the edit arguments mention $output, it also checks the target tree out into output (source, 3-pane choice).
  3. It makes left read-only, and right too in 3-pane mode (source).
  4. If instructions are enabled and no such path already exists, it writes JJ-INSTRUCTIONS into the editable side. In 3-pane mode each pane gets a note saying whether to edit it (source).
  5. It runs the tool once, or once per checked-out file in file-by-file mode. A non-zero exit aborts the edit (source).
  6. It deletes JJ-INSTRUCTIONS and snapshots the editable directory. New files are tracked with no size limit, apart from those the base ignore rules exclude. The snapshot's tree is the result (source).

Because the editable side starts as the target's full tree with only changed paths materialized, everything you didn't see, including unmatched paths, keeps the target's value.

The built-in editor

edit_diff_builtin shows the same diff in a terminal UI where you keep or drop each change. Copy tracking isn't handled yet; the code passes empty copy records. apply_diff_builtin then starts from the target tree, resets every changed path to the base's value, and applies only the changes you kept. As its comment says, this matches the external tool's behaviour for unmatched paths. No instructions file is involved.

Descendants

rebase_descendants applies each descendant's own diff on top of the edited commit, which can conflict. reparent_descendants instead gives each descendant its new parent with its tree untouched, so its content stays the same and its diff absorbs your edit.

Invariants: only the target's tree changes, never its parents, change ID or description. The base is never rewritten. Paths outside the matcher keep the target's value. A no-op edit records nothing. The editor opens even when the two sides are identical: the Empty diff - won't run diff editor. check belongs to DiffSelector, which diffedit doesn't use (source).

8. Worked example

From upstream's test_diffedit, which drives a fake external editor. A adds file1, B adds file2 and file3, and @ deletes file1 and changes file2 to b. When plain jj diffedit runs, the left directory holds only file1 and file2, the two paths that changed, and the right holds JJ-INSTRUCTIONS and file2. file3 isn't checked out at all. Closing the editor without changes prints Nothing changed. (source). With the editor resetting file2 to the left side instead:

Upstream's snapshot of the output (source):

Working copy  (@) now at: kkmpptxz 40ad4f80 (no description set)
Parent commit (@-)      : rlvkpnrz 7e268da3 (no description set)
Added 0 files, modified 1 files, removed 0 files

jj diff -s then shows only D file1. The working copy was updated because @ itself was rewritten. The same test also covers other cases:

  • jj diffedit -r @- writing file3: Rebased 1 descendant commits., and the change shows up in @ (source).
  • jj diffedit --from @--: the left side is A, so it holds only file1, and resetting file2 deletes it from @ (source).
  • jj diffedit --to @-: edits B against @, and the instructions add The diff initially shows the commit's changes relative to: followed by @'s summary (source).
  • A tool that exits with status 1: Error: Failed to edit diff, and the diff is unchanged (source).

Upstream's test_diffedit_restore_descendants shows the other descendant mode: adding a ; to @-'s line with --restore-descendants prints Rebased 1 descendant commits (while preserving their content)., and @'s diff now goes from println!("bar"); to println!("baz"); with no conflict.
