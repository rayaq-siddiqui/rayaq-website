How jj interdiff works

jj interdiff compares what two revsets change, not what they contain. It moves the combined change of the first revset onto the parents of the second, then diffs the result against the second, so differences between their parents drop out.

In short: jj loads the workspace, which snapshots it, and resolves --from and --to to a revset each (whichever is missing defaults to @), rejecting an empty set or one with gaps. Each side is treated as if its revisions were squashed into one: jj merges the trees of its heads and of its roots' parents. It moves --from's combined change onto --to's parents with one in-memory tree merge, warns about explicit paths found in neither tree compared, diffs the concatenated descriptions as a pseudo-file, and diffs the two trees. Nothing is written.

The command is cmd_interdiff. The help text: "Show differences between the diffs of two revsets". It is "like running jj diff -r on each side, then comparing those results", and the typical use is checking how a change moved since it was pushed, jj interdiff --from push-xyz@origin --to push-xyz (source). Unlike jj diff --from A --to B, which includes everything that differs between A's and B's parents, interdiff leaves that out. Either side may be a range: jj interdiff --from A::B --to C::D compares two stacks as if each were one commit (source).

5. What it reads, and snapshotting

  • Snapshot: yes. It loads the workspace with workspace_helper (source), which snapshots the working copy first (source), so --to @ sees current edits. That snapshot may record a snapshot working copy operation; interdiff itself records nothing.
  • Reads: the view at the current (or --at-op) operation, every commit in both sets with its roots, heads and the roots' parents, their trees, and file contents for the matched paths. A code comment notes each revset is evaluated four times: for the commits, the gap check, the roots and the heads (source).
  • Output: the unmatched-paths warning goes to stderr before the pager is requested (source); the diff goes through the pager.

6. Algorithm and invariants

Moving --from's combined change onto --to's parents

Each side is first reduced to roots and heads (source). The "to" side of the diff is the merged tree of --to's heads. The "from" side is what --from's combined change would produce on --to's parents: get_from_to_trees collects the unique parents of each side's roots in encounter order (source), merges each set of parents and each set of heads into one tree (source), then runs one three-way merge: --to's parent tree plus the change from --from's parent tree to --from's head tree (source). Whatever the two sets of parents disagree on is on both sides and cancels out.

The doc comment contrasts this with rebase_to_dest_parent: it "rebases the combined diff rather than each commit's diff separately" (source). That matters for a range containing a merge. In upstream's test, two branches both add shared as x and their merge changes it to y; adding the commits' diffs one by one would count x twice and leave a spurious add/add conflict even when a range is compared with itself, while the combined change is simply "absent → y" (source). There is no special case when both sides have the same parents: the merge then resolves trivially to --from's head tree, and interdiff shows the same file changes as jj diff --from A --to B, except that renames are not detected. When the parents differ, the merge can conflict; the conflict is materialized on the "from" side, labelled with the three roles above, and the diff shows it being replaced by --to's content (see the example). A label names one commit in detail, or several commits by short label joined with ", " (source).

Why gaps are rejected

Before evaluating a side, resolve_revset calls check_diff_revset_has_no_gaps, shared with jj diff -r. It computes roots()..heads() minus the set and fails if anything is left: a revision between the roots and heads but outside the set would have its change silently folded in, because only the roots' parents and the heads' trees are used. Several heads and several roots are fine (source).

The description pseudo-file

Before the files, the descriptions are diffed under the dummy path JJ-COMMIT-DESCRIPTION (source). Each side's text is the descriptions of all its commits joined with a newline, in the order the revset yields them; a TODO notes this won't show reordered commits nicely (source). show_text_diff hands both to show_diff_bytes, which prints nothing if they are equal, and nothing for the short formats, where a dummy path "wouldn't be useful"; it prints a hunk for --git and --color-words, and nothing yet for an external --tool (source). So interdiff -s lists only real files.

Relation to evolog and op log

jj evolog -p and jj op log -p / jj op show -p render their patches with show_inter_diff, which rebases each predecessor with rebase_to_dest_parent and diffs against a single commit (evolog, op diff). interdiff no longer goes through it: since it compares whole revsets, it computes its own trees and calls show_text_diff and show_diff directly (source). The two paths produce the same output for one commit on each side.

Invariants: exactly two trees are compared. No commit is rewritten and nothing is stored; the rebased tree exists only for the diff. Swapping --from and --to generally does not just reverse the output, since the change always moves onto --to's parents.
