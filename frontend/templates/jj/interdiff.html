How jj interdiff works

jj interdiff compares what two revisions change, not what they contain. It moves the first revision's changes onto the second revision's parents, then diffs the result against the second revision, so differences between their parents drop out.

In short: jj loads the workspace, which snapshots it, and resolves --from and --to to one commit each (whichever is missing defaults to @). It warns about explicit paths found in none of the four trees involved. Then it rebases --from's tree onto --to's parents in memory, diffs the two descriptions as a pseudo-file, and diffs the rebased tree against --to's tree. Nothing is written.

The command is cmd_interdiff. The help text: "Show differences between the diffs of two revisions". It is "like running jj diff -r on each change, then comparing those results", and the typical use is checking how a change moved since it was pushed, jj interdiff --from push-xyz@origin --to push-xyz (source). Unlike jj diff --from A --to B, which includes everything that differs between A's and B's parents, interdiff leaves that out.

5. What it reads, and snapshotting

  • Snapshot: yes. It loads the workspace with workspace_helper (source), which snapshots the working copy first (source), so --to @ sees current edits. That snapshot may record a snapshot working copy operation; interdiff itself records nothing.
  • Reads: the view at the current (or --at-op) operation, the two commits and their parents, the four trees, and file contents for the matched paths.
  • Output: the unmatched-paths warning goes to stderr before the pager is requested (source); the diff goes through the pager.

6. Algorithm and invariants

Rebasing --from onto --to's parents

The "from" side of the diff is not --from's tree. It is what --from's tree would be if --from sat on --to's parents: rebase_to_dest_parent takes --to's parent tree and applies the change from --from's parent tree to --from's tree, as one three-way merge (source). The "to" side is --to's own tree (source). Whatever the two parents disagree on is therefore on both sides and cancels out.

There is a fast path: if --from has exactly the same parents as --to, its tree is used unchanged and no merge runs (source). Then interdiff shows the same file changes as jj diff --from A --to B, except that renames are not detected. When the parents differ, the merge can conflict; the conflict is materialized on the "from" side, labelled with the three roles above, and the diff shows it being replaced by --to's content (see the example).

The description pseudo-file

Before the files, the two commit descriptions are diffed under the dummy path JJ-COMMIT-DESCRIPTION (source). show_diff_bytes prints nothing if they are equal, and nothing for the short formats, where a dummy path "wouldn't be useful"; it prints a hunk for --git and --color-words, and nothing yet for an external --tool (source). So interdiff -s lists only real files.

Shared with evolog and op log

The same show_inter_diff renders the patches of jj evolog -p, where each entry is compared with its predecessors (source), and of jj op log -p / jj op show -p for rewritten commits, which use only the first predecessor (source). interdiff always passes exactly one "from" commit (source).

Invariants: exactly two trees are compared. Neither commit is rewritten and nothing is stored; the rebased tree exists only for the diff. Swapping --from and --to generally does not just reverse the output, since the rebase always goes onto --to's parents.

8. Example output

$ jj interdiff --from left
Modified JJ-COMMIT-DESCRIPTION:
   1     : add file2 left
        1: add file2 right
Modified regular file file2:

        2: bar
