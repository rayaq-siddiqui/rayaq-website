How jj file untrack works

jj file untrack removes paths from the working-copy commit while leaving the files on disk. The paths must already be ignored, or the next snapshot would simply add them back.

In short: jj loads the workspace, which snapshots it as usual, and locks the working copy. It writes a new tree for @ without the matching paths and rewrites @ with it. It then resets the working copy's tree state to that commit without touching any files. A snapshot checks the result: if any of the paths come back because they aren't ignored, it fails and nothing is recorded. Otherwise it rebases descendants, updates the Git index in a colocated workspace, and commits the operation untrack paths.

The command is cmd_file_untrack. Its only argument is the paths, which "must already be ignored", via .gitignore or, in colocated workspaces, .git/info/exclude (source). Unlike jj file track, it rewrites @ straight away. It only ever changes the working-copy commit.

5. Transaction and operation

  • Transaction: a raw Transaction committed with tx.commit, with the working copy locked throughout, so the commit rewrite and the working-copy update land together (start, commit).
  • Operation description: untrack paths (source).
  • Commits rewritten: @, then its descendants, with Rebased N descendant commits. if any (source).
  • On error: when a path isn't ignored, the lock is dropped before the error returns and the transaction is never committed, so the repo and the saved working-copy state stay as they were (source, test).
  • jj undo brings the paths back into @.

6. Algorithm and invariants

  1. Remove. For every entry of @'s tree matching the filesets, set it to absent, then write the tree (source).
  2. Rewrite. rewrite_commit(@).set_tree(new_tree) (source).
  3. Reset. Point the working copy at the new commit without changing any file, so the files stay on disk but jj no longer records them as tracked (source).
  4. Verify. Snapshot with the normal auto-track options, as the next command would. If the result differs from the new commit and some of the differing paths match the filesets, those files would be re-added: fail with '…' is not ignored. (or '…' and N other files are not ignored.). If it differs only elsewhere, someone changed the working copy meanwhile; reset again so those edits aren't folded into this operation (source).
  5. Finish. Rebase descendants, export to Git if colocated, commit, save the working copy at the new operation, then print warnings (source).

Invariants: files on disk are never deleted or modified. Only the working-copy commit's tree loses paths. A path that a later snapshot would re-add is refused. Paths that aren't tracked are ignored, with a warning for explicit ones.
