How jj split works

jj split turns one commit into two. You choose which changes go in the first. The rest form the second, either as its child (the default), as a sibling (--parallel), or with the selection extracted elsewhere in the graph (-o/-A/-B).

In short: jj resolves one mutable commit (default @) and selects changes from it, in a diff editor unless you gave paths. It then builds two commits from the original. The "selected" commit gets the chosen tree. The "remaining" commit gets the full original tree (on top of the selected one) or the original minus the selection (in parallel mode). Which of the two keeps the original change ID depends on the mode. Both descriptions are edited in one file. Descendants and working copies are moved onto the remaining commit, and so are bookmarks, by default. One operation records it all: split commit <id>.

The command is cmd_split. Its help text draws the three layouts (source). Selection is the shared DiffSelector (see jj commit, whose help text compares itself with split). The bulk description editor is the one jj describe uses for several commits. The -o/-A/-B mode hands the selected commit to the rebase engine.

5. Transaction and operation

  • Transaction: one, always. Even an empty split writes two commits (source).
  • Operation description: split commit <full hex id of the target> (source).
  • Commits created or rewritten: two replace the target, and every descendant is rebased. With -A/-B, the new children of the selected commit are rebased too.
  • Working copy: snapshotted at the start. If @ was split, it becomes the remaining commit.
  • jj undo restores the single original commit and the old descendants.

6. Algorithm and invariants

Selecting

select_diff runs the diff selector on parent tree → commit tree, with instructions explaining that the right side becomes the new first commit. Paths without -i select whole files. The result is a CommitWithSelection. If the selection is everything, jj warns that the original revision becomes empty. If it is nothing, jj warns that the new revision will be empty. Neither is an error.

Building the two commits

  • Selected (source): the selected tree, the -m text or the original description, with trailers added only if the description isn't empty. In move mode it drops the rewrite source and draws a new change ID, so the original commit doesn't become divergent.
  • Remaining (source): the full original tree. On top of the selected commit, its diff is exactly the unselected changes. In parallel mode, the tree is the original with the selected diff reverse-applied, so its diff against the shared parents is the unselected changes. Outside move mode it is the one with the new change ID.
  • Descriptions (source): unless -m was given without --editor, both drafts are written as hidden commits, with parents set as they will be. They are edited in one bulk file, under the intros "Enter a description for the selected changes." and "Enter a description for the remaining changes.". The result is validated like describe's bulk edit.

Placing them

rewrite_descendants (default and parallel) first, with the legacy setting, re-records the target as rewritten to the remaining commit, which is what carries bookmarks there. It then walks the target's descendants, replacing whichever parent now stands for the target with the remaining commit, or with both commits in parallel mode, and rebases each one. Finally it points every workspace that was on the target at the remaining commit.

move_first_commit (-o/-A/-B) first rebases the target's descendants onto the remaining commit, which kept the change ID. It maps the requested parents and children through those rewrites, then runs move_commits on the selected commit alone. It counts rebased commits carefully so that a commit rewritten twice is reported once.

Invariants: the two commits' changes add up to the original's. Exactly one of them continues the original change; the other is a new change. Descendants keep their content relative to the combined pair. Author and author date carry over to both, as upstream's test_split_by_paths checks.

The help text says "Splitting an empty commit is not supported because the same effect can be achieved with jj new" (source). The code has no such check, though: upstream's test_split_empty splits an empty commit successfully, with the "Empty diff" and "All changes have been selected" warnings, and gets two empty commits.
