How jj log works

jj log evaluates a revset and draws it as a graph, children before parents. Edges between shown commits are recomputed so that skipped commits become "elided" nodes, branches are grouped together, and each commit is rendered with a template.

In short: jj picks a revset (-r, else revsets.log, narrowed to commits that touch the given paths), evaluates it, and streams it as a graph whose edges are direct, indirect or missing. TopoGroupedGraph reorders that stream so each branch is drawn in one piece, with the branch holding @ first. -n cuts it, and --reversed flips it. Each commit is rendered with templates.log, plus an optional diff. The result is drawn by sapling's renderdag. Nothing is written: no transaction, no operation.

The command is cmd_log. The help text: "Show revision history" (source). It also says spans of revisions that -r leaves out are drawn as a synthetic node labelled "(elided revisions)", and that @, ◆ (immutable) and ○ mark the nodes.

5. What it reads, and snapshotting

  • Snapshot: yes. It loads the workspace with workspace_helper (source), which snapshots the working copy first (source), so @ shows current edits. That snapshot may record a snapshot working copy operation; log itself records nothing.
  • Reads: the view at the current (or --at-op) operation, the index, every shown commit, and trees only when a diff or explicit path needs them.
  • Output: through the pager, requested before anything is written (source). Warnings go to stderr.

6. Algorithm and invariants

Edges between shown commits

stream_graph() walks the evaluated set in index order with RevsetGraphWalk, skipping transitive edges (source). A parent in the set gives a direct edge. A parent outside it is walked through until the walk reaches commits in the set, giving one indirect edge to each nearest such ancestor. A path that never comes back into the set gives a missing edge. When a commit has an indirect edge, any edge whose target is also reachable through its other edges is dropped (source), so a commit isn't linked to its grandparent as well as its parent.

cmd_log then turns these into renderer edges, keyed by (commit ID, is_synthetic) (source). Direct stays direct. Indirect becomes a direct edge to a synthetic node for that target, drawn as ~ (elided revisions) with the elided label (source); with ui.log-synthetic-elided-nodes = false it stays a dotted indirect edge. Missing edges collapse into one, drawn as ~ below the node. graphlog.rs maps them to renderdag's parent, ancestor and anonymous edges (source).

Ordering and the limit

  1. Group branches. TopoGroupedGraph is a depth-first walk from the heads built on Kahn's algorithm (source): a commit is emitted once all its children have been, and at a merge the last parent's branch comes first. A new head is only taken when nothing is ready, choosing one that unblocks a waiting fork point (source). The input is read lazily (source).
  2. Prioritize. Every commit of revsets.log-graph-prioritize that is also in the shown set is queued first (source). The intersection is taken against the query resolved at its own visibility, so the prioritized commit is always in the input, which TopoGroupedGraph requires (source).
  3. Limit, then reverse. take(N) is applied to the grouped stream, not its input, for the same reason (source). --reversed collects those nodes and flips every edge (reverse_graph), so commits whose parents were cut off become roots.
  4. Render. Each commit's template and diff are written into a buffer at the width left beside the graph (source, LogContentFormat), the node template picks the symbol, and add_node draws the row (source) with renderdag's GraphRowRenderer (source).

With --no-graph none of the grouping happens: commits come in index order, newest first, so the limit can pick different commits than in graph mode (see the example).

Invariants: a child is always printed before its parents (after them with --reversed). Every commit in the set is printed exactly once, unless cut by -n. Nothing in the repository changes.

8. Example output

From upstream's test_log_limit: a, then b on it, c on a, and d (@) merging c and b. 

$ jj log -T description --limit=3
@    d
├─╮
│ ○  b
○ │  c
├─╯

$ jj log -T description --limit=2
@    d
├─╮
│ ○  b

$ jj log -T description --limit=2 --no-graph
d
c

$ jj log -T description --limit=3 --reversed
○  c
│ ○  b
├─╯
@  d

In graph mode the second parent's branch, b, comes right after the merge; without the graph it's index order, so c. Reversed, a was cut by the limit, so b and c are roots. With a path, from the same test:
