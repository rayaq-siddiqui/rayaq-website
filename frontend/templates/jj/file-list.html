How jj file list works

jj file list prints the paths in one commit's tree, optionally narrowed by filesets. It walks the tree depth-first in name order, skips directories the matcher rules out, and renders one TreeEntry per file, symlink, submodule or conflicted path.

In short: jj resolves -r (default @), parses the positional filesets into a matcher (everything when there are none), and iterates tree.entries_matching(matcher). Directories are descended into rather than printed, and a conflicted tree is merged on the fly. Each entry is rendered with -T or templates.file_list. Afterwards, any literal path that named nothing gets a warning. Nothing is written: no transaction, no operation.

The command is cmd_file_list, and the walk is jj-lib's TreeEntriesIterator. The help text: "List files in a revision" (source).

FileListArgs

The help calls the positional arguments "prefixes", but they are full fileset expressions: parse_file_patterns returns all() for no arguments and otherwise unions each argument parsed with parse_maybe_bare (cli_util.rs, fileset.rs). Globs such as 'glob:**/*.rs' and operators such as ~ work. Upstream's fileset docs cover the language.

2. Configuration

templates.file_list supplies the template when -T is absent (source). Its built-in value prints the path and a newline, through an alias meant for overriding (templates.toml, alias): 

[templates]
file_list = 'format_path(path) ++ "\n"'

[template-aliases]
'format_path(path)' = 'path.display()'

path.display() is relative to the current directory and uses the platform's separator (source, docs), so running in a subdirectory prints paths such as ../README.md. The output is labelled file_list for colour rules. The keywords are the six methods of TreeEntry (commit_templater.rs, docs):

KeywordTypeValue
pathRepoPathRepo-relative path. Printing it directly gives the slash-separated repo path; .display() gives the cwd-relative one.
normal_valueOption<TreeValue>The resolved value (prints as its object ID), or none for a conflict.
conflictBooleanTrue when the merged value isn't resolved.
conflict_side_countIntegerSides after simplifying the merge; 1 when resolved.
file_typeStringfile, symlink, tree, git-submodule or conflict (source).
executableBooleanFor files, the executable bit; for a conflict of files, the bit if the sides agree after a trivial merge. False for anything else (source, resolve_file_executable).

revset-aliases apply when resolving -r, and fileset-aliases when parsing the filesets. ui.pager controls paging.

5. What it reads, and snapshotting

  • No transaction, no operation of its own. The command only reads the repo it loaded (source).
  • Snapshot: workspace_helper snapshots the working copy first and prints the snapshot stats (source). If files changed on disk, that snapshot records its own operation, so a file you just created is listed in @, and an ignored or too-large one isn't.
  • Only trees. The listing comes from tree objects alone. Blob contents aren't read, so the cost grows with the number of directories visited, not with file sizes.
  • jj undo has nothing to revert, except the snapshot if one was taken.

6. Algorithm and invariants

TreeEntriesIterator keeps a stack of directories, each holding its remaining entries in reverse name order. It starts with one entry, the root path with the whole tree as its value (source). Each next() (source):

  1. Pops the next entry off the top directory, or pops the directory itself when it's empty. The iteration ends when the stack is empty.
  2. Tries to read it as a directory with to_tree_merge. That succeeds only if every term of the merged value is a tree or absent; absent terms become empty trees (source). On success the subtrees are pushed as a new stack level and nothing is yielded.
  3. Otherwise yields it. A file, symlink, submodule, or a conflict mixing a tree with a non-tree is returned as (path, value). In the last case the conflicted path is listed once, and nothing inside the directory is.

Building a directory level is where the matcher is applied (source). For each entry: a subdirectory is skipped when matcher.visit(path) says nothing below it can match, and anything else is kept only if matcher.matches(path). A directory that might hold a match is still descended into, and its files are checked one by one. When the directory's trees conflict, entries come from all_tree_entries, which resolves each name trivially using the store's same_change rule before deciding (source).

Unmatched paths. After the listing, every literal path in the fileset (FilePath and PrefixPath patterns, not globs) is looked up with tree.path_value. Those that are absent are joined into one warning (source, as_path, explicit_paths). A path naming a directory isn't absent, so it never warns.

Invariants: output order is depth-first with each directory's entries in name order, so dir/file sits between conflict-file and exec-file. Directories never appear as entries of their own unless they conflict with a non-directory. Each path appears at most once. The listing doesn't depend on the working copy beyond the snapshot folded into @.

8. Example output

From upstream's test_file_list. One side adds dir/file, exec-file, conflict-file and conflict-exec-file, marking the two exec ones executable. A sibling of it, off the root, writes different contents to the two conflict files and marks conflict-exec-file executable. @ is a merge of both. With the default template: 

$ jj file list
conflict-exec-file
conflict-file
dir/file
exec-file

With a template using the TreeEntry keywords. Both conflict files are listed once with file_type conflict. executable is true for conflict-exec-file because both sides set the bit: 

$ jj file list -T 'separate(" ", path, "[" ++ file_type ++ "]",
    "conflict=" ++ conflict, "executable=" ++ executable) ++ "\n"'
conflict-exec-file [conflict] conflict=true executable=true
conflict-file [conflict] conflict=true executable=false
dir/file [file] conflict=false executable=false
exec-file [file] conflict=false executable=true

Another revision, a filter, and the warning for a path that doesn't exist:

$ jj file list -r 'first_parent(@)'
conflict-exec-file
conflict-file

$ jj file list dir file3
dir/file
Warning: No matching entries for paths: file3

normal_value prints the object ID of a resolved value, here a Git blob (test_file_list_normal_value): 

$ jj file list -T 'path ++ " " ++ normal_value ++ "\n"'
file 6b584e8ece562ebffc15d38808cd6b98fc3d97ea
