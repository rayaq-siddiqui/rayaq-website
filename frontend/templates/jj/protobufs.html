Every schema

jj persists everything that isn't a Git object as Protocol Buffers: commits and trees in the simple backend, jj-only commit metadata in the Git backend, every operation and view, the working copy's state, index segment links, the workspace registry and secure-config metadata. This page covers all seven .proto files, every field, and the Rust code that converts each one.

Conventions

  • All files are proto3 and compiled with prost into jj_lib::protos::<package>. In proto3, an unset scalar reads as its zero value, which is why so much of the conversion code checks for an empty bytes or string to detect old formats.
  • IDs are raw bytes, not hex. Commit, tree, file, view and operation IDs are all stored this way.
  • Content-addressed objects are named by a hash of the Rust value, not of the proto bytes. The simple backend and the simple op store both compute the ID as blake2b_hash(&value) over the Rust struct's ContentHash, then write the encoded proto to a file named after that ID (commit, view, operation).
  • Deprecated fields are kept so old repos still load. New code writes only the current fields; readers fall back to the deprecated ones when the current ones are empty.

simple_store.proto

The native object format of SimpleBackend, a backend that stores everything as individual proto files. Git-backed repos never use these messages: commits and trees are Git objects there. Full file.

Signing works on the proto itself: write_commit encodes the commit, passes those bytes to the signing function, and stores the result in secure_sig. When reading, commit_from_proto takes secure_sig out first and re-encodes the remainder, which reproduces exactly the bytes that were signed (write, convert, signatures).

git_store.proto

The Git backend stores commits as real Git commits. That leaves out what Git can't represent, and this one message carries it. The serialized bytes go into a stacked table under .jj/repo/store/extra, keyed by the Git commit ID. Entries are added both when jj writes a commit and when it imports one from Git (write, import). Full file. 

syntax = "proto3";

package git_store;

message Commit {
  repeated bytes predecessors = 2;
  bytes change_id = 4;

  // Alternating positive and negative terms. Set only for conflicts.
  // Resolved trees are stored in the git commit
  repeated bytes root_tree = 1;
  // TODO(#1624): delete when we assume that all commits use this format
  bool uses_tree_conflict_format = 10;

  bool is_open = 8 [deprecated = true];
  bool is_pruned = 9 [deprecated = true];
}
Field#TypeStatusMeaning
root_tree1repeated bytesread onlyConflicted root trees for commits written before conflicts moved into a commit header (about March 2024). New writes leave it empty.
predecessors2repeated bytescurrentRewritten-from commit IDs.
change_id4bytescurrentThe change ID. If it's empty, the change ID read from the Git commit is kept.
is_open8booldeprecatedNot read or written by current code.
is_pruned9booldeprecatedNot read or written by current code.
uses_tree_conflict_format10boolcurrentAlways written as true. The legacy root_tree is honoured only when it's set.

Everything else about a commit's jj view lives in the Git commit itself. A conflicted root tree is written as a jj:trees header of space-separated hex tree IDs, which must hold an odd number of at least three, so jj and Git can never disagree about a resolved commit's contents. Conflict labels go in a jj:conflict-labels header, and the change ID can go in a change-id header written as reverse hex. When a Git commit has no change ID, jj derives a synthetic one from the commit ID (jj:trees, headers on write, serialize_extras / deserialize_extras).

simple_op_store.proto

The operation log. Every operation and every view is one file under .jj/repo/op_store/operations/ or views/, named by the hex of its 64-byte ID. The root operation and root view are never stored: both are all-zero IDs, and the store synthesizes them on read (read/write). Full file.

view_to_proto · view_from_proto

Refs: RefTarget, RefConflict, RefTargetTerm, RefConflictLegacy

A ref target in Rust is RefTarget = Merge<Option<CommitId>>: a normal ref, an absent one, or a conflicted one. The proto has accumulated three encodings of it:

EncodingFieldsStatusNotes
RefTarget.commit_idoneof #1, bytesdeprecatedA plain, non-conflicted ID (jj ≤ 0.8).
RefTarget.conflict_legacy → RefConflictLegacyoneof #2; removes #1, adds #2 (repeated bytes)deprecatedCan't represent absent terms. Converted with RefTarget::from_legacy_form.
RefTarget.conflict → RefConflictoneof #3; removes #1, adds #2 (repeated Term); Term.value #1 (optional bytes)currentAlways written, even for a normal ref, which is just one add and no removes. An absent term is a Term with no value.
RefTargetTermvalue #1 (optional bytes)currentA flat term list used by RemoteRef.target_terms: alternating add/remove, odd length, and an even count is a decode error.

A missing RefTarget message reads as absent (terms, ref_target_to_proto, ref_target_from_proto).
