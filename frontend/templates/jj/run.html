How jj run works

jj run checks each selected commit out into its own scratch working copy, runs a command there, and amends the commit with whatever the command left behind. It can also just run a check across many commits without changing any of them.

In short: jj resolves the revisions (default revsets.run) and orders them parents first. Unless --ignore-changes is given, it refuses immutable ones. It then runs the command on up to --jobs commits at once, each in a reusable slot under .jj/run/default/, with JJ_CHANGE_ID, JJ_COMMIT_ID and JJ_WORKSPACE_ROOT set. After each command it snapshots the slot. A failure stops the run and rewrites nothing, unless --ignore-errors is given. At the end one transaction rewrites every commit whose tree changed and rebases the rest of their descendants. The operation is run: rewrite <n> commits.

The command is cmd_run. Its help text names the environment variables and gives jj run -j 4 -- pre-commit run .github/pre-commit.yaml as an example (source). Unlike jj fix, which pipes single files through formatters in memory, jj run materializes whole trees on disk, so it can run builds and test suites.

5. Transaction and operation

  • Transaction: one, started before any command runs and committed only after all of them have finished, so the result is all or nothing (start).
  • Operation description: run: rewrite <n> commits, where n counts the commits whose own tree changed (source).
  • No changes: with --ignore-changes, or when no tree changed, jj finishes the transaction as run: nothing changed. Since the repo is untouched, tx.finish just prints Nothing changed. and records no operation (source, finish).
  • Failure: without --ignore-errors, the first failing command returns an error before the rewrite step. The transaction is dropped, so even commands that already succeeded change nothing (source).
  • Slots live outside the operation log. Their files and tree state persist after the run, whatever the outcome.
  • jj undo restores the previous view, bringing back the original commits.

6. Algorithm and invariants

The workspace pool

WorkspacePool has --jobs slots, numbered from 1, under .jj/run/default/, next to .jj/repo rather than inside it. acquire does this:

  1. It tries each slot's lock without blocking, sleeping from 10 ms, doubling up to 250 ms, until one is free (source).
  2. If the slot has a saved tree_state and --clean wasn't given, it loads it and deletes the file. The missing file marks the slot as dirty until the job saves it again, so a crash mid-job makes the next user wipe the slot (source).
  3. Otherwise it deletes the slot's working copy and state and starts from an empty in-memory tree state (source).
  4. It sets the sparse patterns, or the root path for full, and checks the commit's tree out. Because it diffs against the saved state, only changed files are touched and ignored build artifacts survive (source).
  5. For a reused slot, it snapshots once more to find files that a previous commit ignored but this one doesn't, deletes them, and checks out again (source).

One job

rewrite_commit runs the command in the slot, or in the same subdirectory you ran jj run from unless --root is given. If that subdirectory doesn't exist in the commit, the commit is skipped (source, subdir). The command gets JJ_WORKSPACE_ROOT (the slot directory), JJ_CHANGE_ID, JJ_COMMIT_ID, and a null stdin. It is killed if its task is dropped. Output is buffered and printed whole when the job finishes, so parallel jobs never interleave (source).

Then jj snapshots the slot using the snapshot.auto-track matcher. If the command failed, it deletes the untracked, non-ignored files it left behind and discards the result. Either way it saves the slot's tree state. A successful snapshot becomes the job's new tree, conflicts included (source).

Scheduling

run_inner spawns jobs in parents-first order on a multi-threaded tokio runtime, with at most jobs in flight (runtime). Results come back in completion order through a channel to a consumer that runs at the same time and prints each one as it arrives (source). On a failure without --ignore-errors, the producer shuts down the remaining tasks, which kills their processes, and the consumer returns the error. Every job checks out its commit's original tree, so a commit never sees a command's changes to its ancestors.

Rewriting

A job's tree counts as changed only if its trees and conflict labels differ from the original (source). jj then walks the selected commits and their descendants with transform_descendants, parents first (source):

  • Changed, default: rebase the commit onto its rewritten parents, then 3-way merge rebased + (command result − original). That way the command's diff and any ancestors' changes both carry through (source).
  • Changed, --restore-descendants: rebase it and set its tree to the command result exactly, ignoring what changed in its ancestors (source).
  • Unchanged, or outside the run set: if its parents changed, rebase it, or reparent it with --restore-descendants. These count as rebased descendants (source).

Invariants: nothing is rewritten unless every command succeeded or --ignore-errors was given. Commands never run in your own working copy. Change IDs and descriptions are kept. Only trees change.

8. Worked example

From upstream's test_run_parallel_changes_propagate_to_descendants. A, B and C each add one file, and @ is empty on top. Running jj run --jobs=3 -r=..@ -- sh -c 'touch newfile-$JJ_CHANGE_ID.txt' runs the command on the four commits, at most three at a time. Each job sees only its commit's original tree, so each adds exactly one new file named after its own change ID:

Upstream then lists @- (that is, C):

a.txt
b.txt
c.txt
newfile-kkmpptxzrspxrzommnulwmwkkqwworpl.txt
newfile-qpvuntsmwlqtpsluzzsnyyzlmlwvmlnu.txt
newfile-rlvkpnrzqnoowoytxnquwvuryrwnrmlp.txt

B and C are rebased onto their rewritten parents, and the 3-way merge adds their own command result on top, so every descendant ends up with all its ancestors' new files. With --restore-descendants, C's tree would instead be exactly what its command produced, without A's and B's new files.
