How jj file delete works

jj file delete removes the files matched by some filesets from one revision, and rebases its descendants on top. It never touches the working copy directly; the files go away on disk only because @ changes.

In short: jj resolves -r (default @) and refuses it if it is immutable. It takes every entry of the commit's tree that the filesets match, conflicted or not, and sets it to absent in a tree builder. If the new tree equals the old one, it prints Nothing changed. and records nothing. Otherwise it rewrites the commit with the new tree, rebases descendants (or, with --restore-descendants, reparents them so their content stays), and records delete paths in commit <id>.

The command is cmd_file_delete. Its help text: "Delete files from the given revision. Removes all files matched by the given filesets from the specified revision. Descendants are rebased on top of the rewritten commit." (source). It is the Delete variant of FileCommand (source, dispatch).

5. Transaction and operation

  • Transaction: one, started only after the new tree is written and found to differ (source).
  • Operation description: delete paths in commit <full hex id>, using the commit's id before the rewrite (source).
  • Commits rewritten: the target, then its descendants through rebase_or_reparent_descendants, which prints Rebased N descendant commits. only when N is above zero, adding (while preserving their content) when reparenting.
  • Nothing matched: no transaction and no operation; upstream's test checks the operation ID is unchanged (test).
  • jj undo restores the previous view, bringing the files back in the target and its descendants.

6. Algorithm and invariants

What gets deleted

tree.entries_matching(matcher) yields every file entry the filesets match, so a directory path deletes everything under it and a pattern such as glob:*.txt deletes every match (source, test). Unlike file chmod, it doesn't look at the value: files, symlinks, submodules and conflicts are all set to Merge::absent(), which the builder documents as the way to remove a value (source).

Conflicted files

A conflicted entry is overridden by a resolved, absent value, so the file and its conflict disappear together. In upstream's test, deleting the conflicted file from a merge leaves jj debug tree empty (test).

Descendants

By default rebase_descendants replays each descendant's own diff on the rewritten commit, so a descendant that didn't touch a deleted file loses it too. With --restore-descendants, reparent_descendants keeps each descendant's tree as it was; its diff now re-adds the file. restore uses the same pair.

Invariants: only the target's tree changes, never its identity or metadata. Paths outside the filesets are untouched. If nothing matched, nothing is recorded.

8. Worked example

From upstream's test_file_delete. base adds file, dir/a, dir/b, notes.txt, data.txt and keep; child, the working-copy commit, only adds other. Then jj file delete -r=base file is run with and without --restore-descendants:

Upstream's snapshot for the plain delete (source):

$ jj file delete -r=base file
Rebased 1 descendant commits.
Working copy  (@) now at: zsuskuln 69c03f6b child | child
Parent commit (@-)      : rlvkpnrz 0f03ba3b base | base
Added 0 files, modified 0 files, removed 1 files

With --restore-descendants the first line becomes Rebased 1 descendant commits (while preserving their content). and there is no Added … removed … line, since @'s tree is unchanged (source).
