How jj git import works

jj git import reads the branches and tags in the backing Git repository and brings jj's view up to date with them: it imports new commits and moves bookmarks and tags. It also abandons commits that Git no longer reaches. In a colocated workspace this already happens at the start of every command, so the command only matters for non-colocated workspaces or with --ignore-working-copy.

In short: jj lists Git's refs/heads/*, refs/remotes/*/* and refs/tags/* and compares them with the Git refs it last saw (git_refs) and with its remote bookmarks and tags. For each change it imports the commits, updates the remote ref (NAME@git for local Git branches and tags), and, if that remote ref is tracked, merges the change into the local bookmark or tag. Commits that only the old ref targets reached are abandoned. New commits that share a change ID with old ones are recorded as their rewrites. Everything happens in one operation, import git refs.

The command is cmd_git_import and the work is jj_lib::git::import_refs, the same code jj git fetch uses after fetching. The reverse direction is jj git export. Bookmarks, tags and tracking are described on the view page.

1. Command-line surface

jj git import takes no arguments of its own (GitImportArgs). Like jj git export, it is skipped in a colocated workspace unless the working copy isn't writable: with --ignore-working-copy, or at an operation other than the head (source, is_working_copy_writable).

3. End-to-end flow

  1. Colocated check. In a colocated workspace, the snapshot at the start of every command imports Git's HEAD and refs itself, in its own import git head and import git refs operations, and prints Done importing changes from the underlying Git repo. (snapshot, import_git_refs). The command then has nothing to add (source).
  2. Remotes. Every remote in the Git config gets an entry in the view, even one with no refs yet, so its absent refs can be tracked (source).
  3. Diff. See §6.
  4. Commits. The new ref targets that jj's index doesn't have are imported in bulk. If that fails, each one is retried alone so the error names the ref (source). They are indexed and added as visible heads.
  5. Refs. See §6.
  6. Report and finish. Each changed ref is printed, for example bookmark: a@git [new] tracked, followed by abandoned and rewritten commits (print_imported_changes) and refs that couldn't be imported. Then tx.finish rebases descendants (Rebased N descendant commits.) and records the operation (source).

4. Core architecture touchpoints

  • Git backend: import_head_commits copies commits Git already has into jj's backend metadata; see the commits page.
  • Index: imported commits are indexed so revsets can see them.
  • View: git_refs, remote bookmarks and tags, local bookmarks and tags, and the visible heads all change here; see the view page.
  • Rewrites: abandoned commits and synthetic predecessors are recorded on the transaction, so descendants are rebased when it finishes; see transactions.

5. Transaction and operation

  • Transaction: one, finished as import git refs (source). If nothing changed, it prints Nothing changed. and records nothing (source).
  • Commits: new commits are imported, not created; old ones may be abandoned, and their descendants rebased.
  • Undo: jj op restore (or jj undo) fully reverses an import, because it only changed jj's own state. Running jj git import again re-imports the same refs (test).

6. Algorithm and invariants

The diff

diff_refs_to_import starts from what jj knew: the git_refs, every remote bookmark, and only the @git tags (the command passes all_remote_tags = false because real remote tags are never updated by Git; source). It then walks Git's local branches, remote branches and tags. Each Git ref that resolves to a commit is removed from the "known" sets; if its value differs from git_refs it is a changed Git ref, and if it differs from the remote ref it is a remote ref update (collect_changed_refs_to_import). Whatever is left in the known sets has disappeared from Git and is updated to absent. Refs that don't point to a commit are skipped, not reported. Results are sorted so merges and output are stable.

Remote refs and local refs

A remote ref keeps its old tracking state; a remote ref seen for the first time gets the default from default_remote_ref_state_for: @git bookmarks and all tags are tracked, other remote bookmarks only if auto-track-bookmarks matches. For tracked refs, the change is merged into the local bookmark or tag as a 3-way merge whose base is the remote ref's old tracked target. So if both jj and Git moved a bookmark, the local bookmark becomes conflicted rather than one side winning. The remote ref itself is simply set to the new value (source).

Abandoning and rewrites

With abandon-unreachable-commits, jj abandons the commits that were ancestors of the old ref targets but are no longer ancestors of anything pinned: local bookmarks and tags, untracked remote refs that are still visible, or the root (abandon_unreachable_commits, pinning). Tracked remote refs don't pin, because their changes were merged into the local refs.

With record-synthetic-predecessors, each newly imported commit whose change ID also appears among the commits that became unreachable gets that old commit as its predecessor. If abandoning is also on, the old commit is marked rewritten into the new one, or divergently rewritten if there are several. Such commits are then not reported as abandoned (record_synthetic_predecessors, source). This is how a commit amended with plain Git shows up as a rewrite of the jj commit, and why its descendants are rebased onto it when the transaction finishes.

Invariants: after an import, every Git branch and tag that resolves to a commit is mirrored in the remote refs and git_refs, and its commits are visible. Tracked changes are merged, never overwritten. git_refs holds exactly what jj last saw in Git.
