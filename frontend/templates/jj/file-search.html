How jj file search works

jj file search is a grep over one commit's tree. It walks the same filtered tree as jj file list, reads each file's contents from the store, and tests every line against a string pattern. Conflicted files are searched on each of their sides.

In short: jj resolves -r (default @), turns the positional filesets into a matcher, and parses --pattern as kind:pattern, with the kind defaulting to regex. For each matching entry it materializes the value. A file's bytes are split on \n, and each matching line is printed as path:line (or path:N:line with -n, or just the path with --name-only). Symlinks, submodules and non-file conflicts are skipped. Nothing is written.

The command is cmd_file_search, and the line printer is write_matches. The help text: "Search for content in files". It also warns: "This is an early version of the command. It does not search files concurrently" (source).

FileSearchArgs

As with jj file list, the help calls the positional arguments "prefixes", but each is a full fileset expression, parsed by parse_file_patterns (cli_util.rs, fileset.rs). Upstream's fileset docs cover the language.

--pattern is split at its first colon (source). The part before the colon has to be one of the eight kinds from_str_kind knows (str_util.rs), so foo:bar is an error rather than a regex. Colons after the first are part of the pattern, so regex-i:foo:bar searches for foo:bar. To search for a literal colon in a regex, spell the kind out.

KindA line matches when
regex (default), regex-iThe regular expression matches somewhere in the line. It runs on bytes, so non-UTF-8 files are searched too.
substring, substring-iThe line contains the text.
glob, glob-iThe whole line matches the glob. A glob with no wildcard characters becomes exact.
exact, exact-iThe whole line equals the text, so exact: finds blank lines.

StringPattern, glob, match_lines. exact-i and substring-i fold ASCII case only; regexes are Unicode-aware (source).

2. Configuration

There is no template and no config key of its own: the output format is hard-coded, and a TODO says so (source). Paths are printed relative to the current directory with format_file_path, so running in dir/ prints file3:… rather than dir/file3:…. revset-aliases apply when resolving -r, fileset-aliases when parsing the filesets, and ui.pager controls paging. The matched line is written as raw bytes, without colour.

5. What it reads, and snapshotting

  • No transaction, no operation of its own. The command only reads the repo it loaded (source).
  • Snapshot: workspace_helper snapshots the working copy first (source). If files changed on disk, that snapshot records its own operation, so jj file search sees what is on disk now, not the last snapshot.
  • Whole blobs, from the store. Even for @, contents come from the commit's tree objects, not the files on disk. Each file is read to the end into memory (read_all), and binary files are searched like any other. Symlink targets are read too, by the materializer, but never searched.
  • Sequential. One file at a time, in tree order; reading concurrently is a TODO (source).
  • jj undo has nothing to revert, except the snapshot if one was taken.

6. Algorithm and invariants

Each entry the walk yields is passed to materialize_tree_value (source), and the command branches on the result:

Line matching. write_matches splits the contents with split_inclusive('\n'), numbering pieces from 1. It strips the trailing \n before testing, so patterns can anchor to the line's end, then prints the prefix and the original line, adding a newline when the last line has none (source). --name-only uses match_lines, which splits the same way, and stops at the first match (source). Only \n separates lines, so a CRLF line is tested with its \r still attached.

Conflicts. try_materialize_file_conflict_value applies only when every term is a file or absent. It simplifies the merge, dropping pairs that cancel out, and reads each remaining term; an absent side reads as empty (source, get_file_contents). The command then searches only the adds(): the contents each side wants, never the base it diverged from, and never the marker text written to the working copy. With -n, numbering restarts on each side, because there is no line numbering shared across sides (source).

Invariants: output follows tree order: depth-first, name order, and within a file, line order (sides in merge order for a conflict). Each matching line is printed once per side it appears on; with --name-only each path at most once. Literal paths that name nothing get one warning afterwards (explicit_paths). An entry that matches the filesets but no lines produces no output.

A pattern that matches nothing prints nothing and exits 0; there is no "no matches" exit status as in grep.

8. Example output

From upstream's test_file_search. @- adds file1 (-foo-) and file2 (-bar-); @ adds dir/file3 (-foobar-): 

$ jj file search --pattern 'glob:*foo*'
dir/file3:-foobar-
file1:-foo-

$ jj file search --pattern 'glob:foo'      # a glob must match the whole line

$ jj file search --pattern 'glob:*foo*' -r @-
file1:-foo-

$ jj file search --pattern 'glob:*foo*' file9
Warning: No matching entries for paths: file9

$ jj file search --pattern foo:bar
Error: Invalid string pattern kind `foo:`

Every matching line, with line numbers, or only the path:

$ printf 'hit-one\nmiss\nhit-two\nhit-three\n' > multi
$ jj file search -n --pattern hit multi
multi:1:hit-one
multi:3:hit-two
multi:4:hit-three

$ jj file search --name-only --pattern hit multi
multi

From test_file_search_conflicts: file1 conflicts with add sides -foo- and -baz- and base -bar-. Each side is searched on its own, so both report line 1. The base and the conflict markers are never matched: 

$ jj file search -n --pattern 'regex:-(foo|baz)-'
file1:1:-foo-
file1:1:-baz-

$ jj file search --pattern 'glob:*bar*'

$ jj file search --pattern 'glob:*%%%*'
