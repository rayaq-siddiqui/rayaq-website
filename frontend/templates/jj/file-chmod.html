How jj file chmod works

jj file chmod sets or clears the executable bit that jj records for files in a commit. It changes the stored bit directly, so it works on any mutable revision, on Windows, and on conflicted files.

In short: jj resolves -r (default @) and refuses it if immutable. For every file entry matching the paths, it sets executable on every term of the value: the one file of a resolved path, or every side and base of a conflict. Symlinks, directories and submodules are rejected. It rewrites the commit with the new tree, tx.finish rebases descendants, and the operation is make paths executable in commit <id> or make paths non-executable ….

The command is cmd_file_chmod. Its help text contrasts it with POSIX chmod: this one works on Windows, on conflicts, and on any revision (source). On disk, the bit only matters once the commit is checked out; see configuration.

2. Configuration

The command itself reads no keys besides revset-aliases."immutable_heads()", which decides whether the commit may be rewritten. working-copy.exec-bit-change (respect, ignore or auto, the default) decides what happens on disk. With ignore, jj neither reads nor sets the executable permission in the working copy, so jj file chmod is the way to change the recorded bit. Windows always behaves that way (docs). Upstream's tests for these settings are test_chmod_exec_bit_settings and the two that follow.

5. Transaction and operation

  • Transaction: one, started after the commit is checked and the paths are parsed (source).
  • Operation description: make paths executable in commit <full hex id> or make paths non-executable in commit <full hex id> (source).
  • Commits rewritten: the target, then its descendants in tx.finish (source).
  • No unchanged check: unlike diffedit or restore, the command doesn't compare trees before rewriting. Whether anything is recorded is left to tx.finish, which only skips when the repo has no changes at all (source).
  • An error aborts everything: the first bad path returns an error before the tree is written, so no other path changes either (source).
  • jj undo restores the previous view.

6. Algorithm and invariants

tree.entries_matching(matcher) yields every path in the commit's tree that the filesets match, each with its MergedTreeValue, a Merge of optional tree values (source). For each one:

  1. It checks that every side (each add term) that is present is a TreeValue::File. Absent sides, as in a modify/delete conflict, are skipped. If a side is something else, the error says Found neither a file nor a conflict for a resolved value and Some of the sides of the conflict are not files for a conflict (source).
  2. It then walks every present term, bases included, and sets executable to the requested value (source). Because every term gets the same value, the executable bit resolves to that value whatever the conflict's shape. Since only adds are checked, a base that isn't a file is left as it is; upstream has a TODO for a test of exactly that case (source).
  3. It stores the value back with set_or_remove (source).

Invariants: file contents and copy IDs never change, only the bit. A conflict stays a conflict with the same terms. Paths outside the filesets are untouched. Either every matched path changes or none does.

The merge conflict then has a 2-sided conflict whose terms disagree on the bit: x's side is executable, while the base and n's side are not.
