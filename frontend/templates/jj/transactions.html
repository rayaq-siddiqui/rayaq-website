Repos, transactions and rewriting

Everything a command changes goes through three types: an immutable ReadonlyRepo at one operation, a MutableRepo that collects changes on top of it, and the Transaction that turns those changes into a new operation. This page covers those types and the rewrite machinery that keeps descendants, bookmarks and working copies following a commit when it's rewritten.

In short: rewriting a commit never edits it. It writes a new commit and records "old → new" in the MutableRepo's parent_mapping. Later, rebase_descendants uses that mapping to rebase every descendant, move bookmarks, and repoint working copies. That's why most commands only touch the commits they care about and never have to think about descendants.

2. Transaction lifecycle

  1. ReadonlyRepo::start_transaction builds a MutableRepo from a mutable copy of the index and a clone of the view.
  2. The command makes changes. has_changes() is true once anything is recorded in commit_predecessors or parent_mapping, or the view differs from the base. If it's false, the CLI records no operation at all.
  3. The CLI calls rebase_descendants before writing (§4).
  4. Transaction::write calls MutableRepo::consume, which normalizes the view's heads and hands back the index, the view and the predecessor map. It then writes the view, the operation and the index, producing an UnpublishedOperation.
  5. publish() moves the op heads to it. See The operation log.

new_parents(old_ids) follows the mapping transitively, so if A became B and B was abandoned onto P, A's children end up on P. This is separate from commit_predecessors, which is never cleared and becomes the operation's record of what was rewritten from what. parent_mapping is consumed and cleared by rebase_descendants.

4. Rebasing descendants

rebase_descendants_with_options(immutable, options, progress) takes every key of parent_mapping as a root and calls transform_descendants_with_options with a callback that rebases any commit whose parents changed:

  1. find_descendants_for_rebase collects the roots' descendants, skipping ones already rewritten and anything in immutable. The CLI passes commits that were already immutable, so a jj git fetch that updates immutable history never rebases it.
  2. transform_commits visits them parents-first. For each one it computes new_parents(old parents) and hands a CommitRewriter to the callback.
  3. After the walk, update_rewritten_references moves bookmarks, updates working-copy commits per the table in §3, and fixes up the heads.
  4. parent_mapping is cleared.

transform_descendants is the same walk with a caller-supplied callback, used directly by commands such as jj fix. The callback can rebase, reparent() (new parents, same tree), abandon, or leave the commit alone. The set of commits to visit is fixed at the start.

How a single commit is rebased

CommitRewriter::rebase_with_empty_behavior computes the new tree as a three-way merge. If the new parents' trees equal the old ones, it keeps the old tree and skips the merge. Otherwise: 

new_tree = merge(
    new_base,   // merge of the new parents' trees  — "(rebase destination)"
  − old_base,   // merge of the old parents' trees  — "(parents of rebased revision)"
  + old_tree    // the commit's own tree            — "(rebased revision)"
)

That's "apply this commit's diff onto its new parents", expressed as a Merge. If the sides disagree, the result is a conflicted tree, stored as a conflict rather than stopping the rebase. The labels in quotes become the conflict marker labels. See conflict_label.
