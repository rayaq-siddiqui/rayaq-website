How jj workspace add works

jj workspace add creates another working copy of the same repo in a new directory. The new workspace gets its own .jj that points back at the existing repo, its own sparse patterns, and its own working-copy commit, by default on the closest immutable ancestors of the current one.

In short: jj picks a name (the destination's basename unless --name), refuses a name already in use or a non-empty directory, and creates the directory. In a colocated repo it may first add a Git worktree there. It writes .jj/repo as a pointer to the existing repo, records the workspace (operation add workspace '<name>', on the root commit), copies the sparse patterns, and then creates the real working-copy commit on the chosen parents: -r, or else the revsets.workspace-add revset, heads(::@ & immutable()) by default (operation create initial working-copy commit in workspace <name>).

The command is cmd_workspace_add. Its counterparts are jj workspace forget and jj workspace remove. How a workspace's working copy is tracked is on the working copy page.

2. Configuration

Without -r, the parents come from revsets.workspace-add, default heads(::@ & immutable()), evaluated in the current workspace (default, source). So the two workspaces share no mutable commits, which the help text says reduces the risk of one going stale or of divergence when commits are rewritten from the other (source). When the result differs from the current working copy's parents, jj says so: Created working copy on top of `revsets.workspace-add` instead of the current working copy's parents. with the hint Use `-r @-` to create it on top of the current working copy's parents instead. A source TODO drops that message in jj 0.54 (source).

Without --colocate or --no-colocate, a Git worktree is created only when the current workspace is colocated and git.colocate is true (its default) (source). -m descriptions get the usual configured trailers added (source). The new workspace doesn't get settings of its own: jj uses the current workspace's settings to create it (source).

3. End-to-end flow

4. Core architecture touchpoints

  • Workspace layout: the new .jj has a repo file holding a path (relative if possible) to the existing .jj/repo directory, and its own working_copy directory (source). That file is how jj tells a secondary workspace from the main one.
  • Workspace store: .jj/repo/workspace_store/index maps names to paths relative to the repo, written under a lock (add). Other commands use it to find a workspace's directory, for example jj workspace root --name and jj workspace remove.
  • View: each workspace has an entry in the view's wc_commit_ids, which is what makes it exist in the repo; see the view page.
  • Git: with colocation, git worktree add --orphan runs first, so the new directory also works with plain git (create_worktree); .jj/.gitignore keeps Git from seeing jj's files (maybe_add_gitignore).

5. Transaction and operation

  • Two operations: add workspace '<name>', which checks out a new commit on the root (init_working_copy), then create initial working-copy commit in workspace <name>, which replaces it with the real one (source). The first, now-empty commit is abandoned by edit, so it doesn't show up (see the two operations in a test's op log).
  • Attribution: both operations are recorded as performed in the workspace the command was run in, not the new one (source, source). So jj undo there undoes them, instead of refusing an operation from another workspace (source).
  • Sparse patterns are written to the new working copy's state without an operation (source).

6. Algorithm and invariants

The new commit's tree is the merge of its parents' trees, so it starts with no changes of its own (source). A description is set only if -m is given; trailers are added only then, because a commit without a description is treated as discardable once it's no longer a working copy, and a trailer-only description would break that (source).

Invariants: names are unique and non-empty; jj never writes into a non-empty directory; the current workspace is unchanged.

8. Worked example

From upstream's test_workspaces_add_second_and_third_workspace. After jj commit -m initial in workspace default, initial is still mutable, so the closest immutable ancestor of @ is the root. jj workspace add --name second ../secondary puts the new working copy there, not next to default@, and says so: 

Created workspace in "../secondary"
Created working copy on top of `revsets.workspace-add` instead of the current working copy's parents.
Hint: Use `-r @-` to create it on top of the current working copy's parents instead.
Working copy  (@) now at: rzvqmyuk 42960ba4 (empty) (no description set)
Parent commit (@-)      : zzzzzzzz 00000000 (empty) (no description set)

Both workspaces then show in the log and in jj workspace list (source):

@  504e3d8c1bcd default@
○  7b22a8cbe888 "initial"
│ ○  42960ba4ec00 second@
├─╯
◆  000000000000

default (current): . rlvkpnrz 504e3d8c (empty) (no description set)
second: ../secondary rzvqmyuk 42960ba4 (empty) (no description set)

When initial is immutable (a test makes immutable_heads() its bookmark), the default revset gives the same parent as -r @-, so no message is printed and the new working copy sits on initial (source).
