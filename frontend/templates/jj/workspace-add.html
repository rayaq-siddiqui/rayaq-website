How jj workspace add works

jj workspace add creates another working copy of the same repo in a new directory. The new workspace gets its own .jj that points back at the existing repo, its own sparse patterns, and its own working-copy commit, by default on the same parents as the current one.

In short: jj picks a name (the destination's basename unless --name), refuses a name already in use or a non-empty directory, and creates the directory. In a colocated repo it may first add a Git worktree there. It writes .jj/repo as a pointer to the existing repo, records the workspace (operation add workspace '<name>', on the root commit), copies the sparse patterns, and then creates the real working-copy commit on the chosen parents (operation create initial working-copy commit in workspace <name>).

The command is cmd_workspace_add. Its counterparts are jj workspace forget and jj workspace remove. How a workspace's working copy is tracked is on the working copy page.

2. Configuration

Without --colocate or --no-colocate, a Git worktree is created only when the current workspace is colocated and git.colocate is true (its default) (source). -m descriptions get the usual configured trailers added (source). The new workspace doesn't get settings of its own: jj uses the current workspace's settings to create it (source).

3. End-to-end flow

4. Core architecture touchpoints

  • Workspace layout: the new .jj has a repo file holding a path (relative if possible) to the existing .jj/repo directory, and its own working_copy directory (source). That file is how jj tells a secondary workspace from the main one.
  • Workspace store: .jj/repo/workspace_store/index maps names to paths relative to the repo, written under a lock (add). Other commands use it to find a workspace's directory, for example jj workspace root --name and jj workspace remove.
  • View: each workspace has an entry in the view's wc_commit_ids, which is what makes it exist in the repo; see the view page.
  • Git: with colocation, git worktree add --orphan runs first, so the new directory also works with plain git (create_worktree); .jj/.gitignore keeps Git from seeing jj's files (maybe_add_gitignore).

5. Transaction and operation

  • Two operations: add workspace '<name>', which checks out a new commit on the root (init_working_copy), then create initial working-copy commit in workspace <name>, which replaces it with the real one (source). The first, now-empty commit is abandoned by edit, so it doesn't show up (see the two operations in a test's op log).
  • Sparse patterns are written to the new working copy's state without an operation (source).

6. Algorithm and invariants

The new commit's tree is the merge of its parents' trees, so it starts with no changes of its own (source). A description is set only if -m is given; trailers are added only then, because a commit without a description is treated as discardable once it's no longer a working copy, and a trailer-only description would break that (source).

Invariants: names are unique and non-empty; jj never writes into a non-empty directory; the current workspace is unchanged.
