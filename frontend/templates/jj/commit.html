How jj commit works

jj commit finishes the working-copy commit: it gives @ a description, optionally keeps only some of its changes there, and starts a fresh working-copy commit on top that holds everything else.

In short: with no paths and no -i, jj commit is jj describe followed by jj new, in one operation. It rewrites @ (same change ID) with the chosen description and the selected tree. Then it creates a new, undescribed commit on top whose tree is the full, original working-copy tree, and moves every workspace that was on the old @ there. So the files on disk never change: unselected changes simply show up as the new @'s diff. The operation is commit <old @ id>.

The command is cmd_commit. It shares its description handling with jj describe, its final step with jj new and jj edit (MutableRepo::edit), and its change selection with jj split. Its own help text lists how it differs from split (source): it isn't interactive by default, has no -r, doesn't move bookmarks forward, and can't send the selection elsewhere. The default alias ci comes from misc.toml.

5. Transaction and operation

  • Transaction: one, always. Even jj commit -m "" on an empty @ records an operation, because a new commit is created (source).
  • Operation description: commit <id>, the full hex ID of the working-copy commit before the command (source).
  • Commits created or rewritten: the old @ is rewritten, and one new commit is created. If the old @ had descendants, which is possible but unusual, finish rebases them onto the committed commit. With a partial selection, that commit lacks the unselected changes, so the rebase may conflict.
  • Working copy: snapshotted first, so everything you've edited is included. After the operation, the new @ is checked out. Its tree equals the snapshot, so nothing on disk changes.
  • jj undo restores the previous view: the old @ comes back as @ with its old description and all its changes, and the two new commits are hidden.

6. Algorithm and invariants

Choosing what to commit

DiffSelector::select works on two trees: before is @'s parent tree, and after is @'s tree. It first runs restore_tree, which starts from before and copies in every path the matcher accepts from after. With no paths, the result is simply @'s tree. Non-interactive selection stops there. Interactive selection then opens the diff editor on before → that result, with the instruction text. The tree you leave on the right side is what gets committed. If there's nothing to choose from, it prints Empty diff - won't run diff editor. and skips the editor.

Building the description

  1. Start from the -m paragraphs, or from @'s current description (source).
  2. Add trailers through add_trailers, unless the description is empty and no editor will open. That would give the commit a description made only of trailers (source).
  3. If the editor is used, write a hidden temporary commit with the selected tree and the draft text, render templates.draft_commit_description for it, and edit it with edit_description. If the result is empty, jj hints that you can jj undo, or describe the parent with jj desc @- (source). The commit still goes ahead.

Rewriting and moving on

rewrite_commit(@).detach() takes the commit's fields and sets the selected tree and the description. It is then written with write, which records the old @ as rewritten (source, write). Then, for the workspaces whose @ was the old commit, jj:

  1. creates one new commit whose parent is the committed commit and whose tree is the old @'s full tree (commit.tree(), not the selection);
  2. advances eligible bookmarks to the committed commit (a no-op unless the experimental setting is on);
  3. calls MutableRepo::edit for each of those workspaces, pointing them all at that new commit (source).

Because the new @'s tree is the snapshotted tree, the diff between the committed commit and the new @ is exactly the unselected changes.

Invariants: the working-copy files are never modified; the committed commit keeps @'s change ID, so it is the "same change" you were working on; the new @ is always a new change; and every workspace that shared the old @ ends up on the same new @.

cmd_commit makes no check_rewritable call of its own, unlike describe. A @ that is a merge stays a merge: the committed commit keeps all its parents, and the new @ has the committed commit as its only parent.
