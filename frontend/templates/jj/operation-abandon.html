How jj operation abandon works

jj op abandon removes operations from the operation log's history. Unlike every other command, it doesn't add an operation: it rewrites the operations that come after the abandoned range so their parent skips over it, then repoints the op heads and the working copy at the rewritten ones.

In short: jj loads the workspace without loading the repo, so it works even when the repo state is broken, and refuses --at-op. It reads the current op heads and resolves the argument: a range A..B, or a single operation, meaning just that one. It refuses to abandon a current head. It copies every operation from B up to the current heads with new parents that skip the range, counts what became unreachable, replaces each op head with its copy, and moves the working copy's operation ID along. The views are untouched, so the repo looks exactly the same.

The command is cmd_op_abandon. Its help gives the two typical uses: jj op abandon ..<id> to discard old history, and jj op restore <id> then jj op abandon <id>..@- to discard recent operations. Old commit versions that only the abandoned operations referred to become eligible for jj util gc (source). How operations and op heads are stored is on the operations page.

5. Transaction and operation

  • No transaction and no new operation. The command writes rewritten copies of existing operations directly to the store (source).
  • Operation IDs change. Operation IDs are content hashes, and a copy has different parents, so every operation after the range gets a new ID, including the current one. Old IDs you noted down no longer resolve to the live history.
  • The repo isn't loaded, by design, "so that this command can be used to recover from corrupted repo state" (source).
  • Not undoable with jj undo: there is no operation to undo. The abandoned operations remain in the store until garbage collection.

6. Algorithm and invariants

With root and heads from the argument, reparent_range is called with the abandoned heads as its roots, the current heads as its heads, and root as the destination (source):

  1. Collect the operations in heads..current_heads; those are the ones to copy (source).
  2. Count root..heads: the operations about to become unreachable (source).
  3. Walk the copies oldest first. Each parent that was already copied is replaced by its copy; the first parent that wasn't, which is in the abandoned range, is replaced by root (at most once per operation). Write the copy and remember its ID (source).
  4. Map each current head to its copy (source).

If every head maps to itself, nothing was in the range: Nothing changed.. Otherwise the op heads are swapped. If the working copy's operation is one of the old heads, it is moved to the copy; if it isn't, for instance after divergent operations, jj warns and leaves it, and you'll need to "re-abandon their ancestors" (source).

Invariants: the current heads' views are unchanged, so every command sees the same repo before and after. The current operation can't be abandoned, nor can the root operation or a merge operation on their own. Each current head gets exactly one copy (asserted).
