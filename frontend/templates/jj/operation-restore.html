How jj operation restore works

jj op restore X writes a new operation whose view is operation X's view, so the repo looks the way it did at X. Nothing in the operation log is removed: the later operations stay there, and the restore itself can be undone.

In short: jj loads the workspace as usual and resolves X. It builds a new View from X's view and the current one: heads, local bookmarks and tags, and working-copy commits come from X; remote bookmarks and tags come from X too unless --what leaves them out; the Git ref mirrors stay current. It installs that view in one transaction, prints Restored to operation: …, and finishes as restore to operation <id>, which checks out the restored @.

The command is cmd_op_restore. It shares its view logic with jj undo and jj op revert. The operation log itself is described on the operations page.

5. Transaction and operation

  • Transaction: one (source).
  • Operation description: restore to operation <full hex id of X> (source).
  • No change: restoring to the current operation prints the summary and then Nothing changed.; nothing is recorded (test).
  • Undoing it: jj undo, or jj op restore to the operation before the restore.
  • Before it: the load's snapshot may record a snapshot working copy operation, so unrecorded edits are kept in the log even though the restore moves away from them.

6. Algorithm and invariants

view_with_desired_portions_restored picks each field of the new View:

FieldTaken from
head_ids, local_bookmarks, local_tags, wc_commit_idsX if --what includes repo, else current
remote_views (remote bookmarks and tags)X if --what includes remote-tracking, else current
git_refs, git_headsalways current

The remote-tracking help notes not to restore those "if you'd like to push after the undo" (source): restoring them makes jj forget what a push or fetch told it about the remote. The view is installed as-is with set_view, which marks the heads as not yet normalized (source).

Invariants: append-only: no operation or commit is deleted. Only the view changes. The Git ref mirrors are never rolled back, so the next import or export still compares against what Git actually has.

8. Worked example

From upstream's test_git_push_revert, which uses jj op restore to take back a push. main was pushed at AA, then described BB and pushed again; the test restores to the operation before that second push:

Upstream's bookmark listing after the restore (source):

main: qpvuntsm d9a9f6a0 (empty) BB
  @origin (ahead by 1 commits, behind by 1 commits): qpvuntsm/1 3a44d6c5 (hidden) (empty) AA

A later jj git fetch, after describing main as CC, ends with main conflicted. The test's own TODO explains why: the restore made jj forget the remote was already at BB, so the fetch looked like a remote update. --what repo avoids that by keeping the current remote-tracking bookmarks (test_git_push_revert_repo_only).
