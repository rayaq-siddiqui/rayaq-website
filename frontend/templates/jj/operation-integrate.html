How jj operation integrate works

jj op integrate X makes an operation that exists in the store, but isn't reachable from the op heads, part of the operation log again. It adds X as an op head and lets jj's usual concurrent-operation handling merge it with whatever else is there.

In short: jj loads the workspace without snapshotting and resolves X. It calls update_op_heads(parents of X → X), so X becomes a head next to the current one. Then resolve_op_heads runs: if X turns out to be an ancestor of another head, it is simply dropped again and nothing happens. Otherwise the heads are merged into a new operation, reconcile divergent operations, and jj prints The specified operation has been integrated with other existing operations.

The command is cmd_op_integrate. Its help explains when that's needed: operations are integrated automatically, but --no-integrate-operation or an internal error can leave one out (source). jj points you here itself when the working copy's operation turns out to be a sibling of the loaded one. Op heads and the merge of concurrent operations are described on the operations page.

5. Transaction and operation

  • No transaction of the command's own. The only operation written is the merge, created inside resolve_op_heads by RepoLoader::merge_operations (source).
  • Operation description: reconcile divergent operations, recorded with this workspace's name and the command's arguments (source).
  • Already integrated: nothing is written and nothing printed (test).
  • Undoing it: jj undo refuses a merge operation; jj op restore to one of the merged operations works.

6. Algorithm and invariants

  1. update_op_heads(old, new) removes the old heads and adds the new one. Passing X's parents as "old" means that if a parent was a head, X replaces it, and otherwise X is simply added next to the existing heads (source).
  2. resolve_op_heads reads the heads. With several, it locks, re-reads, and drops heads that are ancestors of other heads. One left: it's used as is, and the dropped ones are removed from the op heads. Still several: they're sorted by end time and handed to the resolver.
  3. The resolver calls merge_operations, which merges the repos at those operations, using their closest common ancestors as bases, and writes the result as one operation. The op heads are then replaced by it.

Invariants: nothing is removed from the operation store. Integrating twice is harmless. After the command there is exactly one op head, unless another process raced it.

8. Worked example

From upstream's test_integrate_sibling_operation. The test runs jj new -m=first, then removes that operation from the op heads by hand, and runs jj new -m=second --ignore-working-copy, which builds on the older operation. The working copy still records the first one, so jj op log fails with the sibling error and its hint. Running jj op integrate 4bffc36765bd fixes it:
