How jj resolve works

jj resolve hands each conflicted file in a commit to a 3-way merge tool, one file at a time, and writes the tool's output back as the file's new content. With --list it only lists the conflicts.

In short: jj resolves -r (default @) and finds the conflicted paths that match the arguments. With none, it fails with No conflicts found. With --list, it prints them and stops. Otherwise it refuses an immutable commit, checks that every chosen conflict is a 2-sided conflict between regular files, and runs the merge tool on them in order. The first failure stops it. jj rewrites the commit with the files resolved so far, even if a later one failed, then reports that error. Descendants are rebased by tx.finish. The operation is Resolve conflicts in commit <id>.

The command is cmd_resolve. Its help text notes that you can also resolve conflicts by editing the conflict markers in the file directly (source). How conflicts are stored is explained on the conflicts page; this page covers only the command and the merge tools.

5. Transaction and operation

  • Transaction: one, after the conflict list and before the tool runs. --list, and errors before any file is resolved, record nothing (source).
  • Operation description: Resolve conflicts in commit <full hex id before the rewrite>. It is capitalized, unlike most of jj's (source).
  • Partial resolution: if an external tool fails on the second file or later, the files already resolved are still committed and the operation is recorded. Only then does jj resolve exit with Stopped due to error after resolving <n> conflicts (source, return).
  • Descendants: the command doesn't rebase them itself; tx.finish does (source).
  • jj undo restores the previous view, bringing back the conflicted commit.

6. Algorithm and invariants

Finding and checking conflicts

tree.conflicts_matching(&matcher) lists the conflicted paths under the arguments (source). Before any tool runs, MergeToolFile::from_tree_and_path checks every one of them, and any failure stops the whole command:

  1. The value must actually be a conflict, and present.
  2. Every term must be a regular file or absent. Symlinks, directories and submodules can't be resolved here.
  3. After simplifying, the conflict must have at most 2 sides. Simplifying removes terms that cancel out, so a conflict that only looks larger can still qualify (try_materialize_file_conflict_value).
  4. The executable bit must resolve on its own. If it conflicts, the hint points to jj file chmod.

An external tool

run_mergetool_external prints Resolving conflicts in: <path> and calls run_mergetool_external_single_file for each file in turn:

  1. It writes base_<name>, left_<name>, right_<name> and output_<name> into a jj-resolve- temp directory. Left is side 1, right is side 2. All but output are read-only (source).
  2. output starts empty, or with conflict markers if the tool edits markers. The marker length is the minimum unless the tool sees markers or asks for $marker_length; then it is long enough not to clash with the file's content (source).
  3. It runs the tool. A non-zero exit is a failure unless the code is listed in merge-conflict-exit-codes (source).
  4. An empty or unchanged output is a failure. That's how you stop: quit the tool without saving (source).
  5. If the tool edits markers, or exited with a conflict code, jj parses output for markers and may keep a smaller conflict. Otherwise output becomes the file. A conflict exit code with no markers is reported as invalid (source).
  6. A resolved file keeps the resolved executable bit. A still-conflicted one keeps its executable bits and gets new file IDs (source).

The built-in tools

:builtin opens one terminal UI over all the conflicted files, where you choose which side's changes to keep. :ours and :theirs need no UI: pick_conflict_side sets every file to side 1 or side 2 of its simplified conflict. A side where the file is absent deletes it (edit_files).

Invariants: only conflicted paths are touched, and only the target commit's tree changes. Files are handled in the order the tree lists them, and a failure on the first one records nothing. 3-sided and larger conflicts are never sent to a tool; edit their markers by hand.

8. Worked example

From upstream's test_resolution. base has file = base; a and b change it to a and b; conflict merges them. jj resolve --list prints file 2-sided conflict. With a merge tool that writes resolution into $output:

Upstream's snapshot (source):

Resolving conflicts in: file
Working copy  (@) now at: vruxwmqv 741263c9 conflict | conflict
Parent commit (@-)      : zsuskuln 45537d53 a | a
Parent commit (@-)      : royxmykx 89d1b299 b | b
Added 0 files, modified 1 files, removed 0 files

The tool saw an empty output file, as the test checks by dumping it. jj diff then shows the conflict markers replaced by resolution, and jj resolve --list fails with No conflicts found at this revision.

Upstream's test_multiple_conflicts_with_error shows a partial run. The tool resolves file1, then quits on file2 without writing. jj still rewrites the commit, so file1 is resolved, warns that file2 is still conflicted, and then exits with: 

Error: Stopped due to error after resolving 1 conflicts
Caused by: The output file is either unchanged or empty after the editor quit (run with --debug to see the exact invocation).
