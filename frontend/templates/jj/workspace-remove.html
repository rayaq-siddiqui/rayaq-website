How jj workspace remove works

jj workspace remove does what jj workspace forget does and then deletes the workspace's directory. Before deleting anything it snapshots the workspace, so tracked changes that were never committed survive as a commit. It refuses the workspace that holds the repository.

In short: jj requires a writable working copy, skips unknown names with a warning, and for each workspace looks up its directory in the workspace store. It refuses if the directory contains the repo, or now belongs to another repo. It snapshots each workspace in turn, then removes them from the view in one transaction (remove workspace <name>), deletes their store entries, unlinks Git worktrees, and finally deletes each directory.

The command is cmd_workspace_remove. To stop tracking a workspace without touching the disk, use jj workspace forget, which every error here suggests.

2. Configuration

None specific. Snapshotting follows the usual snapshot settings (such as snapshot.auto-track), and the Git worktree step uses git.executable-path.

3. End-to-end flow

4. Core architecture touchpoints

  • Workspace store: the source of each workspace's directory, and the entries are removed afterwards (forget, get_workspace_path).
  • Working copy: each workspace is loaded from its own directory and snapshotted like any command would; see the working copy page.
  • View: remove_workspace, which may abandon an empty working-copy commit, exactly as for forget.
  • Git: worktree unlinking, as for forget (unlink_git_worktree).

5. Transaction and operation

  • Snapshots: one snapshot working copy operation per workspace that had changes, chained so each builds on the last (source).
  • Removal: one transaction, remove workspace <name> or remove workspaces <a>, <b> (source).
  • Outside the operation: the store entries, Git worktrees and directories. jj undo brings the workspace back in the view, but its files are gone.

6. Algorithm and invariants

The "contains the repository" check is why the main workspace (whose .jj/repo is the real repo directory) can't be removed; the source deliberately doesn't suggest forget there either (source). The "another repository" check protects a directory that was replaced by an unrelated repo after the workspace was added (test).

Untracked and ignored files are lost. The snapshot only saves what jj tracks; anything else in the directory is deleted with it (source).

Invariants: the repo is never deleted; every removed workspace's tracked changes are in a commit first; the view, store and disk agree that the workspace is gone, unless a directory deletion fails, which is only a warning.

8. Worked example

From upstream's test_workspaces_remove_snapshots_before_removal. A workspace secondary is added after initial, then a file is written there without running any jj command in it. jj workspace remove secondary from the main workspace: 

Removed workspace directory "$TEST_ENV/secondary".

The file is now in a commit (source):

$ jj log -r 'files("unsnapshotted.txt")' --summary

~  A unsnapshotted.txt
