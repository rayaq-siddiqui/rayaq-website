How jj workspace remove works

jj workspace remove does what jj workspace forget does and then deletes the workspace's directory. Before deleting anything it snapshots the workspace into a new commit, so changes that were never committed survive. It refuses the workspace that holds the repository, and a workspace with files the snapshot would leave untracked.

In short: jj requires a writable working copy, skips unknown names with a warning, and for each workspace looks up its directory in the workspace store. It refuses if the directory contains the repo, or now belongs to another repo. It snapshots each workspace at the operation its working copy last recorded, so a stale workspace works too, and fails if any file would stay untracked. Changes go into a new commit on top of the working-copy commit. One transaction (remove workspace <name>) adds those commits and removes the workspaces from the view. Then it deletes their store entries, unlinks Git worktrees, and finally deletes each directory.

The command is cmd_workspace_remove. To stop tracking a workspace without touching the disk, use jj workspace forget, which every error here suggests.

2. Configuration

None specific. Snapshotting uses the removed workspace's snapshot.auto-track and snapshot.max-new-file-size; a new file outside the first or over the second makes the command fail rather than be lost (source). The Git worktree step uses git.executable-path.

3. End-to-end flow

4. Core architecture touchpoints

  • Workspace store: the source of each workspace's directory, and the entries are removed afterwards (forget, get_workspace_path).
  • Working copy: each workspace is loaded from its own directory, with its own environment, and snapshotted against the repo at the operation its working copy last recorded. A stale workspace can therefore be removed; its snapshot builds on the old working-copy commit (snapshot_workspace, test). See the working copy page.
  • View: remove_workspace, which may abandon an empty working-copy commit, exactly as for forget.
  • Git: worktree unlinking, as for forget (unlink_git_worktree).

5. Transaction and operation

  • Snapshots: no operation of their own. A workspace with changes gets a new commit, a child of its working-copy commit described SNAPSHOT OF REMOVED WORKSPACE `<name>`, written hidden from a transaction that is never finished. The working-copy commit isn't rewritten, so nothing is rebased and immutability isn't checked (source).
  • Removal: one transaction adds each snapshot commit as a head and removes the workspaces: remove workspace <name> or remove workspaces <a>, <b> (source).
  • Outside the operation: the store entries, Git worktrees and directories. jj undo brings the workspace back in the view, but its files are gone.

6. Algorithm and invariants

The "contains the repository" check is why the main workspace (whose .jj/repo is the real repo directory) can't be removed; the source deliberately doesn't suggest forget there either (source). The "another repository" check protects a directory that was replaced by an unrelated repo after the workspace was added (test).

Untracked files stop the command; ignored files are lost. If the snapshot leaves a new file untracked (outside snapshot.auto-track or too large) or skips a path that isn't valid UTF-8, the command fails after the snapshot warnings and the directory stays (source). Ignored files aren't reported, so they are deleted with the directory (source). Snapshots run one workspace at a time before the transaction, so if a later workspace fails, nothing is removed.

Invariants: the repo is never deleted; every removed workspace's changes are in a commit first; the view, store and disk agree that the workspace is gone, unless a directory deletion fails, which is only a warning.

8. Worked example

From upstream's test_workspaces_remove_snapshots_before_removal. A workspace secondary is added after initial, then a 14-byte file is written there without running any jj command in it. With --config=snapshot.max-new-file-size=10, jj workspace remove secondary refuses the file, fails with Cannot remove workspace 'secondary' with unsnapshotted changes, and leaves the directory. Without that option: 

Snapshot commit created for workspace 'secondary': ff0805347b96
Removed workspace directory "$TEST_ENV/secondary".

The file is now in a commit (source):

$ jj log --summary

If the workspace was stale (secondary@ rewritten from the main workspace first), the snapshot still builds on the old working-copy commit, which then shows as divergent with the rewritten one (test).
