How jj duplicate works

jj duplicate copies commits into new changes. Each copy has the same content and, by default, the same description, but a new change ID. Copies go next to the originals, or onto a destination you name with -o, -A or -B.

In short: jj evaluates the revisions (default @), refuses the root commit, and renders each copy's description with templates.duplicate_description. Without a destination, each copy gets the original's parents, with any parent that is also being copied swapped for its copy. Trees are reused unchanged. With a destination, the roots of the set are rebased onto it, the rest follow, and -A/-B rebase the destination's children onto the copies' heads. The originals are never touched, so even immutable commits can be duplicated. The operation is duplicate <n> commit(s).

The command is cmd_duplicate. The work happens in jj-lib's duplicate_commits_onto_parents and duplicate_commits. The second shares its "connected set, internal parents, heads" logic with jj rebase -r.

5. Transaction and operation

  • Transaction: one, unless nothing matched or the root was named (source).
  • Operation description: duplicate <n> commit(s), with the literal (s). Upstream's undo snapshot shows duplicate 1 commit(s) (source).
  • Commits created or rewritten: one copy per original. With -A/-B, the destination's children and their descendants are rewritten too.
  • Working copy: snapshotted at the start. @ is never moved to a copy, so the files on disk change only if @ was a rebased new child.
  • jj undo hides the copies again and restores any rebased children.

6. Algorithm and invariants

Without a destination

duplicate_commits_onto_parents walks the targets oldest first. Each copy is rewrite_commit(original) with no rewrite source and a new change ID. Its parents are the original's, except that a parent which has already been copied is replaced by its copy. The tree isn't touched, so copying a stack reproduces the stack beside the original, with identical content at every step.

With a destination

duplicate_commits treats the targets as a connected set, like rebase -r:

  1. Compute each target's internal parents, its nearest ancestors within the set across any gaps. Targets with none are the roots (source).
  2. For -A/-B, compute the set's heads (source).
  3. Oldest first, copy each target: roots onto the destination parents, others onto their internal parents' copies. Use CommitRewriter::rebase, so each copy's tree is its own diff re-applied on the new base. Then clear the rewrite source and draw a new change ID (source).
  4. Rebase each new child. Any old parent that was a destination parent is replaced by the copies' heads, and the heads are added if missing (source).

Before any of this, jj warns, without stopping, if a copy would land among the descendants or ancestors of its own original (source).

Invariants: originals and everything referring to them are untouched. Every copy is a new change, so duplication never causes divergence. Copies keep their originals' internal graph shape. Without a destination, content is byte-identical.
