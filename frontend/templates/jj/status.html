How jj status works

jj status (alias st) snapshots the working copy, then reports on it: what changed compared to the parents, which new files were left untracked, which commits @ sits on, and any conflicts in the working copy or in bookmarks.

In short: jj loads the workspace and snapshots it, keeping the snapshot's statistics. If the workspace has a working-copy commit, it prints a summary diff of @ against its merged parents (with renames and copies), the untracked paths that snapshot found, collapsed to directories where it can, and one line each for @ and its parents. If @ is conflicted it lists the conflicted paths and may suggest where to start resolving. Finally it lists conflicted local and remote bookmarks. It writes nothing beyond what the snapshot itself records.

The command is cmd_status. The help text: "Show high-level repo status", covering "the working copy commit and its parents, and a summary of the changes in the working copy (compared to the merged parents)", conflicts in the working copy, and conflicted bookmarks (source). The st alias is a built-in default (source).

5. What it reads, and snapshotting

  • Snapshot: yes, and the statistics matter. status calls workspace_helper_with_stats rather than workspace_helper (source, source), because the "Untracked paths" section is built from SnapshotStats.untracked_paths. That list is not stored anywhere; it exists only for the snapshot just taken (source).
  • Without a snapshot: with --ignore-working-copy, or at an --at-op that is not the head operation, no snapshot runs and the statistics are empty (source, source), so no untracked paths are listed, and the changes shown are those recorded at the last snapshot.
  • Ignored files are not "untracked": a new file matching .gitignore is skipped silently and never appears (source, test).
  • Output: snapshot warnings and the unmatched-paths warning go to stderr. Everything else, including the conflict and bookmark warnings, goes to stdout through the pager. The changes are rendered into a buffer first, so the "Working copy changes:" header is printed only if the filtered diff is not empty (source).

6. Algorithm and invariants

Changes against the merged parents

collect_working_copy_status takes @, its parents, @'s tree and the parents' merged tree (source). For a merge commit the parent tree is the auto-merge of all parents, so a clean merge with no edits on top shows no changes (test). The changes are rendered with the ordinary diff renderer in Summary format, one M/A/D/R/C line per path (source).

Whether anything changed is decided on the whole tree, before the path filter: tracked changes exist when the two trees' ids differ (source), and untracked changes when the snapshot found any untracked path (source). So jj status file_1 prints "The working copy has no changes." only when nothing changed anywhere. If only other files changed it prints neither that line nor a header, just the @/@- lines (test, test).

Collapsing untracked paths

The untracked paths that match the filter are passed, in sorted order, to visit_collapsed_untracked_files together with @'s tree. For each path it walks the parent directories down a stack of tracked subtrees. At the first directory with no tracked subtree it prints that directory with a trailing separator and skips every later path under it; if every directory exists in the tracked tree it prints the file itself (source). The stack is reused between consecutive paths, so siblings do not reload the same subtrees (source).

Paths are printed relative to the current directory, so from inside an untracked sub/ the collapsed entry is ./ (test). A file that was untracked with jj file untrack but still exists shows up as D in the changes and again under "Untracked paths" (test); see jj file untrack.

Conflicts and the resolving hint

If @ has a conflict, status warns and prints each conflicted path that matches the filter with its number of sides and anything unusual among them (a deletion, an executable, a symlink, a directory or a submodule), after simplifying the conflict (source, source). It then finds the ancestors of @'s parents that have conflicts, minus the immutable set (source), and passes them to report_repo_conflicts. That prints the hint only if the list is not empty and hints.resolving-conflicts is on; it names the roots of those commits as jj new <change id> lines, so with a chain of conflicted commits it points at the first one (source, test). If @ is the only conflicted commit, as when a merge conflicts in @ itself, no hint is printed.

If @ is not conflicted but a parent is, it prints "Hint: Conflict in parent commit has been resolved in working copy." once (source). jj resolve is the tool the hint suggests.

Conflicted bookmarks

Last, for any workspace state, it reads the view: local bookmarks whose target is not resolved, and remote bookmarks (name@remote) whose target is not resolved (source). Each group gets a warning, one indented name per line, and a hint: jj bookmark set for local ones, fetching again for remote ones (source). A conflicted bookmark arises from concurrent operations, as in the test; see how the view merges refs.

Invariants: status never rewrites a commit or records an operation of its own; any operation comes from the snapshot. The path filter never hides the @/@- lines or the bookmark warnings, and never changes whether "no changes" is printed.

8. Example output

From upstream's test_status_copies: @ modifies copy-source, adds copy-target as a copy of it, and renames rename-source. Copy records turn the add and the delete into C and R: 

$ jj status

M copy-source
C {copy-source => copy-target}
R {rename-source => rename-target}
Working copy  (@) : rlvkpnrz c2fce842 (no description set)
Parent commit (@-): qpvuntsm ebf799bc (no description set)
