How jj evolog works

jj evolog shows the earlier commits a change has pointed to: every snapshot, describe, rebase or squash that replaced its commit. It reconstructs that history by walking the operation log, not the commit graph.

In short: jj snapshots the working copy, resolves -r (default @) to commit IDs, and walks the operation log backwards from the current operation. Each operation records which commits it created or rewrote and from what. Whenever an operation has a record for a commit the walk is following, that commit is printed with the operation, and the walk follows its predecessors instead. It stops when nothing is left to follow, when the operation log runs out, or at an operation written by jj < 0.30, which recorded no predecessors. Entries are drawn as a graph (or a flat list), optionally with a diff against the previous version. No operation is recorded, apart from a snapshot's.

The command is cmd_evolog. The help text: "Show how a change has evolved over time … Lists the previous commits which a change has pointed to. The current commit of a change evolves when the change is updated, rebased, etc." (source). The walk itself lives in jj-lib, in walk_predecessors.

5. What it reads, and snapshotting

  • Snapshot: yes, through workspace_helper (source). With --ignore-working-copy, edits since the last snapshot are not in the history yet.
  • Where the history comes from: each transaction writes the map of commits it created or rewrote to their predecessors into its operation (source). Rewrites fill it through set_predecessors; a CommitBuilder made for a rewrite starts with the old commit as its predecessor (source, source, source). A new commit maps to an empty list.
  • What the map leaves out: "Existing commits (including some commits imported from Git) aren't tracked even if they became visible at this operation" (source). The map is kept even when a commit is rewritten several times in one transaction, as {Y: [X], Z: [Y]}.
  • Output: everything goes to stdout through the pager. No transaction is started, so no operation is recorded beyond the snapshot's.

6. Algorithm and invariants

Walking the operation log

The walk keeps a list of commit IDs still to visit, starting with the -r commits, and a queue of entries ready to yield (source). While the list is not empty and the queue is, it takes the next operation (source):

  • For every listed ID that this operation has a record for, visit_op replaces the ID by its predecessors and marks it to be emitted. A newly created commit is replaced by nothing, so its line of history ends there. IDs without a record stay for older operations (source).
  • Each marked commit is queued with this operation. If one operation marked several, they are sorted newest first through the operation's own map, so {Y: [X], Z: [Y]} gives Z then Y; an ID reached twice in one operation is emitted once (source).
  • When the operation log runs out, or reaches an operation that "was written by jj < 0.30" and so has no map, every remaining ID is queued with no operation and the walk ends. Concurrent branches of the operation log beyond that point are not looked at: "Operation history should be mostly linear" (source, source).

Graph and list ordering

In graph mode each entry gets a direct edge to each of its predecessor IDs (source), and the stream goes through TopoGroupedGraph, as in jj log. Upstream's comment gives the reason: the first predecessor is usually the previous version of the change and the others were squashed into it, and grouping shows "squashed commits in reverse chronological order" and "before the squash destination" (source). The limit is taken from the grouped stream; --reversed then collects it and runs reverse_graph (source). So --limit=3 --reversed shows the three newest entries, oldest first (test).

With --no-graph the walk order is used as is: limit, then reverse the list (source, test). Entries are printed as the walk yields them, so a long history starts printing before the walk reaches the end.

The patch: comparing with the previous version

diff_renderer_for_log returns a renderer only if -p or a diff format flag was given (source). For each entry, show_inter_diff compares its predecessors with its commit (source), the same routine jj interdiff uses:

  • The description is diffed as a pseudo-file, JJ-COMMIT-DESCRIPTION. With several predecessors their descriptions are merged into a conflict, which is why a squash shows conflict markers in that file (source, test).
  • The old tree is rebase_to_dest_parent of the predecessors onto the entry's parents. A single predecessor with the same parents is used as is; otherwise each predecessor's changes are merged onto the new parents' tree (source). A pure rebase therefore shows no diff, even one that produced a conflict; the later version that resolves it shows the resolution (test).
  • An entry with no predecessors (a new commit, or one cut off by the walk) is diffed against its own parents and an empty description.
  • Copy records are not tracked in this diff (source).

The template language has the same comparison as inter_diff() on a CommitEvolutionEntry, next to commit, operation and predecessors (source).

Invariants: the history comes only from the operation log, so it is exactly as long as the operation log that still holds it. Each emitted commit is printed with the operation that created or rewrote it, except entries cut off by the end of the walk, which have no operation. No operation is recorded, apart from a snapshot's.
