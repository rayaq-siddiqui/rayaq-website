How jj squash works

jj squash moves changes out of one or more source commits and into a destination commit. By default that's from @ into its parent. A source left empty is abandoned, and their descriptions are combined.

In short: jj picks the sources and the destination (@ → @-, -r X → X's only parent, or --from/--into), and refuses if any of them is immutable. For each source it selects a diff: all of it, the given paths, or what you pick in a diff editor. jj-lib's squash_commits then removes that diff from each source, abandoning a source whose whole diff was taken. It applies all the selected diffs to the destination as a 3-way merge. The description is your -m, the destination's (-u), or a combination. If more than one involved commit has a description, an editor opens. One operation records it all: squash commits into <destination id>.

The command is cmd_squash. The tree arithmetic lives in jj-lib's rewrite::squash_commits. jj absorb also moves changes into ancestors, but picks the destination per hunk from blame; its page will cover that entry point. Change selection is the same DiffSelector that jj commit uses.

2. Configuration

jj squash has no settings of its own. It reads the same keys as jj commit: ui.editor for descriptions, ui.diff-editor (falling back to :builtin) and ui.diff-instructions for -i, templates.draft_commit_description and templates.commit_trailers, and user.name/user.email for the committer. revset-aliases."immutable_heads()" decides what check_rewritable refuses.

5. Transaction and operation

  • Transaction: one, started after the commits are resolved and checked (source).
  • Operation description (source): squash commits into <destination id> when the destination already exists. In the experimental mode, it is squash commit <id> or squash commit <id> and <n> more, naming the first source by full hex ID. The text is fixed before anything is rewritten.
  • Commits created or rewritten: the destination is rewritten, and partially squashed sources are rewritten. Fully squashed sources are abandoned, and descendants are rebased. In the experimental mode, a new destination commit is created first. Its predecessor record leaves out that intermediate empty commit (source).
  • Working copy: snapshotted at the start. If @ is abandoned, you get a fresh empty @ on its parent, and the files on disk stay the same, since the changes are now in the parent.
  • jj undo restores the previous view: the sources come back unchanged and the destination gets its old tree and description.

6. Algorithm and invariants

Choosing sources and destination

There are two modes (source). With -r, or no revision flags at all, the source is one commit and the destination is its single parent. A merge commit is refused, because it's unclear which parent should receive the changes. With --from/--into, the sources are the union of the --from revsets, minus the destination if it's among them. The order is reversed so that older commits are applied first, which "avoids creating transient conflicts" according to the source comment. The destination can be anywhere: an ancestor, a descendant, or unrelated.

What squash_commits does

Each source arrives as a CommitWithSelection: the commit, its parent tree, and the selected tree, meaning the parent tree plus the chosen changes. Two predicates decide its fate. The selection is full when it equals the commit's tree, and empty when it equals the parent tree.

  1. Classify (source). A source is abandoned when the selection is full and -k wasn't given. A source with an empty selection that isn't being abandoned is skipped. An already-empty source is both full and empty, so it is abandoned, which lets jj squash clean an empty commit out of the middle of a stack. If every source is skipped, nothing happens.
  2. Rewrite sources (source). Abandoned sources are recorded as abandoned. Partial sources are rewritten to merge(source tree, inverted selected diff), which takes the moved changes back out.
  3. Moving into a descendant (source). If any source is an ancestor of the destination, jj rebases descendants first and uses the rebased destination. Otherwise the destination would still contain the changes being moved, applying them again would be a no-op, and they would vanish from history.
  4. Apply to the destination (source). The new tree is MergedTree::merge(Merge::from_diffs(destination tree, [each selected diff])). Every diff is labelled for conflict markers, for example (squash destination) and (squashed revision). If the same lines were changed differently, the destination ends up conflicted rather than the command failing. The builder records the old destination and every source as predecessors.

Choosing the description

SquashedDescription is Exact for -m, UseDestination for -u, and Combine otherwise. For Combine, try_combine_messages looks only at the abandoned sources and the destination. If none has a description, the result is empty. If exactly one does, its description is used. If two or more do, the editor opens with combine_messages_for_editing: the destination's description under JJ: Description from the destination commit:, each source's under JJ: Description from source commit: (empty ones too), and any configured trailers not already present. The editor intro is "Enter a description for the combined commit." A partially squashed source keeps its own description and doesn't contribute (source).

Invariants: the total content is preserved, because every change removed from a source is added to the destination, modulo conflicts. The destination keeps its change ID. A source is only abandoned when nothing of it is left. The result is one operation, so jj undo reverses it all.
