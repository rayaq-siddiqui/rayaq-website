How jj operation diff works

jj operation diff (alias jj op diff) compares the repository as recorded by two operations: which commits appeared, were rewritten or disappeared, and which working-copy commits, bookmarks and tags moved.

In short: jj loads the repository at a "from" operation and at a "to" operation, merges the from-side commit index into an uncommitted transaction on the to-side so both sides' commits can be looked up, and compares the two views. Commits are matched up through the predecessor records the operations stored, falling back to change ids, and filtered by the revsets.op-diff-changes-in revset. Working-copy commits, local bookmarks and tags, and remote bookmarks and tags are compared by name. It never writes a new operation head.

The command is cmd_op_diff. The help text: "Compare changes to the repository between two operations" (source). It is registered as Diff(OperationDiffArgs) in the operation group (source). The comparison itself is show_op_diff, which jj operation show and jj operation log --op-diff also call.

5. What it reads, and snapshotting

It goes through workspace_helper, so the working copy is snapshotted first unless --ignore-working-copy is given (source); the snapshot is then the default to-operation. It reads the operation objects and views of both sides from the op store, both commit indexes, and the commits it prints. With a diff format it also reads the trees and file contents of those commits. Nothing is published: the transaction on the to-repo is dropped, and a merged from-operation is written to the op store but not made an op head (source, source).

6. Algorithm and invariants

Classifying commits

compute_operation_commits_diff takes the visible heads on each side. Newly hidden commits are to_heads..from_heads, newly visible ones from_heads..to_heads (source). Newly hidden commits in the filter are grouped by change id, keeping one per change ("Just pick one if diverged"), and all of them start out abandoned (source). Each newly visible commit in the filter gets its predecessors from the operations' records if there are any, otherwise from a hidden commit with the same change id, otherwise none; those predecessors stop counting as abandoned (source). Whatever remains is shown as abandoned (source).

KindShown as
New commit+ commit
Rewritten commit+ commit, then - predecessor for each predecessor (a squash has several)
Abandoned commit- commit

ModifiedChange, write_modified_change_summary.

Predecessors come from operations in one pass when the to-op's parents are exactly the from-ops; otherwise jj walks back from the from-op to the common ancestor and forward again, and the result is "lossy" if the two have no single common ancestor (source).

The graph

The changed commits are evaluated as a revset in the merged repo and drawn topologically. Edges to commits that are not in the set are dropped "to keep the graph concise", and every node is ○ (source). With --no-graph they are printed flat, in the revset's own order (source).

Elision

The filter is resolved separately against each side's repo (source). Commits outside it are only counted, with count_estimate (source), and summarized as (Elided N newly added and M newly removed revisions), where a count is N+ or some when the estimate is not exact (source).

Patches

For a new or rewritten commit, the patch is an inter-diff from its first predecessor only, so a squash's diff stays readable; upstream marks this as "technically wrong". A new commit has no predecessor and shows its whole patch. An abandoned commit shows its own patch, not a reverse one (source).

Working copies, bookmarks and tags

Each changed name prints + with the to-side target, then - with the from-side target: a commit, (absent), or, for a conflicted target, one (added) or (removed) line per side of the conflict (source). Remote refs also show tracked or untracked; refs on the git remote are skipped, since they "should typically be covered in local branches" (source). Sections with no changes are not printed.
