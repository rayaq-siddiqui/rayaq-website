How jj operation revert works

jj op revert X undoes one earlier operation, X, while keeping everything that happened after it. It does this as a three-way merge of views: apply "X's parent minus X" to the current state, and record the result as a new operation.

In short: jj resolves X (default @) and requires it to have exactly one parent. In a transaction it loads the repo at X and at X's parent and merges them into the current repo, with X as the base and the parent as the other side. Rewrites and abandons implied by that merge are recorded, so later descendants get rebased. --what can keep the current repo state or remote-tracking bookmarks instead of the merged ones. The operation is revert operation <id>.

The command is cmd_op_revert. Compare jj op restore, which jumps back to X's state and drops everything after it, and jj undo, which restores the current operation's parent. Merging views is the same machinery jj uses for concurrent operations.

5. Transaction and operation

  • Transaction: one, started after the parent check (source).
  • Operation description: revert operation <full hex id of X> (source). Unlike undo's description, jj undo doesn't treat it specially, so undoing after op revert undoes the revert.
  • Commits rewritten: descendants of commits whose rewrite is reversed, rebased by tx.finish (source).
  • Nothing to revert: if the merge leaves the view unchanged, tx.finish prints Nothing changed. and records nothing.

6. Algorithm and invariants

The inverse as a merge

MutableRepo::merge(base, other) applies "other minus base" to the repo being built. With base = X and other = parent(X), that is the inverse of X's change, applied on top of the current state (source). Field by field (merge_view):

  • Heads: with the default index, record_rewrites compares the commits X has and its parent doesn't. A commit X introduced whose change ID also appears in parent(X) is recorded as rewritten back to the parent's version; one whose change disappears is recorded as abandoned. Heads present in parent(X) but not X are added back.
  • Bookmarks, tags, Git refs, remote refs, Git HEADs: each name that differs between X and parent(X) is three-way merged into the current value, which can produce a conflicted bookmark if it moved again since.
  • Working-copy commits: merged per workspace the same way.

Then --what

view_with_desired_portions_restored is called with the merged view as the one to "restore" and the transaction's base view as current (source). Leaving out repo keeps the current heads, local bookmarks, tags and working-copy commits; leaving out remote-tracking keeps the current remote bookmarks. Git ref mirrors always come from the current view.

Invariants: append-only. Later operations' effects survive unless they conflict with the inverse. Root and merge operations can't be reverted, because there's no single "before".
