How jj sign works

jj sign rewrites revisions so they carry a cryptographic signature from the configured signing backend (GPG, GPGSM or SSH). It always signs again, even commits that are already signed, and rebases their descendants.

In short: jj refuses if no signing backend is configured. It resolves -r, or the revsets.sign setting (default reachable(@, mutable())), and checks the commits are mutable. In one transaction it rewrites them and their descendants: target commits are written with the sign behavior forced on, optionally with --key; descendants are just reparented, which signs them only as signing.behavior says. It prints Signed N commits:, warns about commits authored by someone else, and records sign commit <id>.

The command is cmd_sign. The reverse is jj unsign. Signatures are also made automatically when commits are written, depending on signing.behavior, and at push time with git.sign-on-push; see jj git push. How commits are stored is on the commits page.

3. End-to-end flow

  1. Backend check. The store's signer can sign only if a main backend is configured (Signer::can_sign, source).
  2. Targets. -r values are unioned; without any, revsets.sign is parsed. Immutable commits are refused before anything is written (source).
  3. Rewrite. transform_descendants visits the targets and all their descendants, parents first, with new parents already filled in (source). A progress bar shows the change being signed (source).
  4. Report and finish. See §5 and §7.

4. Core architecture touchpoints

  • Commit writing: every commit write decides whether to sign with write_to_store: sign only if the signer can sign and should_sign says so, then pass a signing function to the backend.
  • Git backend: the backend serializes the commit, signs those bytes, and adds the signature as a header of the Git commit object, so the commit ID changes (source); see the commits page.
  • Signer: wraps the main backend plus the others used for verifying, with a cache (Signer).
  • Rewrites: each signed commit is a rewrite of the old one, so bookmarks follow and the working copy moves if @ was signed.

5. Transaction and operation

  • Transaction: one, covering all targets and descendants.
  • Operation description: sign commit <id>, or sign commit <first id> and <N> more, using the new commit IDs (source).
  • No targets: -r 'none()' is a valid no-op that prints Nothing changed. (test).
  • jj undo restores the unsigned commits.

6. Algorithm and invariants

Sign behaviors

SignBehavior and SignSettings::should_sign decide per commit. "Yours" means the commit's author email equals user.email. With the default keep, a signed descendant you authored is signed again when jj sign rebases it; an unsigned one stays unsigned (test with drop).

Invariants: every target is signed afterwards, whoever authored it. Commit contents, descriptions and authors are unchanged; the committer timestamp and the commit IDs change. No immutable commit is touched.

8. Worked example

From upstream's test_sign, with a test signing backend and behavior = "keep". Three commits one, two, three and an empty @ are unsigned. jj sign -r ..@ signs all four, so every commit ID changes:

Upstream's output (source):

Signed 4 commits:

  rlvkpnrz 062a3c5a (empty) two
  kkmpptxz d2174a79 (empty) three
  zsuskuln 8d7bc037 (empty) (no description set)
Working copy  (@) now at: zsuskuln 8d7bc037 (empty) (no description set)
Parent commit (@-)      : kkmpptxz d2174a79 (empty) three

Running the same command again signs all four again, with new IDs (source). There is no Rebased line because every descendant was itself a target.
