How jj arrange works

jj arrange opens a full-screen terminal UI over a set of commits. In it you can reorder commits by swapping them with a parent or child, and mark commits to abandon. Confirming turns the edited graph into a rewrite plan, applied in one transaction.

In short: jj resolves the revisions (default revsets.arrange, which is reachable(@, mutable())), checks they are mutable, and refuses a set with gaps. It loads the set plus its external parents and children as context, and builds an in-memory State where each commit has a planned parent list and a keep/abandon action. Key presses only edit that state. On c it builds a RewritePlan and executes it parents-first: abandon, or rebase onto the new parents if they changed. The operation is arrange revisions. q or Ctrl-C discards everything.

The command is cmd_arrange. Nothing touches the repository until you confirm. The UI works on a copy of the graph, and the only write path is RewritePlan::execute. For non-interactive reordering, see jj rebase.

5. Transaction and operation

  • Transaction: one, started only after you confirm (source). Quitting starts none.
  • Operation description: arrange revisions.
  • Commits rewritten: kept commits whose planned parents differ from their old ones (including external children), plus the commits you marked to abandon.
  • Unchanged: a commit keeps its ID only if its planned parents are unchanged and none of them was rewritten. Descendants beyond the external children are rebased when the transaction finishes.

6. Algorithm and invariants

The state model

State holds every loaded commit with its planned parents and action. It also holds head_order (heads of the set, in input order, for a stable display), current_order (the display order of the targets), the selection, and the external children and parents. update_commit_order recomputes the display order with a reverse topological walk over planned parents, ignoring external parents (source). Each key press works on a copy of the state, which is kept only if it changed (source).

Swapping two commits

swap_commits(a, b) exchanges the two commits' positions in the graph. It swaps them in the display order and in head_order, rewrites every commit's parent list so that references to a point to b and vice versa, and then swaps a's and b's own parent lists. The result is that the two commits trade places while everything around them stays attached to the same position. Upstream's unit test swaps a merge D with its parent C: C becomes the merge of B and D.

Executing the plan

execute orders the rewrites with a forward topological walk over planned parents, so a commit is handled after its new parents. For each one, it maps the planned parents through mut_repo.new_parents to their rewritten versions, builds a CommitRewriter, and either abandons the commit or, if the parents changed, rebases it. A gap in the set would leave a commit outside it between two targets, unable to move with them, which is why gaps are rejected up front.

Invariants: nothing is written unless you confirm. External parents are never rewritten. Every target is mutable.
