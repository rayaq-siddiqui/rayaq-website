How jj workspace list works

jj workspace list prints one line per workspace the repo knows about: its name, its root directory if one is recorded, and its working-copy commit. The list comes from the view; the root comes from a separate workspace store.

In short: jj loads the repo and snapshots the working copy, then compiles a template over the WorkspaceRef type, either -T or templates.workspace_list. It walks the view's wc_commit_ids map, which is sorted by workspace name, loads each working-copy commit and renders the template once per workspace. The root keyword looks the name up in .jj/repo/workspace_store/index; it never touches the other workspace's directory, so a deleted workspace is still listed with its old path.

The command is cmd_workspace_list. The help text: "List workspaces" (source). It is the List(WorkspaceListArgs) variant of WorkspaceCommand (source, dispatch). Workspaces are made by jj workspace add and dropped by jj workspace forget.

1. Command-line surface

FlagMeaning
-T, --template TEMPLATERender each workspace with this template instead of templates.workspace_list. Keywords are the zero-argument methods of WorkspaceRef (source). Shell completion offers template aliases.

There is no positional argument and no filter: every workspace is listed. The relevant global flags are --ignore-working-copy and --at-op; with --at-op the list is the workspaces as that operation's view recorded them.

The global flags are on the CLI page.

5. What it reads, and snapshotting

It calls workspace_helper, so the current workspace is snapshotted first (and, if colocated, Git HEAD and refs are imported), unless --ignore-working-copy or --at-op is given. Other workspaces are not snapshotted: their line shows the commit the view last recorded for them, which may lag their files. Beyond the view it reads one commit per workspace and, when the template uses root, the workspace store index. It starts no transaction.

6. Algorithm and invariants

Order

The loop is over wc_commit_ids(), a BTreeMap keyed by workspace name (source), so workspaces come out sorted by name, not by creation time, and the current workspace is not moved to the top.

The default line

builtin_workspace_list is name ": ", then, separated by spaces, the root relative to the current directory if one is recorded and the commit summary with the commit's bookmarks, then a newline (source). name is a revset symbol, so a name that is not a plain identifier is quoted (source).

Where root comes from

root is Option<FsPath>. It reads the workspace store's index, finds the entry with this name and joins its path to the repo directory, resolving .. literally (source). It is empty for workspaces created before jj 0.38.0, which recorded no path, and it is not checked against the disk: upstream's comment says list templates "should also keep rendering if a recorded path is stale or unavailable" and points to jj workspace root --name for strict checks (source).

Marking the current workspace

The default output marks it only by the working_copy label. In a custom template, target.current_working_copy() is true on the current workspace's line (source, test).

8. Example output

From upstream's tests, run in the main workspace after adding second at ../secondary (source): 

$ jj workspace list
default: . rlvkpnrz 504e3d8c (empty) (no description set)
second: ../secondary pmmvwywv 058f604d (empty) (no description set)

With a custom template that marks the current workspace (source): 

$ jj workspace list -T 'name ++ ": " ++ target.commit_id().short() ++ " " ++
    target.description().first_line() ++
    if(target.current_working_copy(), " (current)") ++ "\n"'
default: 504e3d8c1bcd  (current)
second: 058f604dffcd

And after ../secondary has been deleted from disk, root still prints the recorded path ($TEST_ENV is the test's temporary directory; source): 

$ jj workspace list -T 'name ++ ": " ++ root ++ "\n"'
default: $TEST_ENV/main
second: $TEST_ENV/secondary
