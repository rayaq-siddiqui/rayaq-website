How jj operation log works

jj operation log (alias jj op log) prints the operation history: every operation reachable from the current one, newest first, drawn as a graph of operations and their parents.

In short: jj resolves the current operation, walks its ancestors lazily in reverse topological order (ordered by end time where the history forks), and renders each operation with the templates.op_log template beside a graph node. With --op-diff or a patch flag it also prints, under each operation, what that operation changed compared to its parent, using the same code as jj operation diff.

The command is cmd_op_log, and the work is in do_op_log. The help text: "Show the operation log", noting that "Like other commands, jj op log snapshots the current working-copy changes and reconciles divergent operations" (source). It is registered as Log(OperationLogArgs) in the operation group (source, dispatch).

5. What it reads, and snapshotting

Without --at-op (or with --at-op=@) and without --ignore-working-copy, the command goes through workspace_helper: it loads the repo at the head operation, merging divergent op heads into a new operation if there are several, and snapshots the working copy, which can write a snapshot operation. That operation is then the current one and is listed first (source, source).

Otherwise it loads only the workspace and resolves the operation, without loading the repo at it, "so that the operation history can be inspected even with a corrupted repo state. For example, you can find the first bad operation id to be abandoned" (source). The help text recommends --at-op=@ --ignore-working-copy "to inspect the current state without mutation" (source). Op heads are still merged if --at-op is absent (source).

Beyond that it reads operation objects from the op store. Only with --op-diff or a diff format does it read views, commit indexes, commits and, for patches, trees and file contents.

6. Algorithm and invariants

The walk

walk_ancestors wraps each operation in OperationByEndTime and calls topo_order_reverse_lazy, whose neighbours are the operation's parents (source). While at most one operation is pending, the walk is linear: it emits that operation and queues its parents (source). When several are pending, it pops operations by latest end time until the branches meet again in a single operation, then sorts that piece topologically and emits it (source, source). Upstream's note: this "works so long as the operation history is mostly linear" (source). Each operation is emitted once, and a cycle panics with "graph has cycle" (source).

The graph

Each operation's edges are one direct edge per parent id; there are no indirect or missing edges as in jj log (source). The text is rendered into a buffer at the width left beside the graph, followed by the operation diff if any, and then added as a node with the op_log_node symbol (source). Without --reversed, operations are printed as the stream yields them.

--limit and --reversed

--limit is a take on the stream, so it cuts the newest-first order (source). --reversed must then collect every remaining operation: in graph mode reverse_graph turns parent edges into child edges and reverses the order; in flat mode the list is simply reversed (source, source). So -n 3 --reversed shows the three newest operations, oldest first.

Operation diffs

For each operation, jj loads its parents and merges them with merge_operations, passing no ui, workspace name, description or arguments, then loads the repo at the merged parent and at the operation (source). If the operation has more than one parent it prints nothing, because the merged repo "may have newly rebased commits, which wouldn't exist in the index" (source); that check comes after the merge. Otherwise it calls show_op_diff with the graph style unless --no-graph (source). In the tests the root operation shows no changes (test).
