How jj new works

jj new creates a new, empty change on top of one or more parents and, by default, makes it the working-copy commit. With --insert-after or --insert-before it splices the new change into the middle of history and rebases everything above it.

In short: jj resolves the parents (default @), merges their trees into one, writes a commit with that tree and an empty (or templated) description, rebases any requested children onto it, points this workspace's working-copy commit at it, and records all of that as one operation, new empty commit. Because the new commit's tree is exactly the parents' merged tree, it has no changes of its own. That's what "empty" means here.

Everything specific to jj new lives in one function, cmd_new, plus the shared helper compute_commit_location that it shares with jj duplicate, jj rebase and others. Loading the workspace, snapshotting, and finishing the transaction are the shared lifecycle described on the CLI page.

1. Command-line surface

The arguments are NewArgs. The parents can be given positionally or with -o, but not together with -A/-B.

5. Transaction and operation

  • One transaction, started after the parents and children are resolved (source), finished with the description new empty commit (source).
  • Commits created: exactly one. If a description template or trailers template is in use, jj also writes a hidden draft first (write_hidden) just to render the template. It's never added to the view.
  • Commits rewritten: none by default. With -A/-B, each child and then every descendant (via rebase_descendants), and jj prints Rebased N descendant commits.
  • Working copy: snapshotted when the workspace is loaded. Afterwards MutableRepo::edit moves this workspace's @ to the new commit. The previous @ is abandoned at the same time only if it is discardable (empty with no description), is a head, and isn't referenced by a bookmark, tag or other workspace (source). With the default jj new, the old @ is the new commit's parent, so it isn't a head and is kept.
  • jj undo restores the previous operation's view: the new commit stops being a head (it disappears from jj log), @ goes back, and any rebased children and moved bookmarks return to where they were.

6. Algorithm and invariants

Choosing parents and children

compute_commit_location evaluates each revset in order into an IndexSet, so duplicates collapse and order is kept. Then:

GivenParentsChildren to rebase
revisions (or nothing, meaning @)the revisionsnone
-A XXall current children of X (X.children())
-B Ythe parents of Y, in Y's own parent orderY
-A X -B YXY

If there are children, they must all be rewritable, and none may be an ancestor of a parent, or the commit would sit in a cycle (ensure_no_commit_loop). The parent list must not be empty.

The new commit's tree

merge_commit_trees returns the single parent's tree unchanged. For several parents it merges their trees against their common ancestors and resolves what it can. Anything left unresolved stays in the tree as a conflict: jj new never fails because a merge conflicts, it creates a conflicted merge commit. Either way the new commit introduces no changes relative to its parents' merge.

Rewiring the children

For each child (source), every old parent that is also a parent of the new commit is replaced by the new commit, other parents are kept, and the new commit is added if it isn't there yet. In the -A A -B D example from the help text, D's old parent C is not one of the new commit's parents, so D ends up as a merge of C and the new commit.

Advancing bookmarks

Only when no -A/-B is given and there is exactly one parent (source): bookmarks matching the experimental patterns that point at the parent's parents move to the parent. This mirrors jj commit, so a bookmark follows the commit you just finished. It is off by default.

The description

-m wins. Otherwise templates.new_description is rendered, and if empty the description stays empty. Trailers are added only to a non-empty description, because "a commit with no description is treated in a special way in jujutsu: it can be discarded as soon as it's no longer the working copy" (source).
