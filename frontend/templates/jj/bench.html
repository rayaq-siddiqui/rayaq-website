How jj bench works

jj bench is a hidden group that times index and revset operations against a real repo with the Criterion benchmarking library. It exists only in builds with the bench feature.

In short: each subcommand loads the repo through the workspace helper, resolves its inputs once, runs the operation once and reports how long that took, then hands the same closure to Criterion, which samples it repeatedly and compares against a saved baseline. Default builds don't contain it: the feature is off by default.

The group is BenchCommand, help text "Commands for benchmarking internal operations", marked #[command(hide = true)]. It is the Bench variant of the top-level Command enum, compiled only under #[cfg(feature = "bench")] (source, dispatch), and cmd_bench matches on it. The feature only pulls in criterion and is not in default (source).

4. Core architecture touchpoints

PieceRole here
IndexWhat three of the four benchmarks measure directly: common ancestors, ancestry, and prefix resolution, each called on workspace_command.repo().index().
Revsetsbench revset parses each expression once, then times resolution with a symbol resolver that has no extensions ("without parsing/evaluating short-prefixes"), evaluation, and counting the stream (source). With -f, blank lines and lines starting with # are skipped (source).
Store cachesBefore each bench revset batch the workspace is reloaded, because "repo.reload_at() isn't enough to clear store cache", and the index is preloaded with readonly_index (source).
Working copy, operation logOnly the normal workspace helper's snapshot on load; nothing is written by the benchmarks themselves.
