How jj sparse set works

jj sparse set changes which parts of the working-copy commit are written to disk. It adds or removes path prefixes in the workspace's sparse patterns, then checks out or deletes just the files whose inclusion changed. Commits and the operation log are untouched.

In short: jj loads the workspace, which snapshots it as usual, and locks the working copy. It starts from the current patterns, or from none with --clear, removes the --remove paths, adds the --add paths, and sorts the result. The working copy then writes the files that are newly covered and deletes the ones no longer covered. It saves its state under the same operation ID and prints Added N files, modified 0 files, removed M files. No operation is recorded.

The command is cmd_sparse_set. It and its siblings jj sparse edit and jj sparse reset each compute a new pattern list and hand it to the shared update_sparse_patterns_with. Its help text's example: jj sparse set --clear --add README.md --add lib to keep only those two (source).

1. Command-line surface

FlagTypeDefaultMeaning

SparseSetArgs

Paths are parsed by RepoPathBuf::from_relative_path, so they are relative to the workspace root, not the current directory. . alone means the whole repo; any other . or .. component is rejected. With no flags at all, the patterns stay as they are.

2. Configuration

None. The patterns aren't configuration: each workspace keeps its own list in its working-copy state, the sparse_patterns field (3) of the TreeState message, as a list of prefixes (source; see protobufs). A new workspace's list comes from jj workspace add --sparse-patterns, which copies the current workspace's by default.

5. Transaction and operation

  • Transaction: none. Only the working-copy lock is taken (source).
  • Operation: none. finish gets old_operation_id(), so the checkout state's operation ID doesn't change and only the tree state is rewritten (source, finish).
  • Before it: loading may record a snapshot working copy operation. That snapshot runs first, so edits to files about to be deleted are already in the commit.
  • jj undo does not reverse it, since there is no operation to undo. Run jj sparse set again, or jj sparse reset.

6. Algorithm and invariants

Computing the list

The closure starts from an empty HashSet. Unless --clear is given, it copies the current patterns in and then removes each --remove path. It then inserts each --add path and returns the set sorted (source). Removal is by exact equality: --remove lib/foo doesn't narrow a lib pattern, and --remove lib leaves lib/foo in place if both were listed. Adds win over removes of the same path, since they are applied last.

Updating the files

Each pattern is a path prefix: lib covers lib and everything under it, and the root covers everything (PrefixMatcher). TreeState::set_sparse_patterns builds two difference matchers from the old and new patterns:

  1. Added (new minus old): update from the empty tree to the current tree under it, which writes those files.
  2. Removed (old minus new): update from the current tree to the empty tree under it, which deletes them.
  3. Store the new patterns. Assertions check that nothing was "modified"; the stats report only additions, removals, and additions skipped because something already occupied the path on disk.

Invariants: the working-copy commit and every other commit are unchanged. After the command, the files on disk match the current tree under the new prefixes. Files outside them, even untracked ones, are not touched by the deletion step, which only removes tracked files. The pattern list is kept sorted.

8. Worked example

From upstream's test_sparse_manage_patterns. @ has file1, file2 and file3, and the patterns start as .. The commands run from a subdirectory, which makes no difference because paths are workspace-relative:

Upstream's snapshot for the first step (source):

$ jj sparse set --remove .
Added 0 files, modified 0 files, removed 3 files

jj sparse list then prints nothing, the three files are gone from disk, and jj file list still prints all three: they are in the commit, just not checked out. In the fourth step one call adds file1 and removes the other two, and the stats count both directions.
