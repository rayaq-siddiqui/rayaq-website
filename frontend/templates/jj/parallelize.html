How jj parallelize works

jj parallelize turns a chain of commits into siblings. Each target keeps its own changes and its parents from outside the set, but no longer depends on the other targets. Commits that used to sit on top of a target become merges of the targets they depended on.

In short: jj evaluates the target set and works through it parents-first. Each target's new parents are its old parents, with any target parent replaced by that parent's own new parents. Only the targets whose parents change must be mutable. A second map gives each target the set of targets that a non-target child must now merge. In one transform_descendants pass, targets get their new parents, non-target children of targets get the merged parent sets, and every commit whose parents changed is rebased, which keeps its own diff. The operation is parallelize N commits.

The command is cmd_parallelize. It uses the same rewrite machinery as jj rebase: a commit's tree is recomputed by merging its diff onto its new parents. How a rebased commit's tree is computed is on the trees page.

5. Transaction and operation

  • Transaction: one, after the rewritability check (source).
  • Operation description: parallelize <N> commits, where N counts every target, including those left unchanged (source).
  • Commits rewritten: targets with a target parent, non-target children of targets, and all their descendants (rebased with new IDs).
  • Commits unchanged: targets whose parents are all outside the set. In upstream's tests, target 1 keeps its commit ID (test).

6. Algorithm and invariants

New parents for targets

Targets are processed parents-first (source). For each parent of target T: if the parent is a target, T takes that parent's already computed new parents. Otherwise T keeps the parent. In a chain 0 ← 1 ← 2 ← 3 with targets 1::3, that gives 1 → [0], 2 → [0] and 3 → [0], so all three become children of 0.

New parents for non-target children

A non-target commit that sat on a target used to see every target below it in its ancestry. To keep those ancestors, new_child_parents maps each target to itself plus everything its target parents mapped to. For the chain above, that maps 3 to {1, 2, 3}. A child of 3 therefore becomes a merge of 1, 2 and 3 (source). This is why the help text says descendants outside the set "remain descendants".

Rebasing

Only commits whose parents changed are written (source). They use rebase(), not reparent(), so each commit keeps the changes it introduced, not its old snapshot. A target that depended on an earlier target's edits can therefore end up conflicted.

Invariants: ancestry with commits outside the set is preserved in both directions. Ancestry among targets is removed. Every changed target is mutable.

1 keeps its ID because its parent (the root) is outside the set. 2, 3 and 4 now sit on the root. 5 was a non-target child of 4, and new_child_parents[4] = {1, 2, 3, 4}, so it becomes a four-way merge. When a non-target child hangs off an interior target, it merges only the targets up to that point, as in test_parallelize_where_interior_has_non_target_children (2c parents: 1 2).
