How jj git fetch works

jj git fetch runs git fetch for each selected remote, then imports the changed remote-tracking refs into jj's view. Along the way it updates tracked local bookmarks, abandons commits the remote dropped, and records commits the remote rewrote as rewrites.

In short: jj picks the remotes (from --remote, --all-remotes, git.fetch, the only remote, or origin). For each remote it builds a bookmark expression and a tag expression, and turns them into forced Git refspecs. It shells out to git fetch --porcelain --prune --no-write-fetch-head --refmap= --no-tags, dropping and retrying refspecs the remote doesn't have. Fetched bookmarks land in jj's own refs/jj/remote-bookmarks/ namespace, not refs/remotes/. jj then diffs those refs against the view and imports the changes. Tracked remote bookmarks are merged into local ones. Commits no longer reachable from any ref are abandoned, and remotely rewritten commits get synthetic predecessors. All of this is one operation, fetch from git remote(s) <names>. In a colocated workspace, the new remote bookmarks are exported to refs/remotes/ when that operation is written.

The command is cmd_git_fetch. Most of the work happens in jj-lib's GitFetch and the shared import code in import_refs_inner. Remote bookmarks and their tracking state live in the view (view page). Abandoning and rebasing descendants is the usual rewrite machinery, run when the transaction finishes (CLI page).

3. End-to-end flow

Every remote is fetched before anything is imported, so the import sees all remotes at once (source). Just before the fetch loop it prints Fetching from Git remotes: <r1, r2, …> on the status stream (source). If any git fetch fails, the command errors out before the transaction is committed. Refs that git already wrote stay in the Git repository.

5. Transaction and operation

  • Transaction: one, started after the remotes are chosen and before any refspec is built (source).
  • Without integration: with --no-integrate-operation the operation is written but not committed, and nothing is exported to Git. The fetched refs stay in jj's own namespaces (test).
  • Operation description: fetch from git remote(s) <r1, r2, …>, the matched remotes joined with a comma and a space, the same list the status line prints (join, finish). Upstream's evolog shows it as fetch from git remote(s) origin (test).
  • Commits: fetched commits are imported unchanged. Abandoned commits are hidden, and their local descendants are rebased. With synthetic predecessors, local descendants of remotely rewritten commits are rebased onto the new versions.
  • Working copy: if @ was rebased or abandoned, it is updated when the transaction finishes, as with any rewrite.
  • jj undo restores the previous view. The fetched Git objects stay in the Git store.

6. Algorithm and invariants

Refspecs

split_into_positive_negative_patterns requires each expression to be (p1 | p2 | …) ~ (n1 | …): at most one union of positive patterns, minus unions of negative ones. Each pattern must convert to a Git glob containing none of : ^ ? [ ] (source, pattern_to_refspec_glob). Positive patterns become forced refspecs into jj's namespaces. Negative ones become ^refs/… exclusions. Without fetch-bookmarks, the remote's Git refspecs are reused if they have the shape +refs/heads/X:refs/remotes/<remote>/X. Anything else is skipped with a warning (load_default_fetch_bookmarks).

Missing remote refs

git fetch fails as a whole when one explicit source ref doesn't exist, and reports only one at a time. So fetch loops: run git, drop the failing refspec, and retry. --prune doesn't delete a ref named explicitly by a refspec, so when a refspec is dropped jj deletes its destination ref itself through gix, which is how a branch that disappeared upstream goes away locally. A failed deletion is Failed to prune stale refs. If no refspecs are left, nothing is fetched from that remote. --refmap= stops Git from also updating refs through the remote's configured remote.<name>.fetch mappings, so only the refspecs jj passed are applied (spawn_fetch).

Import

The import only considers refs matching what was fetched from each remote, so --branch a1 doesn't notice that a2 was deleted upstream (source). diff_fetched_refs_to_import compares the refs under refs/jj/remote-bookmarks/ and refs/jj/remote-tags/ with the view's remote bookmarks and tags. A known ref missing from Git becomes an update to absent.

Abandonment (abandon_unreachable_commits) hides pinned..old_remote_heads. Here pinned means local bookmarks and tags, plus untracked remote refs that are still visible, plus the root. It only runs when some changed ref had an old target, and only for commits that are currently visible. Synthetic predecessors (record_synthetic_predecessors) match change IDs between the commits the remote dropped and the newly reachable ones. A match marks the old commit as rewritten into the new one, or as a divergent rewrite if there are several new ones. Rewritten commits are then removed from the abandoned list (source).

Invariants: remote-tracking refs always mirror what the remote last reported, even when the local merge conflicts. Untracked remote bookmarks never move local bookmarks. Fetched commits are never modified.

8. Worked example

From upstream's test_git_fetch_remotely_rewritten. The local repo has book@origin (untracked) on eedc2709 "bookmarked", whose parent is 97604bbe "original", and the working copy @ sits on top. On the remote, "original" is re-described as "modified", which rewrites both commits. Then jj git fetch runs:

Upstream's snapshot:

$ jj git fetch
Fetching from Git remotes: origin
bookmark: book@origin [updated] untracked
Updated 2 rewritten commits.
Rebased 1 descendant commits.
Working copy  (@) now at: royxmykx 0818b176 (empty) (no description set)
Parent commit (@-)      : kkmpptxz 3ee37bc8 book@origin | (empty) bookmarked

Both new commits carry the old change IDs, so the commits only eedc2709 reached are mapped onto them instead of being abandoned. jj evolog then shows each new commit with the predecessor it replaced, created by the fetch from git remote(s) origin operation. Compare test_git_fetch_removed_bookmark: there, a tracked bookmark deleted on the remote deletes the local bookmark, and its commit is reported as Abandoned 1 commits that are no longer reachable.
