How jj prev works

jj prev moves the working copy backward along the commit graph. By default it starts a new empty working-copy commit on top of an ancestor of @'s parent. With --edit it edits an ancestor of @ directly instead.

In short: jj decides whether to edit (--edit, --no-edit, or ui.movement.edit). In new-commit mode @ must be a head. The target is the ancestors exactly offset generations above the start: @'s parents, or @ when editing. With --conflict, it is the nearest conflicted ancestors instead. One target is used, several prompt for a choice, and none is an error. One transaction then checks out a new commit on the target (prev: A -> B) or edits it (prev: A -> editing B).

cmd_prev calls the shared move_to_commit with Direction::Prev. The code, preconditions and outcomes are those of jj next, except for how the target revset is built. This page covers what differs and repeats the rest briefly.

5. Transaction and operation

  • Transaction: one, after the target is chosen.
  • Operation description: prev: <old @> -> <target> or prev: <old @> -> editing <target>, with short commit IDs (source).
  • Commits: at most one created (new-commit mode) and at most one abandoned (the old @).

6. Algorithm and invariants

Unlike next, prev uses the same formula in both modes: ancestors_at(start, offset) (source). Only the start differs. With --edit, jj prev edits @'s parent. Without it, jj prev puts the new @ on @'s grandparent, so that @- ends up one commit further back. A merge has several parents, and following each one can give several targets, which leads to the prompt (test_prev_prompts_on_multiple_parents).

With --conflict the result is the heads of the conflicted ancestors: the nearest conflicts going back. The source notes that roots() could be used to jump to the oldest one instead, pending feedback (source).

Invariants: the same as jj next. New-commit mode needs a childless @, edit mode never edits an immutable commit, and no existing commit is rewritten.
