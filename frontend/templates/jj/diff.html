How jj diff works

jj diff compares two trees and prints the difference. By default the trees are @'s parents, merged, and @ itself. -r widens that to a whole range of revisions; --from and --to pick any two revisions directly.

In short: jj loads the workspace, which snapshots it, and turns the paths into a matcher. With --from/--to it resolves each to exactly one commit (default @) and compares their trees. Otherwise it evaluates -r (default @), refuses a set with gaps, and compares the merged trees of the roots' parents with the merged trees of the heads. Copy records join the two sides, then a template or the diff formats print the result. Nothing is written.

The command is cmd_diff. The help text: "Compare file contents between two revisions", defaulting to -r @ (source). Unlike jj show, it prints no commit header and its result is always a single diff, however many revisions are selected.

5. What it reads, and snapshotting

  • Snapshot: yes. It loads the workspace with workspace_helper (source), which snapshots the working copy first (source), so jj diff shows current edits. That snapshot may record a snapshot working copy operation; diff itself records nothing.
  • Reads: the view at the current (or --at-op) operation, the index, the selected commits and the roots' parents, their trees, file contents for the matched paths, and copy records.
  • Output: through the pager, requested once both trees and the renderer are ready (source). The unmatched-paths warning goes to stderr after the diff (source).

6. Algorithm and invariants

Diffing a set of revisions

With -r, jj does not diff each revision in turn. It takes the set's roots and heads, and first checks that nothing between them is missing: roots..heads, the commits reachable from a head but not from a root (source), minus the set itself, must be empty (source). Then the parents of the roots, kept in order and without duplicates, are merged into the "from" tree, and the heads are merged into the "to" tree (source). One commit gives its own tree; several are merged with their merge bases and resolved where possible (merge_commit_trees). So -r X for a single commit is the same diff jj show X prints, and a set is one combined diff.

Upstream's test_diff_revisions exercises the cases. A single revision, a merge, a chain (A::C), a chain with an internal merge (B::E), several roots (C|D|E: both roots have the parent B) and several heads (B|C|D: the to tree merges C and D) all work. A|C is refused because B is missing, and C|E because D, E's other parent, is reachable from the head but not from the root.

--from and --to

Here no merging happens: each side must resolve to exactly one commit, and its tree is used as it is (source). The two commits need not be related, so jj diff --from main compares main with @ directly, whatever lies between them. Copy records are fetched for that one pair (source).

-T and the formats

Without -T, the formats are chosen as for jj show: at most one short and one long format from the flags, else ui.diff-formatter (source; see jj show). With -T, the renderer gets an empty format list, so it prints nothing, and the template is applied to each entry of the tree diff instead (source, source). The template sees the copy records too, so a rename is one entry with status renamed.

Invariants: exactly two trees are compared, whatever the arguments. The matcher limits both the diff and the copy records. Nothing in the repository changes.

From upstream's test_diff_basic: @ deletes file1, edits file2, and adds file3 and file4 with the old contents of file1 and file2, which the Git backend reports as a rename and a copy. The default :color-words format: 

$ jj diff
Modified regular file file2:
   1    1: 1
   2     : 2
        2: 5
   3    3: 3
   4     : 4
Modified regular file file3 (file1 => file3):
Modified regular file file4 (file2 => file4):

$ jj diff -s
M file2
R {file1 => file3}
C {file2 => file4}

file2 => file2 (modified)
file1 => file3 (renamed)
file2 => file4 (copied)
