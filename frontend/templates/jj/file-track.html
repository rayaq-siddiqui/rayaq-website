How jj file track works

jj file track snapshots the working copy once more, this time also starting to track the paths you name, even if snapshot.auto-track doesn't match them, and, with --include-ignored, even if they are ignored or too large.

In short: jj loads the workspace with the usual snapshot. It then takes a second snapshot whose "start tracking" matcher is your paths instead of snapshot.auto-track, and with --include-ignored whose "force tracking" matcher is your paths too. That snapshot updates only the working copy's own tree state. It records an operation, track paths, that changes no commits. The working-copy commit picks the files up at the next command's snapshot; upstream calls this out as a TODO (GH #8298).

The command is cmd_file_track. Its help text points out that by default new files are tracked automatically, so the command matters only when snapshot.auto-track is narrowed (source). The opposite command is jj file untrack. Snapshots in general are described on the working-copy page.

5. Transaction and operation

  • Transaction: a raw Transaction (into_inner()), committed directly with tx.commit rather than through tx.finish, so there is no Nothing changed. check (source).
  • Operation description: track paths. Its view equals the previous one, since nothing in the repo changed. Before it, the load may record a snapshot working copy operation for edits made since the last command.
  • Commits: none in this command. The rebase_descendants call has nothing to rebase (source).
  • Working copy: locked for the second snapshot, then released with the new operation's ID, so the next command doesn't consider it stale (source).
  • The real change lands in the next command's snapshot working copy operation, so that is what jj undo would undo first.

6. Algorithm and invariants

Two snapshots, two matchers

Loading the workspace takes the normal snapshot, whose "start tracking" matcher is snapshot.auto-track, and keeps its stats (source). The command's own snapshot swaps that matcher for your paths. With --include-ignored, it also sets them as the "force tracking" matcher, which overrides both the ignore rules and the size limit (source, field docs). Files that are already tracked are always snapshotted, whatever the matchers say.

Why the commit changes later

locked_wc().snapshot() returns a new tree, but the command ignores it: it never rewrites the working-copy commit or calls set_wc_commit (source). The working copy's tree state now includes the files, and it is saved as up to date with the track paths operation. On the next command, snapshot_working_copy finds that tree differs from the working-copy commit's and rewrites the commit, printing Rebased N descendant commits onto updated working copy. if it has descendants. Upstream's test marks this with TODO: fix GH #8298 so tracking is immediate (source).

Warnings

print_track_snapshot_stats combines the two snapshots' stats. A path the second snapshot skipped only because it isn't one of yours, which it reports as "not auto-tracked", takes the first snapshot's reason instead, so a file left out for size is still reported as too large. Only too-large files are printed, under Refused to snapshot some files:; the hint lists them and suggests jj file track --include-ignored (source, hint).

Invariants: no file is ever untracked by this command. Without --include-ignored, ignored and oversized files stay untracked. No commit is rewritten during the command itself.

8. Worked example

From upstream's test_track_ignored, with snapshot.auto-track = 'none()'. file1 and file1.bak exist, and *.bak is ignored. jj file list prints nothing, and jj new --no-edit adds a child on top of @:

jj file track file1 prints nothing. The next jj file list prints (source): 

file1
Rebased 1 descendant commits onto updated working copy.

The rebase message comes from that command's snapshot, not from jj file track. Later in the test, jj file track file1.bak without --include-ignored prints nothing and leaves the ignored file untracked. test_track_ignored_with_flag shows --include-ignored tracking file2.ignored, and test_track_large_file_with_flag shows the size warning for the file left out, with its hint.
