How jj bisect run works

jj bisect run binary-searches a range of revisions for the first "bad" one. For each candidate it checks the revision out in your own working copy, runs your command there, and reads the exit status: 0 is good, 125 is skip, 127 aborts, anything else is bad.

In short: jj resolves --range and assumes its heads are bad and the parents of its connected roots are good. Unless --trust-endpoints is given, it first runs the command on those endpoints to confirm. Then, until no candidates remain, it picks the middle of the commits between the latest good and the earliest bad ones. It checks that commit out, which records an operation and puts a new empty working-copy commit on top, and runs the command. The commits found are reported as the first bad ones, and the operation to restore to undo the search is printed. --find-good inverts the meaning of the result.

The command is cmd_bisect_run, the only subcommand of jj bisect (source). The search itself is jj-lib's Bisector, a small state machine the CLI drives one step at a time. The help text's example runs a fix from another revision on top of each candidate: jj bisect run --range v1.0..main -- bash -c "jj duplicate xyz -B @ && cargo test" (source).

2. Configuration

No bisect-specific keys. The commit summaries printed at each step use the usual commit-summary template (templates.commit_summary). Checking out each revision follows the same rules as jj new, so snapshot.* settings apply when the workspace is reloaded between steps. The command receives two environment variables: JJ_BISECT_TARGET, the full commit ID, and JJ_EXECUTABLE_PATH, the running jj binary (source).

5. Transaction and operation

  • One transaction per evaluated revision, including each pre-bisection check. It checks the revision out and is finished as Updated to revision <full hex id> for bisection before the command runs (source).
  • The command may run jj itself. After every Evaluate step the workspace is reloaded, because "the evaluation command may run `jj` commands" (source).
  • Undoing the search: the final output names the operation that was current at the start; jj op restore <id> discards every revision created during the search (source).
  • Afterwards the working copy is left on top of the last evaluated revision, not on the result.

6. Algorithm and invariants

Setting up

Bisector::new records heads(range) as bad. The good set starts empty. The endpoints to verify are heads(range), expected bad, and parents(connected(range)) ~ connected(range), expected good. They are popped from the end of a list, so the heads are checked first. A passing check isn't recorded; it only lets the search continue (source, CLI).

Each step

The candidates are range & (heads(good)..roots(bad)) ~ bad ~ skipped (source). The next revision is latest(bisect(candidates), 1), where bisect() in the default index takes the middle element of the candidate list in index order. Upstream notes this is "somewhat poor" for non-linear history (engine, docs). The "N revisions left" count printed first is the size of that candidate set, which still includes the revision about to be tested, and the step estimate is ceil(log2(N + 1)) (source).

The command's exit status is mapped to an Evaluation: 0 is good, 125 skip, 127 abort, anything else bad, including a signal (source). With --find-good the result is inverted before it's recorded, so the bisector always looks for "bad" (source, invert).

The result

When no candidates remain, next_step takes roots(bad). None means Indeterminate. Otherwise it walks parents from those roots through skipped commits: any found are "possibly bad", giving FoundDespiteSkips; else Found. Several roots are possible when the range has several disjoint heads (source).

Invariants: a commit is marked at most once (asserted). Bad is assumed to propagate to descendants within the range. Only the working-copy commit and operation log change; the range itself is never rewritten by jj.
