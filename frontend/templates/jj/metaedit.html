How jj metaedit works

jj metaedit rewrites commits to change their metadata (author, author date, description, change ID) without touching their trees. It only rewrites a commit when something actually changes, unless --force-rewrite is given, and rebases the descendants.

In short: jj resolves the revisions (default @) and checks they are mutable. If the set is empty it prints No revisions to modify. and stops. In one transaction it runs transform_descendants over the set. For each target it builds a rewrite and applies the requested author, timestamp, description and change-ID changes. It writes a new commit only if one of them differs from the old commit, or --force-rewrite is set. Descendants are reparented. The operation is edit commit metadata for commit <id>, plus and N more when there are several.

The command is cmd_metaedit. To edit a description in an editor, use jj describe. What a commit's metadata fields are, and how a rewrite copies them, is on the commits page.

5. Transaction and operation

  • Transaction: one, after the rewritability check (source).
  • Operation description: edit commit metadata for commit <full hex id>, or … for commit <id> and <N> more (source). The ID is the first target's old commit ID. Upstream's evolog shows edit commit metadata for commit 75591b1896b4990e7695701fd7cdbb32dba3ff50 (test).
  • Commits rewritten: targets with a real change, and descendants whose parents moved.
  • No-op runs: when nothing differs, no commit is written and the transaction finishes with Nothing changed. (test).

6. Algorithm and invariants

The source comment explains why transform_descendants is used instead of rewriting each target: if one target descends from another, it is still rewritten only once, so its predecessor chain gets one entry, not two.

The builder comes from rewriter.reparent(), which already applies two defaults from for_rewrite_from. First, the committer becomes the current user at the current time. Second, an empty author name or email is filled in from the committer, and a discardable commit authored by the committer gets its author date reset. So the change check compares against the old commit's author, not the builder's (source). A timestamp counts as changed only if it differs from both the builder's and the old commit's. That is why repeating the same --author-timestamp is a no-op, as upstream's test_metaedit_set_same_timestamp_twice checks.

Precedence (source): --author wins over --update-author (clap also rejects using both). --author-timestamp is applied after --update-author-timestamp, and clap rejects that pair too.

Invariants: trees never change. Immutable commits are never rewritten. Without --force-rewrite, a target is rewritten only if its metadata changes or its parents were rewritten.

Upstream's snapshot:

Modified 1 commits:
  yqosqzyt 01d6741e b | (no description set)

Parent commit (@-)      : yqosqzyt 01d6741e b | (no description set)

The evolog for the new change ID yqosqzyt lists the old kkmpptxz commits as its predecessors, linked by the edit commit metadata for commit 75591b18… operation (test). So the history isn't lost, even though the change ID is new.
