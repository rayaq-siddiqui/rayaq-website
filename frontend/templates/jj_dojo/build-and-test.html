Build, test and packaging

How Jujutsu Dojo is built with Bazel, how its Jasmine tests run against a fake VS Code API, and what CI checks on every pull request.

In short: everything builds with Bazel 9.1.0 and the Aspect JS/TS rules. npm run build is bazel build //:extension, npm run package builds //:vsix with vsce, and npm test is bazel test //.... Two in-repo macros wrap the rules: ts_library compiles a package and drops its test files, and jasmine_test compiles the tests and runs Jasmine with three helpers. One helper makes require('vscode') return an empty object, which each test fills with fakes from src/testing/ by calling installVscode. Another puts a pinned jj 0.45.1 binary on PATH. Bazel deps and visibility decide which packages may import Node or npm code. CI runs lint, a license-header check, a lockfile check and the full test suite.

4. Restricting dependencies

Inside Google the extension runs on Cider, a VS Code Web fork that can't import packages like node. The design notes ask for code to be split into interface files and implementation files, with only implementations allowed to import external-only packages, and use Bazel's deps to enforce it (docs/intro.md). A ts_project only sees the type declarations of what is in its deps, so a package without //:node_modules/@types/node can't compile an import of node:fs.

6. Tests and the fake VS Code API

Jasmine helpers

jasmine.json sets spec_dir to . and spec_files to **/*_test.js. Each jasmine_test loads three helpers before any spec.

HelperWhat it doesSource
install_global_vscodePatches Module.prototype.require so require('vscode') returns one shared empty object, marked __esModule so import * as vscode works. Without it, importing vscode outside the editor fails.28–49
install_global_jjPrepends $TEST_SRCDIR/_main/tools/bazel/jj to PATH, so a test that runs jj gets the pinned binary. It also prepends /usr/local/git/current/bin and /opt/homebrew/bin: jj git clone, fetch and push need Git 2.41 or later, and Bazel's sanitized PATH would otherwise find macOS's older Xcode Git. The src/client tests rely on this.23–44
source_map_stack_traceWraps Error.prepareStackTrace: after Node's source-map handler runs, it swaps the sandbox …runfiles/_main/ prefix for the real workspace path. It finds that path by following the execroot's BUILD.bazel symlink. Paths in failures then open in an editor.42–93

installVscode

Tests call installVscode in a beforeEach (for example extension_test.ts). It fills the shared vscode object in three passes:

  1. Every enum from third_party/vscode/vscode_enums.ts, 64 of them, generated from @types/vscode.
  2. Classes: CancellationTokenSource, CodeLens, Disposable, Position, Range, Selection, ThemeColor, EventEmitter, LogOutputChannel, and Uri as vscode-uri's URI with its Utils merged in.
  3. Fresh namespace objects: workspace, languages, commands, window, extensions.

Because the namespaces are new instances each time, every test starts clean. It returns the object typed as the fakes, so tests can reach helpers the real API doesn't have. fakeVscode() returns the same thing later, and logs() returns the fake JJ Extension output channel.

//src/testing is a ts_library over all of these (BUILD.bazel). Six test targets depend on it: //src, //src/client, //src/logging, //src/file_system_watcher, //src/ui/icon_theme_service and //src/utils. The others test plain logic and don't need the fake API.

newRepo

newRepo() is called inside a describe. Before each test it makes a fresh temporary directory, resolves it with realpath and runs jj git init there, or, given {remote}, runs jj git clone from another newRepo's root (which must be declared first, or it throws); after each test it deletes the directory. It returns the repository plus helpers that run jj in it, write or remove a file by relative path, and read the working-copy commit's change ID (source). Callers destructure the result when the describe runs, before any beforeEach, so the root path lives on a TestRepo object rather than in a string that would be captured stale (source). It runs jj through the client's subprocess helper, which is why //src/testing now depends on //src/client:subprocess_util. The SubprocessClient tests are its only users.

8. Generated VS Code enums

Tests can't import the real enums, because the real vscode module only exists inside the editor. populate_vscode_enum.py generates third_party/vscode/vscode_enums.ts instead. It refuses to run unless npm run lint is clean. Then it reads node_modules/@types/vscode/index.d.ts, pulls out every export enum with its doc comment using a regex that tolerates one level of braces, writes them after the original license header and a "do not edit" line, runs npm run fix to format the file, and copies @types/vscode's LICENSE next to it.

9. Loose ends at this pin

  • The .vsix ships no npm packages. vsce runs with --no-dependencies and the compiled host code is not bundled, so a runtime require of an npm package from the extension host would fail in the packaged extension. A TODO says this will matter once @parcel/watcher is used (source). At this pin nothing that reaches activate imports it.
  • Stale pointer in a helper. install_global_vscode.ts tells the reader to see vscode_test.ts for the setup and teardown helpers. No such file exists; the helpers are in install_vscode.ts (source).
  • Prefix match on paths. ts_library's test_ check uses startswith on the whole path, so sub/test_x.ts from a recursive glob would not be dropped. No such file exists today (source).
  • No Windows arm64 jj. addlicense is fetched for six platforms but jj for five, so tests that need jj can't build there.
  • Hand-synced Node version. pnpm is now read from package.json by both Bazel and CI, but Node 22 is still written in the lint workflow and kept in step with the Bazel lockfile only by a comment (_lint_run.yaml).
  • One //src target. The split between Google-importable code and the rest is still a TODO, so the deps scheme isn't yet enforced for most of src/.
