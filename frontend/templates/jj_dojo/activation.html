Activation and wiring

What Jujutsu Dojo declares to VS Code in package.json, what runs when the extension activates, the order its features are registered in, and how logging and errors are set up.

In short: VS Code activates the extension once startup has finished, or as soon as a workspace containing .jj opens. activate creates an output-channel logger and installs it as the global logger, then logs the version. It then builds JjUi, which registers the merge-conflict feature (tracker, decorations, CodeLens and two commands) and then the commit graph webview view. Every piece is a Disposable chained into context.subscriptions, so VS Code tears it all down on deactivation. Errors go through one JjError type and a small set of log… helpers. At this pin nothing outside the logging module calls the error helpers yet.

2. activate and deactivate

activate does four things, in order:

  1. Creates an OutputChannelLogger, pushes it onto context.subscriptions, and installs it with setGlobalLogger.
  2. Logs Extension version: ${packageJSON.build}. package.json has no build field at this pin, and the vsix target packages it unchanged, so outside tests this reads undefined. The upstream test supplies build: 'test-version' (test).
  3. Constructs JjUi and pushes it onto context.subscriptions.
  4. Logs Extension activated successfully.

deactivate only removes the global logger. Everything else is released by VS Code disposing context.subscriptions.

3. What ui.ts registers, and in which order

ui.ts splits the UI in two (source). JjUiBase is "shared between external and internal". Its constructor calls activateMergeConflict(). JjUi adds the parts "only used externally": after super() it registers the webview view provider. So merge-conflict support is always registered first.

OrderRegistrationDetails
1activateMergeConflict()Creates a ConflictTracker, a ConflictDecorator and a ConflictCodeLensProvider on top of it, and registers the two jj.mergeConflict.* commands. It returns them as one vscode.Disposable.from(…) (source).
2registerWebviewViewProviderFor CommitGraphViewProvider.viewType = jj-dojo.commit-graph (source), with webviewOptions.retainContextWhenHidden: true, so the graph keeps its state while the SCM view is hidden (source). How the view talks to its webview is on graph-protocol.

4. Disposables and lifecycle

Every resource ends up in one tree of Disposables rooted at context.subscriptions: the logger, and JjUi. JjUiBase keeps a disposables array, and its dispose() calls the shared helper dispose. That helper disposes each entry in array order, then empties the array, so a second dispose() is a no-op. The merge-conflict bundle disposes its tracker, decorator, CodeLens provider and command registrations together.

6. Error reporting

JjError is the project's single error type. It carries four optional flags: isShownToUser, isLogged, isNetworkError and isInternalError. getMessage() prefixes Internal Error - for internal errors. addPrefix(p) rewrites the message to p: message. JjError.from(x) normalises anything thrown: a JjError as is, a string, an Error (message only), or JSON.stringify of anything else. A private prefixes array is declared but never used, since addPrefix edits the message directly. isNetworkError isn't set anywhere at this pin.
