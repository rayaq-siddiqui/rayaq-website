Activation and wiring

What Jujutsu Dojo declares to VS Code in package.json, what runs when the extension activates, the order its features are registered in, and how logging and errors are set up.

In short: VS Code activates the extension once startup has finished, or as soon as a workspace containing .jj opens. activate creates an output-channel logger and installs it as the global logger, then logs the version. If no workspace folder is open it stops there. Otherwise it builds the jj subprocess client for the first workspace folder, wraps it in ApiImpl, and builds JjUi with that API. JjUi registers the merge-conflict feature (tracker, decorations, CodeLens and two commands), a read-only file system for the jj-commits scheme, and then the commit graph webview view. Every piece is a Disposable chained into context.subscriptions, so VS Code tears it all down on deactivation. Errors go through one JjError type and a small set of log… helpers, which the client and the file system providers now use.

2. activate and deactivate

activate does these things, in order:

  1. Creates an OutputChannelLogger, pushes it onto context.subscriptions, and installs it with setGlobalLogger.
  2. Logs Extension version: ${packageJSON.build}. package.json has no build field at this pin, and the vsix target packages it unchanged, so outside tests this reads undefined. The upstream test supplies build: 'test-version' (test).
  3. Reads the first workspace folder's path. If there is none, it logs No workspace folders found and returns, so nothing else is registered: no merge-conflict support and no graph view.
  4. Creates a SubprocessClient rooted at that folder and wraps it in ApiImpl, the implementation of the UI-facing Api interface. Its one method, readFileAtCommit, forwards to the client.
  5. Constructs JjUi(context, api) and pushes it onto context.subscriptions.
  6. Logs Extension activated successfully.

deactivate only removes the global logger. Everything else is released by VS Code disposing context.subscriptions.

3. What ui.ts registers, and in which order

ui.ts splits the UI in two (source). JjUiBase is "shared between external and internal" and keeps the Api it is given. Its constructor calls activateMergeConflict(), then registers the commit file system. JjUi adds the parts "only used externally": after super(api) it registers the webview view provider. So merge-conflict support is always registered first.

OrderRegistrationDetails
1activateMergeConflict()Creates a ConflictTracker, a ConflictDecorator and a ConflictCodeLensProvider on top of it, and registers the two jj.mergeConflict.* commands. It returns them as one vscode.Disposable.from(…) (source).
2registerFileSystemProviderA CommitIdFileSystemProvider over the API for the jj-commits scheme, with isCaseSensitive: true and isReadonly: true. Both the provider and its registration go into disposables (source). It serves a file's content at a commit, for URIs of the form jj-commits://<path>?commitId=…&opId=…&showParents (source); the read path is on roadmap. Nothing in the extension opens such a URI yet.
3registerWebviewViewProviderFor CommitGraphViewProvider.viewType = jj-dojo.commit-graph (source), with webviewOptions.retainContextWhenHidden: true, so the graph keeps its state while the SCM view is hidden (source). How the view talks to its webview is on graph-protocol.

4. Disposables and lifecycle

Every resource ends up in one tree of Disposables rooted at context.subscriptions: the logger, and JjUi. JjUiBase keeps a disposables array, and its dispose() first calls removeFocusModeConfigCache(), then the shared helper dispose. That helper disposes each entry in array order, then empties the array, so a second dispose() is a no-op. The merge-conflict bundle disposes its tracker, decorator, CodeLens provider and command registrations together. When activation returned early for want of a workspace folder, only the logger is there to dispose.

6. Error reporting

JjError is the project's single error type. It carries four optional flags: isShownToUser, isLogged, isNetworkError and isInternalError. getMessage() prefixes Internal Error - for internal errors. addPrefix(p) rewrites the message to p: message. JjError.from(x) normalises anything thrown: a JjError as is, a string, an Error (message only), or JSON.stringify of anything else. A private prefixes array is declared but never used, since addPrefix edits the message directly. isNetworkError isn't set anywhere at this pin.

extension.ts only uses logInfo. Of the wired code, the subprocess client and the file system providers throw through logAndShowInternalError: for a failed jj template parse, an unknown file status, a malformed jj-commits URI, or a write to the read-only file system (see roadmap). Nothing calls the two setGlobal… hooks, so no error callback or feedback provider is installed. The machinery is tested in logging_test.ts.
