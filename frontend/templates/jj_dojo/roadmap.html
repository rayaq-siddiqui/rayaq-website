Externalization plan

Jujutsu Dojo started as a Google-internal extension. This page lays out Google's plan for making it work outside Google, layer by layer and milestone by milestone, and checks each item against the code at the pinned commit.

In short: docs/intro.md splits the extension into a UI layer, an API layer and a client layer. Most of the UI layer can be shared with the internal build. The API and client layers need external implementations, built on the jj CLI where Google uses gRPC-web servers. At this pin, the commit graph, the conflict highlighter and two file system providers have landed. activate now builds a SubprocessClient and wraps it in an ApiImpl, whose two methods read files for the jj-commits and jj-file-id providers; the graph still gets fake data. Other lower-layer pieces are in the tree but nothing calls them yet: a @parcel/watcher-based FileSystemWatcher, an OptimisticStateEstimator that takes the place of the plan's PendingSnapshotsManager, and bare interfaces for an op-head watcher, a network-reconnect watcher and telemetry. Everything else is planned. The M1–M4 labels on this page come from the four-milestone timeline intro.md carried until this pin; it now points to a GitHub project board instead (§2).

File system providers

The providers live in src/ui/file_system_providers/. An abstract BaseFileSystemProvider owns the onDidChangeFile emitter, gives watch a no-op, and makes readDirectory, writeFile, createDirectory, delete and rename throw internal errors, leaving subclasses only stat and readFile.

CommitIdFileSystemProvider serves URIs of the form jj-commits://<path>?commitId=<id>, with an optional opId and a showParents flag that reads the merged file of the commit's parents instead (source). stat always returns an mtime of 0, since a commit's file never changes. readFile parses the query, requiring commitId, turns the path into a workspace-relative one, and calls Api.readFileAtCommit; a missing file becomes empty bytes, "most likely a new file" (source). Six tests cover the stat, each query parameter, the missing file and the missing commitId (source). A tested EmptyFileSystemProvider sits beside it, but nothing registers it.

FileIdFileSystemProvider serves jj-file-id://<path>?fileId=<id> (source). A file ID names one version of a file's contents, so stat also returns an mtime of 0. readFile requires fileId, throwing an internal error when it is missing or empty, turns the path into a workspace-relative one, and calls Api.readFileById (source, source). Its three tests cover the stat, a read, and the missing fileId (source).

Client layer

The client layer fetches information about jj (source). Internally that is gRPC-web calls to Google's jj servers, which are built directly on jj-lib. Externally it will be the jj CLI with templates, possibly replaced by a daemon client in the long run. The plan warns that a CLI client is harder than it looks. The internal server exposes things the CLI doesn't, such as file IDs, and answers in one request what may take several CLI commands. The plan says the internal server and the CLI may need to converge as part of open-sourcing. At this pin the client reads the commit graph through the CLI, but only its file reads are called; see §3.

3. The subprocess client so far

client.ts (88 lines), subprocess_client.ts (548 lines), subprocess_util.ts (90 lines), their tests, src/api/api.ts and BUILD.bazel

The Client interface has four methods. getWorkspaceState snapshots the working copy without publishing an operation and returns a RepoState: a list of commits, the opHead they were read at, which may be that unpublished operation, and conflictedFiles. Unlike a commit's files, which only lists what it changed, that holds every conflicted file in the working copy, including conflicts inherited from a parent or made by merging several parents (source). Its doc comment explains the optional lastKnownUnpublishedOperation argument. Because an unpublished snapshot is never remembered, jj keeps snapshotting the same files again, which caused "resource exhaustion issues internally inside Google". The internal extension passes the last unpublished operation to its server as the base to snapshot on top of. The CLI can't do that, so the CLI implementation ignores the argument (source). workspaceAdd is "the equivalent of jj workspace add <workspaceRoot>" and returns the new WorkingCopy (source). The other two read file contents as bytes. readFileAtCommit reads a path at a commit, or at its combined parents when showParent is set, and returns undefined if the file isn't there. It takes an optional opId because on the Git backend jj file show only finds commits reachable from the operation it runs at; the comment says Google's commit cloud may ignore it. readFileById reads a file by its FileId (source).

The types it returns live in the //src/api package. A Commit carries:

  • its ID and change ID, parentIds and childIds;
  • whether it is immutable: the root commit or an ancestor of immutable_heads();
  • files, the files it modifies, each a CommitFile with a path, a modification type (ADDED, MODIFIED, DELETED, RENAMED, COPIED, CONFLICTED or UNKNOWN), its metadata as a Merge of optional file IDs that may be conflicted, and, for a move or copy, the source path (source);
  • whether it is the working copy (active) or a parent of it (isWorkingCopyParentCommit);
  • its full description and a descriptionTitle, "usually" the first line;
  • author and committer times in milliseconds, and conflict and divergence flags;
  • the display ID with how much of it to highlight, and the change offset when the change is divergent;
  • its bookmarks, each with a name, an optional remote, needsUpload (jj's *) and isConflicted (source);
  • ancestors and descendants, read-only sets of commit IDs that include the commit itself;
  • workingCopies: the workspaces whose working copy it is, each with a jj workspace name, an optional root path, a display name, and currentWorkspace, true for the workspace the client runs in (source).

CommitId, ChangeId and OperationId are small classes that wrap a hex string and implement HashMapKey, as does the new FileId, so they can be HashMap keys (source). A MutableCommit mapped type drops the readonlys and turns the read-only sets into HashSets, so the client can fill them in (source). These are not the commit graph's own protocol types; nothing converts one into the other yet.

SubprocessClient answers getWorkspaceState with two jj calls:

  1. snapshotWithoutIntegrating runs jj --no-integrate-operation op log -n=1 --no-graph -T=id. Running any command snapshots the working copy, and --no-integrate-operation keeps the resulting operation out of the op log, so this returns the ID of an unpublished operation (see operations). A TODO notes that --no-graph drops jj's elided edges, which the commit graph can't draw either.
  2. getCommits runs jj --at-op <op> log --no-graph with a template that prints one JSON object per commit, including its bookmarks, working copies and modified files, and, for the current working copy only, its conflicted files (source). Each working copy carries currentWorkspace from jj's current_workspace() (source). The template is built field by field by toJsonObjectTemplate. No revset is passed, so it shows whatever the user's default log revset selects. It then:
    • makes every display ID as long as the longest shortest unique prefix, and at least 4 characters (source);
    • builds each commit's child list from the parent lists, and marks the working copy's parents (source);
    • gives the working-copy commit a default workspace rooted at the client's directory when jj reports none, which jj does when there is only one workspace. A comment admits this is "technically not correct" for a renamed default workspace. That fallback is marked current (source);
    • fills in every commit's ancestors and descendants with commit_topology (source);
    • returns the commits together with the working copy's conflicted files, mapped the same way as a commit's files (source).
    rawCommitToApiCommit appends /<offset> to a divergent commit's display ID, takes the first line as the title, and sets needsUpload for a local bookmark that is neither synced nor conflicted. isImmutable comes straight from the template. files now comes from the template's diff.files() (source): jj's status maps to a modification type, with a conflicted file becoming CONFLICTED and an unknown status logged as an internal error and returned as UNKNOWN; source is set when the source path differs; and the metadata is a Merge built from the file IDs on each side (source).

workspaceAdd runs jj workspace add --name=<basename> -- <root>. It names the workspace after the last path component itself, because jj workspace add prints nothing machine-readable, then finds that name in jj workspace list --ignore-working-copy and returns it. The -- keeps a path that starts with - from being read as a flag. If the new workspace isn't listed, it throws through logAndShowInternalError (see activation), which is why the target now depends on //src/logging.

readFileAtCommit calls fileShow, which runs jj --at-op=<op> --color=never file show -r=<id> -- root:"<path>", adding - after the ID for showParent. Without an operation ID it passes --ignore-working-copy instead of --at-op. The quoted root: pattern makes the path match literally instead of as a glob. jj exits with 1 for every user error, so a missing file is recognised by the text Error: No such path: and turned into undefined. A TODO notes that - fails on a merge commit until jj PR 10464 makes parents_of() usable. readFileById runs jj debug object file -- <path> <id>; its comment says there is no stable API for this yet, a jj file show --id was rejected upstream, and git cat-file would only work on the Git backend.

Every call goes through subprocess, Node's execFile promisified with a 10-second timeout, or its twin subprocessBuffer, which returns stdout as bytes for the file reads. Both run the command directly, with no shell, and raise execFile's 1 MiB output limit to 10 MiB. The comment explains the cap: diffs still go through VS Code's FileSystemProvider, which loads whole files, and jj doesn't snapshot files over 1 MiB by default anyway (source). The helper's only dependency is @types/node, so under the deps scheme it belongs on the external-only side. The interface target client depends only on //src/api.

The 36 SubprocessClient tests run the pinned jj (see the jj rule) in fresh repositories from newRepo. Fifteen cover a new repository, the returned opHead, modified files of every kind including a symlink, conflicted files, descriptions (including binary data and a multi-line title), divergent commits with their change offsets, a conflict, ancestors and descendants across several commits, a second workspace, and a workspace path that starts with -, commits beyond immutable_heads() being elided, and every parent of a merge working copy being marked (source). The snapshot test reads the op log the same unpublished way. A clean working copy adds no operation. A dirty file shows one "snapshot working copy" operation on top, and once the file is removed, the op log is back to what it was. Nothing was ever published (source). Five more run against a local repository with a remote and check local, conflicted, synced, unsynced and diverged remote bookmarks (source). Eleven read files at a commit: text, text read without an operation ID, binary data, a missing file, glob characters taken literally, showParent on a normal commit, files just under and just over the buffer limit, a file at an older opHead after its commit was rewritten or abandoned, and nested paths with spaces. On a merge commit the showParent reads are expected to fail until the TODO above is fixed (source). Five read files by ID, one in a nested directory, which the test gets from jj debug tree (source). The subprocess_util test still runs jj version (source). extension.ts constructs the client, and //src's deps now include //src/client:subprocess_client and //src/api:api_impl (source).

LocalFileSystemWatcher

Its doc comment explains why it uses @parcel/watcher rather than VS Code's createFileSystemWatcher: parcel supports exclusions, which are needed to ignore changes to gitignored files, and VS Code has no plans to add them (source).

At this pin it does use them. Every subscription passes parcel an ignore list, and every event that gets past it is checked against the same rules jj applies when it snapshots: global Git excludes, info/exclude, and the workspace's .gitignore files (see working copy).

  1. Construction takes a directory, which must be an absolute path, or it throws an internal error. Parcel doesn't follow symlinks, so it resolves the directory with realpath first, which also drops a trailing slash; a path that can't be resolved is reported as a user error. It builds a WorkspaceIgnoreManager for the directory and subscribes with that manager's native ignore list. Tests can inject a replacement subscribe, environment and home directory (source).
  2. Subscribing is generation-counted, so a subscription that an ignore change has replaced, or one that finishes after dispose, unsubscribes itself and goes quiet. Once a subscription is ready, the manager's cache is reset and the ignore list recomputed; if it changed in the meantime it subscribes again, otherwise it logs the path and every subscriber gets undefined, so nothing that happened during setup is missed. A parcel error, such as an event-queue overflow, also resets the cache and either resubscribes or sends undefined. A failure to subscribe is logged and shown to the user unless the watcher is already disposed (source).
  3. Each batch of parcel events goes through two passes. The first makes each path relative to the watched directory with / separators and drops any path with a .jj or .git segment (source). It records which paths are directories and drops cached rules a changed .gitignore, a changed excludes file or a deletion makes stale. The second pass drops ignored paths, so a rule change in a batch already applies to that batch. stateChanged is still set when an event's path is exactly <dir>/.jj/working_copy/checkout, but that path no longer appears in fileChanges. If the root .gitignore or the excludes file changed the native ignore list, it resubscribes. A batch with no state change and no surviving file produces no delta and doesn't advance the counter (source).
  4. Fan-out calls every callback and logs any exception it throws, so one failing subscriber doesn't starve the others (source).
  5. Dispose clears the callbacks, swaps in a no-op subscription so repeated calls are harmless, and then unsubscribes, logging any failure (source).

WorkspaceIgnoreManager reads only the base ignores and the root .gitignore at startup. Its doc comment says a nested .gitignore is read only when an event arrives under its directory, and never beneath an ignored directory, so that large or VFS-backed repositories don't need a tree walk. isIgnored walks a path's ancestors top-down, stopping at the first ignored one. Parcel's delete events don't say whether the path was a directory, which matters for rules ending in /, so the manager remembers which paths it has seen as directories. The native list is .git, .jj/repo when it is a directory rather than a secondary workspace's pointer file, and the top-level directories the root .gitignore ignores (source). The base ignores are the global excludes file, from core.excludesFile or $XDG_CONFIG_HOME/git/ignore, then info/exclude in the Git directory, which it finds through .jj/repo, a pointer file, store/git_target or .git (source). It parses just enough Git config to read core.excludesFile, including continuation lines, quoting and ~ (source).

The 30 integration tests run against the real @parcel/watcher on a temporary directory. They wait up to 30 seconds for each expected delta and use the fake VS Code API from //src/testing (fake API). Besides the three change types, they check that stateChanged fires for the workspace's own checkout file but not for a nested workspace's or for foo.jj/working_copy/checkout (source). Others cover subscriber isolation, disposal in every order, the error path and path handling (source). The ignore tests check the native list, the pointer-file case, suppressed empty deltas, root and nested rules with negations and directory-only rules, a symlinked .gitignore being skipped, reloading and resubscribing when rules change, changes during a resubscribe or an overflow, info/exclude in colocated, git_target and secondary-workspace layouts, and the global excludes file's precedence and parsing (source). Three more drive the real jj binary: a jj command that moves the working copy sets stateChanged, a plain edit doesn't, and a secondary workspace made with SubprocessClient.workspaceAdd reports its own checkout (source).

//src lists //src/file_system_watcher in its deps, which is the interface target, but nothing in the extension creates a watcher yet (source).

6. Design considerations

The plan ends with five rules for the work (source).

  • Use Bazel for builds. The internal extension runs on Cider, a VS Code Web fork that can't import packages like node. So code is split into interface files and implementation files, and Bazel deps keep external-only packages out of the interfaces. See build and test for how far this is enforced at this pin.
  • Avoid dependencies. Fewer dependencies mean less supply-chain risk and less work importing TypeScript libraries into Google. The extension's runtime dependencies at this pin are @parcel/watcher, @vscode-elements/elements, @vscode/codicons, jsonc-parser, lit and safevalues (source).
  • Reads should stay reads. Read commands will pass --no-integrate-operation and --ignore-working-copy, so a read neither causes divergence nor adds entries to the user's op log (see operations and working copy). SubprocessClient passes --no-integrate-operation and reads at that operation with --at-op, but not --ignore-working-copy: it snapshots on purpose, so the graph reflects unsaved file changes without publishing an operation. A file read with no operation ID passes --ignore-working-copy.
  • Different defaults internally and externally. Google developers are used to settings such as jj.includeWorkingCopyInParentDiffs and threeWayMerge.enabled being on. The plan says to check whether those defaults suit external users. At this pin contributes.configuration holds only jj.graph.focusMode, so neither setting exists.
  • Missing features in parallel. Features the internal extension still lacks, such as blame and squashing part of a file, are open for outside contributors while externalization goes on.

7. Loose ends at this pin

  • A native module in a package that ships no dependencies. @parcel/watcher is a native npm package, and the .vsix is built with --no-dependencies. A TODO already notes this has to change before the watcher is used (build and test).
  • The subprocess helper's limits. Output is capped at 10 MiB and every call has a fixed 10-second timeout (source). getCommits prints the whole log in one call, so a very large repository would still make it reject, and a file over the cap can't be read at all.
  • Two commit types. The client returns //src/api commits, while the graph takes its own protocol types, and the Api facade has no method that returns commits yet. Something still has to convert one into the other before the graph can show real data.
  • Providers nothing opens. activate now reaches the client, but only through the jj-commits and jj-file-id providers, and no command or view opens either kind of URI yet. The watcher, the estimator, the graph's SelectedCommitManager, the command hooks under src/ui/commands/, the focus-mode setting cache in src/ui/config/ (only dispose touches it) and the three interfaces are built and mostly tested on every CI run without affecting the shipped extension, as is the unregistered EmptyFileSystemProvider. They move from "in progress" to implemented once something uses them.
