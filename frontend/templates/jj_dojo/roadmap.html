Externalization plan

Jujutsu Dojo started as a Google-internal extension. This page lays out Google's plan for making it work outside Google, layer by layer and milestone by milestone, and checks each item against the code at the pinned commit.

In short: docs/intro.md splits the extension into a UI layer, an API layer and a client layer. Most of the UI layer can be shared with the internal build. The API and client layers need external implementations, built on the jj CLI where Google uses gRPC-web servers. At this pin, the commit graph and the conflict highlighter have landed. Two pieces of the lower layers are in the tree but nothing calls them yet: a one-function subprocess helper in src/client/, and a @parcel/watcher-based FileSystemWatcher in src/file_system_watcher/. Everything else is planned across four milestones running from October 2026 to June 2027.

Client layer

The client layer fetches information about jj (source). Internally that is gRPC-web calls to Google's jj servers, which are built directly on jj-lib. Externally it will be the jj CLI with templates, possibly replaced by a daemon client in the long run. The plan warns that a CLI client is harder than it looks. The internal server exposes things the CLI doesn't, such as file IDs, and answers in one request what may take several CLI commands. The plan says the internal server and the CLI may need to converge as part of open-sourcing. At this pin the client is a single helper function; see §3.

3. The subprocess client so far

src/client/subprocess_util.ts (38 lines), its test, and the subprocess_client target in BUILD.bazel

subprocess({cwd, command, args}) is Node's child_process.execFile, promisified, with a 10-second timeout. It resolves to {stdout, stderr} (source). It runs the command directly, with no shell, and it knows nothing about jj: it adds no flags and parses no output. Its only dependency is @types/node, so under the deps scheme it belongs on the external-only side.

The single test runs jj version in the current directory and expects the output to contain jj (source). That works because the test rules put the pinned jj binary on PATH (see the jj rule). The subprocess_client target isn't in //src's deps (source) and no file outside src/client/ imports it.

4. The file-system watcher

file_system_watcher.ts (57 lines), local_file_system_watcher.ts (171 lines), local_file_system_watcher_test.ts (17 tests) and BUILD.bazel

The package follows the interface/implementation split from the plan's design notes. The file_system_watcher target holds only the interface and depends only on @types/vscode. local_file_system_watcher adds @parcel/watcher, @types/node and the logging and error packages (source). The interface's doc comment says the abstraction exists so the extension can work with virtual file systems, and that internally it corresponds to a citc pubsub (source).

LocalFileSystemWatcher

Its doc comment explains why it uses @parcel/watcher rather than VS Code's createFileSystemWatcher: parcel supports exclusions, which are needed to ignore changes to gitignored files, and VS Code has no plans to add them (source).

  1. Construction takes a directory and subscribes to it recursively. Tests can inject a replacement subscribe. Once the subscription is ready, every subscriber gets undefined, so nothing that happened during setup is missed. If subscribing fails, the error is logged and shown to the user (source).
  2. Each batch of parcel events becomes one SnapshotDelta with the next counter value. stateChanged is set when an event's path is exactly <dir>/.jj/working_copy/checkout. A parcel error is logged and sent to subscribers as undefined (source, source).
  3. Fan-out calls every callback and logs any exception it throws, so one failing subscriber doesn't starve the others (source).
  4. Dispose clears the callbacks, swaps in a no-op subscription so repeated calls are harmless, and then unsubscribes, logging any failure (source).

The 17 tests run against the real @parcel/watcher on a temporary directory. They wait up to 30 seconds for each expected delta and use the fake VS Code API from //src/testing (fake API). Besides the three change types, they check that stateChanged fires for the workspace's own checkout file but not for a nested workspace's or for foo.jj/working_copy/checkout (source). The others cover subscriber isolation, disposal in every order, and the error path.

//src lists //src/file_system_watcher in its deps, which is the interface target, but nothing in the extension creates a watcher yet (source).

5. Design considerations

The plan ends with five rules for the work (source).

  • Use Bazel for builds. The internal extension runs on Cider, a VS Code Web fork that can't import packages like node. So code is split into interface files and implementation files, and Bazel deps keep external-only packages out of the interfaces. See build and test for how far this is enforced at this pin.
  • Avoid dependencies. Fewer dependencies mean less supply-chain risk and less work importing TypeScript libraries into Google. The extension's runtime dependencies at this pin are @parcel/watcher, @vscode-elements/elements, @vscode/codicons, jsonc-parser, lit and safevalues (source).
  • Reads should stay reads. Read commands will pass --no-integrate-operation and --ignore-working-copy, so a read neither causes divergence nor adds entries to the user's op log (see operations and working copy). No code passes these flags yet, because nothing runs jj reads.
  • Different defaults internally and externally. Google developers are used to settings such as jj.includeWorkingCopyInParentDiffs and threeWayMerge.enabled being on. The plan says to check whether those defaults suit external users. At this pin contributes.configuration is empty, so neither setting exists.
  • Missing features in parallel. Features the internal extension still lacks, such as blame and squashing part of a file, are open for outside contributors while externalization goes on.

6. Loose ends at this pin

  • Exclusions are the reason for parcel, but none are passed. The watcher picks @parcel/watcher for its exclusion support, yet calls subscribe with no ignore option (source). As written, gitignored build output and every write under .jj/ produce events.
  • A native module in a package that ships no dependencies. @parcel/watcher is a native npm package, and the .vsix is built with --no-dependencies. A TODO already notes this has to change before the watcher is used (build and test).
  • Symlinked repositories. A TODO says to check what happens when the repository is opened through a symlink, since the checkout path isn't resolved with realpath. The tests resolve their temporary directory first (source).
  • The subprocess helper's limits. It keeps execFile's default output buffer, which Node caps at 1 MiB, and a fixed 10-second timeout. A large jj log or a slow repository would make it reject. It has no callers yet, so neither limit has been tested against real use.
  • Neither package is reachable from activate. Both are built and tested on every CI run but don't affect the shipped extension. They move from "in progress" to implemented once a state manager or client uses them.
