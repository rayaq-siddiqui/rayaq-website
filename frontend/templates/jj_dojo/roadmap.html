Externalization plan

Jujutsu Dojo started as a Google-internal extension. This page lays out Google's plan for making it work outside Google, layer by layer and milestone by milestone, and checks each item against the code at the pinned commit.

In short: docs/intro.md splits the extension into a UI layer, an API layer and a client layer. Most of the UI layer can be shared with the internal build. The API and client layers need external implementations, built on the jj CLI where Google uses gRPC-web servers. At this pin, the commit graph and the conflict highlighter have landed. Several pieces of the lower layers are in the tree but nothing calls them yet: a Client interface with a SubprocessClient that reads the commit graph through jj, a @parcel/watcher-based FileSystemWatcher, and bare interfaces for an op-head watcher, a network-reconnect watcher and telemetry. Everything else is planned across four milestones running from October 2026 to June 2027.

Client layer

The client layer fetches information about jj (source). Internally that is gRPC-web calls to Google's jj servers, which are built directly on jj-lib. Externally it will be the jj CLI with templates, possibly replaced by a daemon client in the long run. The plan warns that a CLI client is harder than it looks. The internal server exposes things the CLI doesn't, such as file IDs, and answers in one request what may take several CLI commands. The plan says the internal server and the CLI may need to converge as part of open-sourcing. At this pin the client reads the commit graph through the CLI, but nothing calls it; see §3.

3. The subprocess client so far

client.ts (45 lines), subprocess_client.ts (161 lines), subprocess_util.ts (40 lines), their tests, src/api/api.ts and BUILD.bazel

The Client interface has one method, getWorkspaceState. It snapshots the working copy without publishing an operation and returns a RepoState, which is just a list of commits. Its doc comment explains the optional lastKnownUnpublishedOperation argument. Because an unpublished snapshot is never remembered, jj keeps snapshotting the same files again, which caused "resource exhaustion issues internally inside Google". The internal extension passes the last unpublished operation to its server as the base to snapshot on top of. The CLI can't do that, so the CLI implementation ignores the argument (source).

The types it returns live in a new //src/api package. A Commit carries its ID and change ID, parent and child IDs, whether it is the working copy, its description, author and committer times in milliseconds, conflict and divergence flags, the display ID with how much of it to highlight, and the change offset when the change is divergent. CommitId, ChangeId and OperationId are small classes that wrap a hex string so they can be map keys (source). These are not the commit graph's own protocol types; nothing converts one into the other yet.

SubprocessClient answers with two jj calls:

  1. snapshotWithoutIntegrating runs jj --no-integrate-operation op log -n=1 --no-graph -T=id. Running any command snapshots the working copy, and --no-integrate-operation keeps the resulting operation out of the op log, so this returns the ID of an unpublished operation (see operations). A TODO notes that --no-graph drops jj's elided edges, which the commit graph can't draw either.
  2. getCommits runs jj --at-op <op> log --no-graph with a template that prints one JSON object per commit (source). No revset is passed, so it shows whatever the user's default log revset selects. It then builds each commit's child list from the parent lists, and makes every display ID as long as the longest shortest unique prefix, and at least 4 characters (source). A divergent commit's display ID gets /<offset> appended (source).

Every call goes through subprocess, Node's execFile promisified with a 10-second timeout. It runs the command directly, with no shell. A comment now notes that execFile's 1 MiB output limit "might cause problems" for large descriptions or file contents (source). The helper's only dependency is @types/node, so under the deps scheme it belongs on the external-only side. The interface target client depends only on //src/api.

The six SubprocessClient tests run the pinned jj (see the jj rule) in a fresh repository from newRepo. They cover a new repository, a description, a description that is binary data, divergent commits with their change offsets, and a conflict. The last test reads the op log the same unpublished way. A clean working copy adds no operation. A dirty file shows one "snapshot working copy" operation on top, and once the file is removed, the op log is back to what it was. Nothing was ever published (source). The subprocess_util test still runs jj version (source). No file outside src/client/ imports the client, and //src's deps don't include it (source).

5. The file-system watcher

file_system_watcher.ts (58 lines), local_file_system_watcher.ts (204 lines), local_file_system_watcher_test.ts (20 tests) and BUILD.bazel

The package follows the interface/implementation split from the plan's design notes. The file_system_watcher target holds only the interface and depends only on @types/vscode. local_file_system_watcher adds @parcel/watcher, @types/node and the logging and error packages (source). The interface's doc comment says the abstraction exists so the extension can work with virtual file systems, and that internally it corresponds to a citc pubsub (source).

LocalFileSystemWatcher

Its doc comment explains why it uses @parcel/watcher rather than VS Code's createFileSystemWatcher: parcel supports exclusions, which are needed to ignore changes to gitignored files, and VS Code has no plans to add them (source).

  1. Construction takes a directory, which must be an absolute path, or it throws an internal error. Parcel doesn't follow symlinks, so it resolves the directory with realpath first, which also drops a trailing slash; a path that can't be resolved is reported as a user error. It then subscribes to the directory recursively. Tests can inject a replacement subscribe. Once the subscription is ready, it logs the path and every subscriber gets undefined, so nothing that happened during setup is missed. If subscribing fails, the error is logged and shown to the user, and not rethrown (source).
  2. Each batch of parcel events becomes one SnapshotDelta with the next counter value. Each path is made relative to the watched directory. stateChanged is set when an event's path is exactly <dir>/.jj/working_copy/checkout. A parcel error is logged and sent to subscribers as undefined (source, source).
  3. Fan-out calls every callback and logs any exception it throws, so one failing subscriber doesn't starve the others (source).
  4. Dispose clears the callbacks, swaps in a no-op subscription so repeated calls are harmless, and then unsubscribes, logging any failure (source).

The 20 tests run against the real @parcel/watcher on a temporary directory. They wait up to 30 seconds for each expected delta and use the fake VS Code API from //src/testing (fake API). Besides the three change types, they check that stateChanged fires for the workspace's own checkout file but not for a nested workspace's or for foo.jj/working_copy/checkout (source). The others cover subscriber isolation, disposal in every order, the error path, and the new path handling: a relative path is rejected, a trailing slash is ignored, and a directory opened through a symlink still produces events (source).

//src lists //src/file_system_watcher in its deps, which is the interface target, but nothing in the extension creates a watcher yet (source).

6. Design considerations

The plan ends with five rules for the work (source).

  • Use Bazel for builds. The internal extension runs on Cider, a VS Code Web fork that can't import packages like node. So code is split into interface files and implementation files, and Bazel deps keep external-only packages out of the interfaces. See build and test for how far this is enforced at this pin.
  • Avoid dependencies. Fewer dependencies mean less supply-chain risk and less work importing TypeScript libraries into Google. The extension's runtime dependencies at this pin are @parcel/watcher, @vscode-elements/elements, @vscode/codicons, jsonc-parser, lit and safevalues (source).
  • Reads should stay reads. Read commands will pass --no-integrate-operation and --ignore-working-copy, so a read neither causes divergence nor adds entries to the user's op log (see operations and working copy). SubprocessClient passes --no-integrate-operation and reads at that operation with --at-op, but not --ignore-working-copy: it snapshots on purpose, so the graph reflects unsaved file changes without publishing an operation.
  • Different defaults internally and externally. Google developers are used to settings such as jj.includeWorkingCopyInParentDiffs and threeWayMerge.enabled being on. The plan says to check whether those defaults suit external users. At this pin contributes.configuration is empty, so neither setting exists.
  • Missing features in parallel. Features the internal extension still lacks, such as blame and squashing part of a file, are open for outside contributors while externalization goes on.

7. Loose ends at this pin

  • Exclusions are the reason for parcel, but none are passed. The watcher picks @parcel/watcher for its exclusion support, yet calls subscribe with no ignore option (source). As written, gitignored build output and every write under .jj/ produce events.
  • A native module in a package that ships no dependencies. @parcel/watcher is a native npm package, and the .vsix is built with --no-dependencies. A TODO already notes this has to change before the watcher is used (build and test).
  • The subprocess helper's limits. It keeps execFile's default output buffer, which Node caps at 1 MiB, and a fixed 10-second timeout. An upstream comment now acknowledges the buffer limit (source). getCommits prints the whole log in one call, so a large repository or long descriptions would make it reject.
  • Two commit types. The client returns //src/api commits, while the graph takes its own protocol types. Something still has to convert one into the other before the graph can show real data.
  • Nothing new is reachable from activate. The client, the watcher and the three interfaces are built, and the first two are tested, on every CI run, but none affects the shipped extension. They move from "in progress" to implemented once a state manager uses them.
