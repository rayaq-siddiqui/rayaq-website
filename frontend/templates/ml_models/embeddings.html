Embeddings

A neural network can only do arithmetic, so every word, token, user or product has to become a list of numbers first. An embedding is that list: one learned row of a table, found by index. This page shows the table as a lookup and as a one-hot matrix product (they're the same thing), trains a tiny word2vec by gradient descent so you can watch meaning turn into geometry, and reads nn.Embedding out of PyTorch {{ upstream.tag }}.

Problem

Text arrives as symbols: "cat", "dog", "car". Symbols have no arithmetic. You can't add "cat" to "dog", and the number you'd get by assigning each word an ID (cat = 17, dog = 18, car = 19) is worse than useless, because it claims that cat and dog are close and that car is just one step further, for no reason except alphabetical luck. A model fed raw IDs would try to learn from that false geometry.

The alternative that avoids false geometry, giving each word its own on/off switch (a "one-hot" vector with {{ vocab|length }} slots for this page's tiny vocabulary, 50,257 for GPT-2), treats every pair of words as equally unrelated and wastes huge amounts of memory on zeros. What we want instead is a short dense vector for each symbol in which similar symbols get similar vectors, and we want the model to find those vectors itself.

Intuition

Think of a spreadsheet with one row per word and a handful of columns. Looking a word up means reading its row. That's the whole mechanism. The rows start out random, and training nudges them: every time a word's row helps the model make a better prediction, the row moves a little in the direction that helped. Words that appear in the same kinds of sentences get nudged in the same directions, so their rows drift together.

Linguists put it as "you shall know a word by the company it keeps". "Cat" and "dog" are both followed by "eats" and "chases", so after training their rows are close. "Car" is followed by "drives" and "needs", so its row lands elsewhere. Nobody wrote down that cats and dogs are animals; the geometry fell out of the statistics.

Highlighted rows are the ones this sentence reads. Nothing is computed: each output row is a copy of a table row, so the layer costs memory and index arithmetic, not multiplications.

Mechanics

Lookup equals one-hot times matrix

Let E be the embedding matrix with V rows (the vocabulary) and d columns (the embedding dimension). For a token with index i, its one-hot vector ei has a single 1 in position i, and

embed(i) = eiT E = E[i, :]    shapes: [1, V] @ [V, d] → [1, d]

The matrix product with a one-hot row just picks out row i, so a linear layer without a bias fed one-hot inputs is an embedding layer, and nn.Embedding is that layer without the wasted multiplications by zero. For a batch of index tensors of any shape (*), the output is (*, d). A batch of {{ ex.batch|length }} sentences of {{ ex.batch[0]|length }} tokens becomes a [{{ ex.batch|length }}, {{ ex.batch[0]|length }}, {{ table[0]|length }}] tensor.

What the gradient does

Because the forward pass copies rows, the backward pass adds into rows. If upstream gradient Gt (shape [d]) arrives at the output for position t whose token is it, then

∂L/∂E[j, :] = Σt : it = j Gt

Rows of tokens that do not appear in the batch get zero gradient, and a token appearing three times gets the sum of three gradients. That's why the gradient of a 50,000-row table is mostly zeros, why sparse=True exists (the gradient is stored as just the touched rows, but only some optimizers accept it), and why scale_grad_by_freq=True divides each row's gradient by how often its token occurs in the mini-batch, so that frequent words don't get most of the movement. padding_idx blocks the gradient for one row, which is how padding tokens stay at the all-zero vector they're initialized to.

Learning geometry: word2vec

Nothing above says why similar words end up close. That comes from the training task. The skip-gram model of word2vec (Mikolov et al., 2013) gives every word two vectors, vw as a center word and uw as a context word, and trains them so that a center word predicts the words within a window around it:

p(o | c) = exp(uo · vc) / Σw exp(uw · vc),   L = −Σ(c,o) log p(o | c)

This is softmax regression (see logistic regression and loss functions) where the "features" are the learned vector vc. The gradient on vc is Σw (p(w|c) − 1[w = o]) uw, and the gradient on each uw is (p(w|c) − 1[w = o]) vc. Two words that are followed by the same neighbours receive nearly the same pushes, so their vectors converge. In practice the full softmax over a vocabulary of a million words is too slow, and the paper replaces it with hierarchical softmax or negative sampling (the follow-up paper), which updates only a few sampled wrong answers per step. The objective is the same idea.

Static versus contextual

An embedding table gives one vector per word, whatever sentence it's in, so "bank" gets the same row in "river bank" and "bank loan". These are static embeddings (word2vec, GloVe, fastText). Modern language models use the table only as the first layer: transformer layers then mix each token's vector with its neighbours', so the vector at the top of the stack is contextual: it depends on the whole sentence (ELMo, BERT, GPT). A sentence-embedding model pools those contextual vectors into one vector per sentence or document, which is what retrieval systems search.

Scaling and weight tying

Two details from the original Transformer: the embedding output is multiplied by √dmodel, so its scale is comparable to the added position signal, and the input table is shared with the final output projection (pre-softmax linear layer). Sharing works because the output layer computes a dot product between the final hidden vector and one vector per word, which is the same shape as the input table (Press and Wolf, 2017). For GPT-2 small (V = 50,257, d = 768) the table has {{ "{:,}".format(tie.table) }} parameters, so tying saves {{ "{:,}".format(tie.saved) }} of an untied {{ "{:,}".format(tie.untied_total) }}, leaving {{ "{:,}".format(tie.tied_total) }}.

Implementation

import torch
import torch.nn as nn

emb = nn.Embedding(num_embeddings=6, embedding_dim=3, padding_idx=0)
emb.weight[0]                         # tensor([0., 0., 0.]), zeroed at construction
ids = torch.tensor([[1, 2, 3, 0, 0, 0]])
out = emb(ids)                        # shape [1, 6, 3]

# the same thing as a matrix product with one-hot rows
onehot = torch.nn.functional.one_hot(ids, num_classes=6).float()   # [1, 6, 6]
torch.allclose(onehot @ emb.weight, out)                           # True

out.sum().backward()
emb.weight.grad[0]                    # zeros: padding_idx gets no gradient
emb.weight.grad[1]                    # tensor([1., 1., 1.])

# weight tying for a language model head
head = nn.Linear(3, 6, bias=False)    # weight shape [6, 3], same as the table
head.weight = emb.weight              # one Parameter, used twice

# start from existing vectors, frozen by default
pretrained = nn.Embedding.from_pretrained(torch.randn(6, 3), freeze=True)

Skip-gram with a full softmax, in plain Python:

import math, random

def skipgram(sentences, dim=2, window=2, lr=0.05, epochs=300, seed=0):
    vocab = sorted({w for s in sentences for w in s})
    ix = {w: i for i, w in enumerate(vocab)}
    rng = random.Random(seed)
    V = [[rng.gauss(0, 0.5) for _ in range(dim)] for _ in vocab]   # center vectors
    U = [[rng.gauss(0, 0.5) for _ in range(dim)] for _ in vocab]   # context vectors
    pairs = [(ix[s[i]], ix[s[j]]) for s in sentences for i in range(len(s))
             for j in range(max(0, i - window), min(len(s), i + window + 1)) if j != i]
    for _ in range(epochs):
        for c, o in pairs:
            logits = [sum(a * b for a, b in zip(V[c], u)) for u in U]
            top = max(logits)
            exps = [math.exp(x - top) for x in logits]
            probs = [e / sum(exps) for e in exps]
            grad_v = [0.0] * dim
            for k, u in enumerate(U):
                g = probs[k] - (k == o)
                for d in range(dim):
                    grad_v[d] += g * u[d]
                    u[d] -= lr * g * V[c][d]
            for d in range(dim):
                V[c][d] -= lr * grad_v[d]
    return dict(zip(vocab, V))

Tradeoffs

  • Memory is the cost. V × d parameters, plus the optimizer state for each. A 50,257 × 768 float32 table is {{ "%.0f"|format(tie.table * 4 / 1e6) }} MB, and Adam keeps two more copies. Recommendation models with hundreds of millions of IDs spend most of their memory here, which is why they shard tables and use sparse=True gradients with optimizers that support them.
  • Out-of-vocabulary words. A word-level table has no row for an unseen word. Subword tokenization (BPE and relatives) fixes this by making the vocabulary pieces of words; fastText instead sums character n-gram vectors.
  • Dimension. Too small and distinct meanings collide; too large and rarely seen rows stay close to their random start. Typical sizes run from 64 for small models to over 10,000 for the largest language models.
  • Static versus contextual. Static vectors are cheap, interpretable and reusable across tasks, but conflate senses of a word. Contextual vectors resolve that at the cost of a full forward pass of a large network.
  • Weight tying saves a whole table and often helps perplexity in small models, but ties the input and output geometries together, which large models sometimes prefer to keep separate.
  • Pitfalls. Indices must be in [0, V): an out-of-range ID raises an error on CPU and can silently misbehave or crash on GPU. Learned geometry also reproduces the biases in the training text; "nearest neighbour" is not "true meaning".
  • Compared with one-hot. One-hot is exact and needs no training but has V dimensions and no similarity structure; an embedding is a learned low-rank factorization of that input layer.

Check yourself

Why is nn.Embedding(V, d) equivalent to a bias-free nn.Linear(V, d) on one-hot inputs, and why is it still the better choice?

Multiplying a one-hot row by the weight matrix selects one row, so the results match (up to the transposed weight layout of Linear). The lookup skips V − 1 multiplications by zero and never builds the V-wide input.

A batch of {{ ex.batch[0]|length }} ids contains token 1 twice and token 2 once. What is the gradient of row 1 if every output position receives gradient g?

2g, because gradients add into the rows they were read from. With scale_grad_by_freq=True it becomes g.

Two words never appear together in the corpus but always share neighbours. Will skip-gram embed them close together?

Yes. Skip-gram never pairs them directly; it only pushes each toward the same context vectors, which pulls the two center vectors together. That is the "company it keeps" idea.

Why can the input table and the output projection share weights?

Both have shape [V, d]: the input reads row i for token i; the output computes a dot product of the hidden vector with every row to get V logits. Sharing makes "the vector that represents a word" and "the vector that predicts a word" the same.
