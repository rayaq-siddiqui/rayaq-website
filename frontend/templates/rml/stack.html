The inference stack

rml is becoming a layered, MLIR-style inference stack: models defined in PyTorch, JAX and TensorFlow are exported into rml's own graph IR, checked against each framework, and lowered to kernels that aim to beat the frameworks on CPU. This page walks the levels and marks which exist at this commit.

In short: a model is written once per framework, from shared weights. An offline Python exporter traces it into rml-graph, a JSON op list over mmapped safetensors weights. From there rml runs it in C++ with no Python, and a golden test checks the result against the framework's own output. Today the graph runs op by op on rml's readable kernels. The plan adds a StableHLO import route above the graph, and a fused, buffer-planned, threaded kernel-level plan below it. Every model is benchmarked against each framework's eager and compiled modes.

The direction

rml's plan (docs/progress.md L135–146) extends the Python front ends to every neural model on the ML models reference. Three commitments shape it:

  • Three frameworks, one model. Each model is defined in PyTorch, JAX and TensorFlow, exported, checked against the framework, and benchmarked on CPU.
  • Layered like MLIR. Frameworks hand over StableHLO through their own production exporters, which is what an MLIR pipeline consumes. tools/ lowers it to rml-graph, and inside rml, rml-graph lowers to a kernel-level plan that runs fused, threaded kernels.
  • Two routes, cross-checked. The direct per-framework exporters stay as a second way in, and the two routes are checked against each other.

Why layers

Each level has one job, so each can be tested on its own. The framework-facing work stays in offline Python, where the frameworks live. The format in the middle is small on purpose (graph_ir.md L87–91): exporters lower framework ops onto it, so JAX's dot_general becomes transpose + reshape + matmul, and an op an exporter cannot lower fails the export with the framework's op name. There is no silent fallback. Below the format, optimization happens in rml without touching any exporter.

StableHLO is the planned front door because each framework already produces it with its production tooling, and it is the input an MLIR pipeline expects. Keeping the direct exporters as well gives two independent routes into the same IR, which the plan checks against each other.

What stays out

  • Training. The format is inference only: there is no backward pass (graph_ir.md L6). Training in rml goes through {{ link('autograd', 'Autograd') }}.
  • Classical ML and KV-cache decoding stay out of the graph stack (progress.md L143–146). LLM decoding keeps its own allocation-free loop in rml/llm; the graph executor is a general model runner.
  • Sampling loops stay outside the graph. The exported network is one step, and noise is an input, so a diffusion sampler calls the graph once per step.

Where it stands

The first benchmark run (progress.md L128–133, on a 4-vCPU Linux container) shows the shape of the remaining work. rml beats every framework only on the batch-1 CNN, by 1.6–3.5× on one thread, where per-call overhead dominates. It is 2–20× slower wherever GEMM dominates, because only GEMM is threaded and the JAX and TensorFlow graphs arrive with layer norm, softmax and GELU decomposed into chains of small ops (frameworks.md findings). The planned levels target exactly those gaps: a packed SIMD GEMM, threaded kernels over buffers planned at load, and fusion of the decomposed patterns. {{ link('benchmarks', 'Benchmarks against the frameworks', '') }} has the numbers, and {{ link('lowering', 'Lowering and fast CPU', '') }} the plan.

Apple Silicon numbers (NEON, Accelerate) have not been produced yet, and GitHub CI has failed before any job starts since October 17, so these changes are verified only in rml's Linux container (progress.md L164–166).
