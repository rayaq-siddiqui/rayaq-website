Exporters and the model zoo

tools/rml_export/ is the offline Python half of the inference stack. It takes a model in PyTorch, JAX or TensorFlow by one of two routes, lowers each op onto the rml-graph op set, checks every step against the framework, and writes the graph file rml loads. The zoo defines the same 19 models in all three frameworks.

In short: every framework has two ways in. The direct exporters walk the framework's own traced graph (an ATen ExportedProgram, a jaxpr, or a frozen GraphDef); the StableHLO importer reads the StableHLO module each framework's compiler path produces (torch-mlir, jax.export, XLA's StableHLO stage). Both call one shared Builder, which computes a NumPy example value for every op, so each lowering is shape-checked node by node and ops on constants fold away. Clean-up passes then cancel transposes, drop broadcasts, merge repeated work and fuse written-out means, softmaxes, layer norms and GELUs back into single ops. A fixture script exports all 19 zoo models by all six routes, and C++ tests require rml to match every framework and all twelve results per model to agree.

Everything here runs offline in a virtualenv pinned by tools/requirements-export.txt (NumPy 2.5.4, PyTorch 2.14.1, JAX 0.12.0, TensorFlow 2.21.0 and torch-mlir 20261001), created with Python 3.12 or newer; rml itself never links or needs Python. The format the exporters write is described on {{ link('graph-ir', 'The rml-graph IR') }}, and where this fits in the whole stack on {{ link('stack', 'The inference stack') }}.

The shared builder

common.py holds the Builder that every exporter calls once per lowered op, and a NumPy reference implementation of every IR op (REFERENCE, L163). Carrying a concrete example value for every graph value is the central idea: it gives each value its recorded shape and dtype, it lets an exporter check its lowering against the framework node by node, and it folds constants.

The direct exporters

Each direct exporter starts from the graph its framework already produces, so it sees what the framework would run, not a re-trace of Python code. Each one lowers op by op, checks every lowered value's shape against the framework's recorded shape, and raises ExportError naming the framework op when it has no lowering. There is no silent fallback. They keep the framework's high-level ops where the IR has them (graph_ir.md L10–12).

The StableHLO route

StableHLO is the MLIR dialect all three frameworks lower to, so one importer serves all of them (from_stablehlo.py L1–14). It parses the module's text with the MLIR Python bindings that ship in jaxlib (parse, L554–564) and walks func.func @main op by op. The leading arguments of @main become stored constants and the rest graph inputs (export, L567–586). The contraction, convolution and pooling lowerings are borrowed from the JAX exporter's Lowering, since StableHLO's ops carry the same dimension numbers as jax's primitives.

Clean-up passes

Lowering leaves debris: identity reshapes, stacked transposes, the NHWC ↔ NCHW pairs TensorFlow's convolutions produce, the explicit broadcasts StableHLO spells out, and layer norms, softmaxes and GELUs written out as chains of elementwise ops. passes.py removes it before the graph is written, running the passes until none changes anything and dropping dead code after each round (run_passes, L523–528).

PassRewriteSource
simplify_shape_opsDrops identity reshapes and transposes, collapses reshape-of-reshape, composes transposes (transpose(transpose(y, p), q) = transpose(y, p[q])), and turns a reshape of a reduction back to its input's rank into the reduction with keep_dims.L38–77
sink_transposesRewrites f(transpose(x)) as transpose(f(x)) for elementwise f, permuting a constant other operand to match; only single-reader transposes move. Sinking below a conv's bias add and ReLU brings it next to the next layer's inverse transpose, where the two cancel.L80–120
drop_implicit_broadcastsRemoves broadcast_to, and reshapes that only prepend size-1 axes, when every reader is a binary op that broadcasts anyway.L128–159
shrink_broadcast_constantsA constant folded from a broadcast repeats along some axes; it is shrunk back to the slice it repeats.L162–196
unbatch_matmul_weightsA constant matmul weight of rank > 2 whose batch slices are all equal (PyTorch's LSTM input projection) becomes one 2-D slice, so the executor runs the batch as one matrix product.L199–224

The fusions are why the three frameworks now export the tiny transformer block to similar sizes: 32 nodes from PyTorch, 42 from JAX and 29 from TensorFlow, where JAX and TensorFlow hand over layer norm, softmax and GELU decomposed. rml's own docs/progress.md checks off export-time fusion of layer norm and GELU (L163). Fusion inside rml, below the graph, is on {{ link('lowering', 'Lowering and fast CPU') }}.

The zoo

tools/rml_export/zoo/ defines each model once per framework (torch_zoo.py, jax_zoo.py, tf_zoo.py). All three load their parameters from weights(), which draws them from a NumPy generator seeded per model (1234 plus the model's index), so the three definitions compute the same function from identical weights (weights.py L1–7, L98–202). Each model has a "tiny" size, committed as a test fixture, and a "bench" size, which is timed (CONFIGS, L19–76). encoder and tiny_gpt take int32 token ids (TOKEN_MODELS, L16). Recurrent models are unrolled: JAX's lax.scan by the exporter, PyTorch's nn.RNN / nn.LSTM by torch.export, and TensorFlow's by a Python loop over time steps.

Fixtures and golden tests

make_graph_fixtures.py exports every tiny zoo model by six routes: torch, jax, tf, and stablehlo_torch, stablehlo_jax, stablehlo_tf, with PyTorch first because torch.export loads triton, which crashes if TensorFlow's or jaxlib's LLVM loaded before it (L27–30). For each pair it draws a batch of 2 inputs, exports the graph and runs the framework, writes <route>_<model>.json and .safetensors, evaluates the written graph with the NumPy reference ops and requires it to match the framework, and finally writes the framework's inputs and outputs to .golden.safetensors (L101–115). That is 114 committed graphs.

golden_test.cc closes the loop in C++ with no Python. It loads each fixture, runs it through rml's executor on the golden inputs, and requires every output element within 1e-5 of the framework's (L20–54). Its cases are every .json in the testdata directory, so a new fixture is tested without editing the test, and a second test fails if any direct framework and model pair is missing (L56–81).

Cross-framework agreement

Matching each framework separately does not prove the three definitions are the same model. Two more tests check that.

  • cross_framework_test.cc runs in bazel test //... with no Python. For every model with a fixture from all six routes, it first requires every route's golden inputs to be identical, then runs all six graphs and compares all twelve results (each route's framework output and its rml output) pairwise within 1e-5 (L80–136). A second test fails if any model is missing a route, or if there are fewer than 19 (L141–153).
  • tools/cross_framework_test.py runs the frameworks live and lowers each by both routes into rml-graph-run, then asserts that all nine results (three framework outputs, six rml runs) agree within 1e-5 + 1e-5 |b| with no NaNs (L184–211). Its nine cases per model are batches 1, 2, 5 and 7, inputs scaled by 4 and 10, all zeros, and the smallest and largest token ids (L53–65); RML_CROSS_BENCH=1 adds a bench-size case at 1e-4. It also checks that rml repeats itself bit for bit on one thread and agrees across 1 and 4 threads (L214–224), and that an op rml-graph lacks fails the export by name in every framework and in the StableHLO importer (L227–270).

The suite found one real framework difference: with all-zero input every MoE router probability ties, and torch.topk on CPU picks different tied indices than JAX, TensorFlow and rml, which take the lowest. That one comparison is excluded in KNOWN_DIVERGENCE, and rml run on the PyTorch export must still agree (L67–75).

tools/rml_infer_example.py is the same idea as a short end-to-end demonstration: one small classifier (dense, layer norm, tanh-GELU, dense, softmax) written the ordinary way in PyTorch, JAX and TensorFlow on shared weights, lowered by the direct exporters, run by rml-graph-run, and printed with a table of pairwise maximum differences that must all be within 1e-5 (L148–179).

Exact tiny examples

Two examples run framework-defined models from C++ with no tolerance at all. Each model is written once per framework on the same non-zero dummy weights, exported by the direct exporters, run by the executor, and compared bit for bit, fused and unfused. That works because the dummy values make every op exact in f32, so the output has one value whatever the summation order, fusion, threading or exp and tanh approximation (tiny_models.h L1–10).

The generators, make_tiny_net.py and make_tiny_models.py, check each framework's output and each written graph (evaluated in NumPy) against a NumPy reference with np.array_equal, then print the reference as C++ literals for the tests (make_tiny_net.py L103–119). The C++ side repeats the input formulas, and tiny_net also has a plain-loop ReferenceForward (tiny_net.cc L51–71). Building them found one framework detail: torch.nn.LayerNorm's one-pass CPU kernel rounds the variance by an ulp once a row's mean exceeds about 1/6, so the PyTorch block uses a two-pass layer norm like JAX and TensorFlow (make_tiny_models.py L338–351, progress.md L172).
