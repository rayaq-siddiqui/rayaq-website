Exporters and the model zoo

tools/rml_export/ is the offline Python half of the inference stack. It traces a model in PyTorch, JAX or TensorFlow, lowers each framework op onto the rml-graph op set, checks every step against the framework, and writes the graph file rml loads. The zoo defines the same models in all three.

In short: each exporter walks its framework's own traced graph (an ATen ExportedProgram, a jaxpr, or a frozen GraphDef) and calls one shared Builder. The builder computes a NumPy example value for every op, so each lowering is shape-checked against the framework node by node, and ops on constants fold away. Clean-up passes then remove redundant reshapes and transposes before the graph is written as JSON plus safetensors. A fixture script exports the four zoo models from all three frameworks and saves each framework's outputs, which a C++ golden test compares with rml's. The StableHLO route is planned.

Everything here runs offline in a virtualenv pinned by tools/requirements-export.txt (NumPy, PyTorch, JAX and TensorFlow); rml itself never links or needs Python. The format the exporters write is described on {{ link('graph-ir', 'The rml-graph IR') }}, and where this fits in the whole stack on {{ link('stack', 'The inference stack') }}.

The shared builder

common.py holds the Builder that every exporter calls once per lowered op, and a NumPy reference implementation of every IR op (REFERENCE, L163). Carrying a concrete example value for every graph value is the central idea: it gives each value its recorded shape and dtype, it lets an exporter check its lowering against the framework node by node, and it folds constants.

Three exporters

Each exporter starts from the graph its framework already produces, so it sees what the framework would run, not a re-trace of Python code. Each one lowers op by op, checks every lowered value's shape against the framework's recorded shape, and raises ExportError naming the framework op when it has no lowering. There is no silent fallback.

Clean-up passes

Lowering leaves debris: identity reshapes, stacked transposes, and the NHWC ↔ NCHW pairs TensorFlow's convolutions produce. passes.py removes it before the graph is written, repeating until nothing changes (L121–124):

  • simplify_shape_ops (L33–61) drops identity reshapes and transposes, collapses reshape-of-reshape into one, and composes two transposes into one, since transpose(transpose(y, p), q) = transpose(y, p[q]).
  • sink_transposes (L64–104) rewrites f(transpose(x)) as transpose(f(x)) for elementwise f. For a binary op the other operand must be a constant, which is permuted to match, and only transposes with a single reader move, so nothing is duplicated. Sinking a transpose below a conv's bias add and ReLU brings it next to the inverse transpose of the following layer, where the two cancel.
  • eliminate_dead_code (L107–118) drops nodes and constants nothing reads.

The passes do not yet fuse decomposed patterns. JAX and TensorFlow hand over layer norm, softmax and tanh-GELU as chains of elementwise ops, which is why the tiny transformer block exports to 76 nodes from JAX and 54 from TensorFlow, against 32 from PyTorch. Fusing those patterns at export is planned work (see {{ link('lowering', 'Lowering and fast CPU') }}).

The zoo

tools/rml_export/zoo/ defines each model once per framework (torch_zoo.py, jax_zoo.py, tf_zoo.py). All three load their parameters from weights(), which draws them from a NumPy generator seeded per model, so the three definitions compute the same function from identical weights (weights.py L1–7). Each model has a "tiny" size, committed as a test fixture, and a "bench" size, which is timed (L11–33).

Fixtures and golden tests

make_graph_fixtures.py exports every tiny zoo model from every framework (L60–74). For each one it draws a batch of 2 inputs, exports the graph and runs the framework, writes <framework>_<model>.json and .safetensors, evaluates the written graph with the NumPy reference ops and requires it to match the framework, and finally writes the framework's inputs and outputs to .golden.safetensors.

golden_test.cc closes the loop in C++ with no Python. It loads each fixture, runs it through rml's executor on the golden inputs, and requires every output element within 1e-5 of the framework's (L20–54). Its cases are every .json in the testdata directory, so a new fixture is tested without editing the test, and a second test fails if any framework and model pair is missing (L56–78).
