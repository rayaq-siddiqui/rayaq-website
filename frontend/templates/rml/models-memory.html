Models and memory

Which open-weight models rml targets, the arithmetic that decides whether each one fits a 16 GB Mac, and how far each model has actually got: config parsing, golden tests on real weights, or still planned.

In short: rml's budget is a 16 GB Apple Silicon Mac with the inference process under about 11 GB peak RSS, and docs/models.md works the numbers for each target from its config.json: weights at a given bits per weight, plus a KV cache, prefill scratch and runtime overhead. Llama 3.1 8B fits at Q8_0 (about 10.2 GB, tight) and Q4_K_M (about 6.6 GB, the performance target) but not bf16; Qwen3 8B is the second dense architecture; Qwen3-30B-A3B does not fit, so OLMoE-1B-7B proves the MoE path. In the code, ParameterCount reproduces the parameter counts and its tests pin them. Five real checkpoints, from SmolLM2-135M to OLMoE-1B-7B, pass golden tests; the 8B milestone models and every measurement of peak RSS are still planned.

The models page sits beside the rest of rml's planning documents: the milestone in progress.md L5–8 is that rml-chat loads Llama 3.1 8B Instruct at 4-bit by mmap, stays under about 11 GB peak RSS, matches the reference top-1 tokens and decodes within 1.5× of llama.cpp, and the README's goal says the same (README.md L8–10). How weights stay mapped is on {{ link('model-files', 'Model files') }}; the block formats behind "bits per weight" are on {{ link('quantization', 'Quantization') }}; the concepts are {{ ml('quantization', 'quantization') }} and {{ ml('kv-cache', 'the KV cache') }}.

The budget and the formula

The process gets about 11 GB so macOS, the window server and a browser keep about 5 GB. Weights are mmapped and only count toward RSS as pages are touched, but decode touches every weight on every token, so in steady state the whole file is resident: the document plans as if it all counts (models.md L3–6). The parameter count in code

ParameterCount(const ModelConfig&) is the same sum, counting a tied head once (config.cc L495–506): per layer, the Q, K, V and output projections, any q/k/v bias and QK-norm weights, three hidden × intermediate matrices per expert (one expert for a dense model) plus the router, and two norm vectors (four with Gemma 3's sandwich norms); then the final norm and the embedding, doubled when the head is untied. The consequences (L41–45): bf16 cannot be the runtime format, so full-precision checks on the 8B model either page through the mmap layer by layer or run Q8_0 against bf16 reference logits; Q8_0 fits with about 0.8 GB to spare and an int8 KV cache adds headroom; Q4_K_M is the main performance target. rml can run both quantized formats: DotActivationType pairs Q8_0 and Q4_0 weights with Q8_0 activations, and Q4_K, Q5_K and Q6_K (the mix inside a Q4_K_M file) with Q8_K (dot.cc L285–297).

Worked example: the KV cache

With the Llama 3.1 8B shape, one position in one layer stores kv_heads × head_dim = 8 × 128 = 1024 keys and as many values. At f16 and an 8192-token context: 

2 (K, V) × 32 layers × 8 kv_heads × 128 head_dim × 8192 tokens × 2 bytes
  = 1,073,741,824 bytes ≈ 1.07 GB

rml's KvCache holds exactly that per position and layer as a row of row_bytes() (kv_cache.h L55–56): 4096 bytes at f32, 2048 at f16. Its int8 mode is not quite half of f16, because each group of quant_group() channels (at most 32) carries one f32 scale, 1.125 bytes per entry (L13–18): a 1152-byte row here, so about 0.60 GB for 8K tokens where models.md L44 rounds the int8 cache to 0.54 GB by leaving the scales out. The cache grows a 16-token page at a time out of an arena reserved up front, and pages it never touches are never made resident. KvCache::Create defaults to f32 (L40–43), but rml-chat asks for f16 and a 4096-token context unless told otherwise (main.cc L48–49), which is 0.54 GB for this model. The layout is drawn on {{ link('decoder', 'The decoder', '#attention-kv-cache') }}.

Why the memory number is also the speed number

Decode is memory bound: each token reads every weight once. At Q4_K_M (about 4.9 GB a token) the ceiling is about 14 tok/s on an M1 (68 GB/s), 20 on an M2 or M3 (100 GB/s) and 24 on an M4 (120 GB/s), and achieved GB/s as a fraction of that is meant to be the headline benchmark (L47–49). That benchmark, beside llama.cpp on the same file, is planned (progress.md L71); see {{ link('kernels', 'Kernels', '#planned') }}.

Streaming experts from SSD through the page cache is rejected: which experts a token touches changes every token, so the resident set still grows toward the whole file and the OS would thrash (L83–85). OLMoE won out without special handling; its real-weight golden passes, and a Qwen1.5-MoE golden is listed only as a later step (progress.md L292).

Getting the weights

Weights live in a gitignored models/ directory and are never committed (AGENTS.md L40). tools/download_model.py fetches a Hugging Face checkpoint into models/<name> using only the standard library:

Argumentsrepo (owner/name), --revision (default main), --dest (default models/<name>)L49–55

Only safetensors are downloaded; GGUF files such as the README's llama-3.1-8b-q4_k_m.gguf are fetched by hand. CI uses the script for one model, SmolLM2-135M-Instruct at a pinned revision, cached between runs (ci.yml L48, L56–63).
