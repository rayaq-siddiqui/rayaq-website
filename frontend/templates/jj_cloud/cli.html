The custom jj binary

The cli crate builds a binary named jj. It is stock jj-cli 0.43.0 with two additions: the commit-cloud store factories, and one subcommand, jj cc init, which registers a repository on a server and creates a local workspace that points at it.

In short: main.rs is 47 lines. It hands CliRunner a set of store factories named commit_cloud and a cc subcommand. jj cc init runs jj-lib's ordinary workspace initialisation with the commit-cloud stores swapped in. After that, every other command is jj-cli's own: it finds commit_cloud in the repo's type files and reads and writes through gRPC without knowing it.

The index store, submodule store and working copy are jj-lib's defaults. Only commits, trees, files, operations, views and op heads live on the server.

Step by step

  1. Build UserSettings from StackedConfig::with_defaults() and a Signer from them (L37–42). This is jj's built-in default config only. The user's config files aren't read by this command, so the first operation and working-copy commit don't carry the user's name or settings.
  2. Define three initialiser closures (L44–67). The backend one calls CommitCloudBackend::init. The op store and op heads store ones call their load, because they have nothing to create.
  3. Call jj-lib's Workspace::init_with_factories with those closures and the default index, submodule and working-copy factories (L69–83). From here jj-lib drives:
    1. Create .jj/ (create_jj_dir). If it already exists, init fails with DestinationExists.
    2. ReadonlyRepo::init creates .jj/repo/store/ and runs the backend closure. It calls RegisterRepository, receives a new UUID, and writes store/config.toml with server_url and repo_id. jj-lib then writes store/type = commit_cloud.
    3. It creates op_store/ and op_heads/, runs their closures and writes their type files. Both find the config through the ../store/config.toml fallback (util.rs), which works only because the backend closure has already run. The op heads store ignores the root operation ID it is given, and nothing is written for it on the server. An empty repository already reports the root as its head.
    4. It creates the local index/ and submodule_store/, then loads the root operation and its view from the server.
    5. init_working_copy starts a transaction and checks out a new empty commit on top of the root. Committing the transaction writes the commit, the view and the operation "add workspace 'default'", then publishes it.
    6. The local working-copy state is written under .jj/working_copy/, and the workspace is recorded.
  4. Print "Initialized remote Commit Cloud repository" (L85).

Any error is turned into a user_error. If anything inside init_with_factories fails, jj-lib deletes the new .jj/ (L338–341). The repository it may already have registered on the server stays registered, and nothing ever unregisters it.

Commit, view and operation IDs are computed or accepted as described in object-ids. The op-heads lock taken before UpdateOpHeads is a no-op (L89–91).

Stock commands on commit-cloud stores

Once the workspace exists, jj describe, jj log, jj op log and the rest are jj-cli's code, unchanged (see {{ jj_link('cli', '/jj/cli') }}). Loading the workspace reads each type file under .jj/repo/ and looks the name up in the merged factories. For commit_cloud, each factory's load reads config.toml and makes no network call (repo.rs). From then on, every Backend, OpStore and OpHeadsStore call jj-lib makes becomes an RPC. The working copy and index stay local.

A command that changes the repository ends the same way init does: a transaction writes its new objects, then the view (write_view), then the operation (write_operation), then publishes with update_op_heads. So WriteView, WriteOperation and UpdateOpHeads close every write, in that order. A snapshot of a changed file adds WriteFile and WriteTree before the commit. The upstream tests exercise this with describe, log and op log (see testing). Commands that need Git or other backends' features aren't covered by anything upstream.

What the binary doesn't do

  • --create does nothing, and there is no way to attach a second workspace to an existing remote repository: cc init always registers a new one.
  • cc init uses jj's default config, not the user's.
  • A failed init can leave an orphan registration on the server.
  • Concurrent writers from two workspaces lose operations silently (client-op-store).
  • The binary is named jj, so installing it shadows a stock jj on the PATH.
