Commit Cloud architecture

A detailed, source-linked map of how jj-commit-cloud-poc works inside: a gRPC server that stores a jj repository's commits, trees, files, operations, views and op heads, the client-side jj-lib store implementations that talk to it, and the custom jj binary that ties them together.

Upstream calls this a proof of concept, and these pages say plainly what it doesn't do yet. For jj's own storage model (commits, operations, views and backends), see the jj architecture reference. That reference describes its own pinned jj version, which can differ from the jj-lib {{ upstream.jj_lib_version }} this project builds against.

The components

The custom jj binary

The cli crate builds a binary named jj. Its main is jj-cli's own CliRunner with two additions: store factories that know the commit_cloud backend, op store and op heads store, and a cc subcommand whose only child is init. The factories are built from StoreFactories::empty() (source), but jj-cli merges them into its defaults (source), so this binary opens ordinary jj repositories as well as commit-cloud ones. jj cc init --server <url> registers a new repository on the server and initialises a local workspace whose stores all point at it. The --create flag is accepted and ignored. See the custom jj binary.

cc-lib, the client stores

cc-lib implements three jj-lib traits over gRPC: Backend (commits, trees and files), OpStore (operations and views) and OpHeadsStore. Each loads server_url and repo_id from .jj/repo/store/config.toml. Every trait method calls run_async, which spawns an OS thread, builds a single-threaded tokio runtime on it, connects a new tonic client, makes one RPC and joins the thread. See the client Backend and the client OpStore and OpHeadsStore.

cc-common, the wire

cc-common compiles backend.proto and op_store.proto with tonic-build, and holds the shared ID lengths and root IDs. See every schema.

jj-cc-server

The server crate (jj-commit-cloud-server, binary jj-cc-server) listens on --host (default 127.0.0.1) and --port (default 8080), serves both services plus the standard gRPC health service, and keeps every repository in one shared Store (source). It computes the ID of every object it is sent, using Git's object format for commits, trees and files. See the server, storage engines and object IDs.

Status and limitations

Upstream calls this a proof of concept, "beginning life as an intern project", with "no guarantee of completeness, performance, or API stability". At the pinned commit:

  • Storage is in memory only. Restarting the server loses every repository. --store-type sqlite prints "SQLite storage backend is not yet implemented" and exits (source).
  • No symlinks, copies or submodules. The symlink RPCs exist but are unimplemented on both sides, and copy tracking and submodules return Unsupported on the client.
  • Files travel whole. WriteFile is a single message, so large files can hit gRPC's message size limit (a TODO in both the schema and the server).
  • The custom binary only opens commit-cloud repos, and jj cc init --create is ignored.
  • Signatures, tags and Git refs don't round-trip. See what the wire doesn't carry.
  • No authentication. Any client that knows a repository's UUID can read and write it, and the server takes a client-supplied commit ID without checking it.
