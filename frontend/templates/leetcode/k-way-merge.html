K-way merge

Merging two sorted lists is a two-finger walk. Merging k of them is the same walk with k fingers, and the only new question is which finger points at the smallest value right now. A min-heap answers that in O(log k), so the whole merge costs O(n log k) for n items, and the heap never holds more than k entries.

Problem

You have k sequences that are each already sorted, and you want one sorted sequence, or just the first few items of it, or the best item that touches every sequence. The sequences may be linked lists, arrays, or streams that you can only read forward. The shape is the same in all of them: several ordered sources, and a rule that always asks for "the smallest next item across all of them".

SignalPatternWhy
"Merge k sorted lists or arrays"Min-heap of one head per sourceThe next output is the smallest head, and the heap finds it in O(log k).
"Each user has a time-ordered list; show the newest across users"Heap of the latest item per sourceA news feed is a k-way merge that stops after ten items.
"Smallest range containing one item from every list"Heap of heads plus a running maximumThe window is the heap minimum to the maximum; advance the minimum to shrink or move it.
"The k-th smallest in sorted rows or a sorted matrix"Heap of row heads, pop k timesEach pop is the next smallest overall, so the k-th pop is the answer.
"Merge two sorted lists"Two pointersWith k = 2 the heap is overhead; compare the two heads directly.
"Sources are unsorted"Sort first, or a different patternThe heap trick relies on each source being ordered, so the head is its minimum.

Intuition

Picture a card game where k players each hold a sorted hand, face up, smallest on the left. The dealer wants all the cards in one sorted pile. At every step, the next card for the pile must be the smallest card overall. That card is certainly the leftmost card of some hand, since each hand is sorted, so only the k leftmost cards compete. The dealer takes the smallest of those k, and the owner's next card steps up to take its place.

Finding the smallest of k cards by scanning costs k comparisons per output card, so O(nk) in all. A min-heap holding just those k front cards finds the smallest in O(1) and repairs itself in O(log k) after one is replaced. That is the entire idea: a heap is a scoreboard for the k fingers.

Green boxes are the heads currently in the heap. Everything to their right is waiting behind a head in its own list. The diagram scrolls sideways on a narrow screen.

Mechanics

The invariant

The heap holds exactly one entry for each source that still has items: its first unread item. Each entry also carries the source index and position, so you know where to read next, and so that ties compare on integers and never on list nodes (which cannot be ordered). Every value already written to the output is no larger than every value that is still unread. Why: any unread value is either in the heap, in which case it is at least the heap minimum that was just removed, or sits behind a head in a sorted list and is at least that head. So removing the minimum head and appending it is always the correct next output, and replacing it with its successor restores the one-entry-per-source rule.

Why O(n log k)

Each of the n items is pushed once and popped once, and the heap never has more than k entries, so each heap operation is O(log k). The setup is O(k). Memory is O(k) beyond the output. Compare folding the lists in one at a time: merging a running result of growing length with each new list re-touches early items again and again, which is O(nk) for equal lists. Merging pairs in rounds like a tournament costs n per round for ⌈log₂ k⌉ rounds, which is the same O(n log k) as the heap.

Moves of items for {{ sizes | length }} lists of {{ sizes[0] }}. Folding in one by one grows with the number of lists times the total; the heap and the round-by-round merge both grow with the total times log of the number of lists.

Beyond plain merging

The heap does not need to run to completion. A news feed pops only the first ten entries. The k-th smallest in a sorted matrix pops k times. In smallest range, you also track the largest head: the heap root and that maximum bound a window that touches every list. Moving the minimum forward is the only move that can shrink the window, because the maximum cannot go down without losing a list; and as soon as one list runs out there is no window left, so the search ends.

Implementation

import heapq


class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next


def merge_k_lists(lists):
    heap = []
    for i, node in enumerate(lists):
        if node:
            heap.append((node.val, i, node))   # i breaks ties so nodes are never compared
    heapq.heapify(heap)
    dummy = tail = ListNode()
    while heap:
        _, i, node = heapq.heappop(heap)
        tail.next = node
        tail = node
        if node.next:
            heapq.heappush(heap, (node.next.val, i, node.next))
    return dummy.next


def merge_arrays(arrays):
    heap = [(a[0], i, 0) for i, a in enumerate(arrays) if a]
    heapq.heapify(heap)
    out = []
    while heap:
        value, i, j = heapq.heappop(heap)
        out.append(value)
        if j + 1 < len(arrays[i]):
            heapq.heappush(heap, (arrays[i][j + 1], i, j + 1))
    return out


def smallest_range(arrays):
    heap = [(a[0], i, 0) for i, a in enumerate(arrays)]
    heapq.heapify(heap)
    high = max(h[0] for h in heap)
    best = (heap[0][0], high)
    while True:
        low, i, j = heap[0]
        if high - low < best[1] - best[0]:
            best = (low, high)
        if j + 1 == len(arrays[i]):
            return list(best)
        nxt = arrays[i][j + 1]
        heapq.heapreplace(heap, (nxt, i, j + 1))
        high = max(high, nxt)

The standard library already has heapq.merge(*iterables), a lazy k-way merge, which is good for real code and a fair way to check your own. The tie-break index i is the part people forget: without it, equal values make Python compare the nodes themselves and raise a TypeError.

Variations and edge cases

  • Divide and conquer. Merge lists in pairs, then pairs of pairs. It matches the heap's O(n log k) time, needs no heap and reuses a plain two-list merge, which is handy for linked lists.
  • News feed. Each user's recent items are a sorted source ordered newest first (so use negated timestamps or a max-heap). Stop after ten pops, and push the next item of the user you just popped from.
  • Sorted matrix. Treat each row as a list and push only the first column at the start, or treat each column as a list and expand lazily; pop k times for the k-th smallest.
  • Lazy output. A generator that yields after each pop never builds the full result, so the merge can run over streams larger than memory.
  • Edge cases: k equal to 0, lists that are empty or None (skip them when seeding the heap), a single list, duplicate values across lists (the index tie-break keeps them in a stable order), and one very long list next to many tiny ones.

Complexity and tradeoffs

  • Time: O(n log k) for n total items in k sources, plus O(k) to seed the heap.
  • Space: O(k) for the heap, and O(1) extra for linked lists if you relink nodes instead of copying; the output array costs O(n) when you need it.
  • Baseline. Concatenate and sort: O(n log n), a one-liner, and often fast in practice because Python's sort exploits existing runs. It ignores the sorted structure, so it is a fair first answer but not the intended one.
  • When it fails. If k is 2, a plain two-pointer merge is simpler and faster. If sources are not sorted, the head is not their minimum and the heap gives wrong answers. If you only need the k smallest overall and the sources are huge, popping k times keeps the cost at O((k + m) log m) for m sources, much less than n.

Check yourself

Why does the heap hold at most one entry per list?

Only the first unread item of a sorted list can be the next overall minimum, since everything behind it is at least as large. In the example the heap peaked at {{ trace.peak }} entries for {{ lists | length }} lists, however long the lists were.

Why put the list index in the heap tuple?

When two values are equal, Python compares the next tuple field. Without a comparable tie-break it would compare list nodes, which cannot be ordered, and raise a TypeError. The index also tells you which source to read the successor from.

Why is merging the lists one after another slower than the heap?

The running result grows, and every merge touches all of it again. For {{ sizes | length }} lists of {{ sizes[0] }} items that is {{ cost.sequential }} moves, against {{ cost.heap }} for the heap, and the gap widens as k grows.

In the smallest-range search, why advance only the list holding the minimum?

The window needs one item from every list, so its low end is the smallest head. Raising any other head cannot shrink the window, because the minimum stays the same, while raising the minimum can. When that list has no next item, every later window would miss it, so the search stops, as it did after {{ rng.steps | length }} windows here.
