Hash maps and sets

A hash table answers "have I seen this before?" and "what did I store for this key?" in constant time on average. This page explains why that is possible, shows the three shapes almost every hash problem takes (a seen-set, a complement map and a group-by-key map), and ends with how to build a hash table yourself, because interviewers ask.

Problem

Brute force on arrays is mostly a story of re-scanning: for each element, look through the rest of the input for a partner, a duplicate or a match. That costs O(n²). A hash table turns the inner scan into a single lookup, so you trade O(n) extra memory for a drop from O(n²) to O(n). Whenever you catch yourself writing "for each x, find a y such that…", ask whether y can be computed from x and looked up instead.

Intuition

Think of a coat check. You hand over a coat and get a numbered ticket; later the ticket takes you straight to the right hook instead of a search along the whole rack. A hash table makes the ticket from the key itself: a hash function turns the key into a number, and that number picks a bucket. Looking a key up repeats the same calculation and goes straight to the same bucket.

The pattern comes from reading a problem backwards. "Find a pair that sums to 9" sounds like a search over pairs. But standing on one number, say 7, the partner you need is already determined: it is 2. So the problem is not "search for a pair" but "for each number, has its one possible partner already gone by?" Remembering what has gone by is exactly what a hash table is for.

The map is a memory of the past; each step asks it one question.

Mechanics

How a hash table works

A hash table keeps an array of buckets. To store a key, compute hash(key) mod size and put the key in that bucket. To look it up, compute the same index and look only in that bucket. Two different keys can land in the same bucket (a collision); the simplest fix, separate chaining, keeps a short list in each bucket and scans it. Python's built-in dict and set use open addressing instead (probing for another free slot in the same array) but the consequences are the same.

Collisions lengthen one chain; resizing the table keeps chains short.

The invariants

Hash tables stay fast because of two promises. First, equal keys always hash equally, so a key can only ever be in one bucket. Second, the table is kept from getting too full: when the load factor (keys divided by buckets) passes a limit, the table doubles and every key is re-hashed. With a good hash function the expected chain length stays near the load factor, so lookup, insert and delete are O(1) on average, and doubling makes insert O(1) amortized.

For the solving patterns the invariant is about the map's contents, not its internals: before processing element i, the structure answers correctly for elements 0 to i − 1. Complement maps are correct because every valid pair (a, b) with a before b is found when b is processed, since a is already stored. Look up first, then insert, so an element never pairs with itself.

What can be a key

A key must be hashable: immutable, with a stable hash. Ints, strings, bytes and tuples of those work; lists, sets and dicts do not. To use a list or a grid state as a key, convert it: tuple(row), "".join(chars), or frozenset(items). Floats work but suffer from rounding, so avoid them as keys.

Implementation

def has_duplicate(nums):                       # seen-set
    seen = set()
    for x in nums:
        if x in seen:
            return True
        seen.add(x)
    return False


def two_sum(nums, target):                     # complement map: value -> index
    seen = {}
    for i, x in enumerate(nums):
        if target - x in seen:                 # look up before inserting
            return [seen[target - x], i]
        seen[x] = i
    return []


from collections import defaultdict

def group_by_key(items, key):                  # canonical key -> group
    groups = defaultdict(list)
    for item in items:
        groups[key(item)].append(item)
    return list(groups.values())


def longest_consecutive(nums):                 # set instead of sorting
    members, best = set(nums), 0
    for x in members:
        if x - 1 not in members:               # x starts a run
            length = 1
            while x + length in members:
                length += 1
            best = max(best, length)
    return best


class MyHashSet:                               # separate chaining, fixed bucket count
    def __init__(self, size=1009):
        self.buckets = [[] for _ in range(size)]

    def _chain(self, key):
        return self.buckets[hash(key) % len(self.buckets)]

    def add(self, key):
        chain = self._chain(key)
        if key not in chain:
            chain.append(key)

    def remove(self, key):
        chain = self._chain(key)
        if key in chain:
            chain.remove(key)

    def contains(self, key):
        return key in self._chain(key)

Variations and edge cases

  • Map instead of set. MyHashMap stores (key, value) pairs in the chain and, on a repeated key, replaces the existing pair rather than appending a second one.
  • Random access with deletion. To pick a random element in O(1), keep the values in a list plus a dict from value to list index. Delete by overwriting the slot with the last element, updating that element's index, and popping the tail.
  • One set per rule. For Sudoku, keep a set for each row, each column and each 3 × 3 box (index (r // 3, c // 3)) and reject a digit that is already in any of them.
  • Rank maps. For custom orderings such as an alien alphabet, map each symbol to its position and compare words by those ranks.
  • Edge cases: inserting before looking up (an element pairs with itself), duplicate values in complement problems (target 6 with [3, 3] works only if you look up first), hashing a mutable list, relying on dict order for answers, and a prefix such as "abc" being a prefix of another key in custom tables.

Complexity and tradeoffs

  • Time is O(n) for one pass with O(1) average operations. The worst case for a single operation is O(n) if every key collides, which a sane hash function makes vanishingly unlikely; say "O(1) average" rather than "O(1)".
  • Space is O(n) for the table, the price of avoiding rescans.
  • Baselines. Brute force is O(n²) time and O(1) space. Sorting first is O(n log n) time and often O(1) extra space, and can be the better answer when memory is tight or when two pointers apply afterwards.
  • When it fails. A hash table has no order: it cannot give you the next larger key or the minimum cheaply. For ordered queries use sorting with binary search, a heap, or a balanced tree. Hashing also adds a constant factor; for tiny alphabets an array of counts is faster than a dict.
  • Hash flooding. Adversarial input can force collisions. Python randomizes string hashes per process for this reason; it is not a concern in interviews.

Check yourself

In Two Sum, why do we look up the complement before inserting the current number?

Otherwise a number could pair with itself: with target 8 and the number 4 at index 0, inserting first would "find" the 4 we just stored. Looking up first only matches earlier elements.

Why does Longest Consecutive Sequence only start counting at numbers whose predecessor is missing?

Each run then has exactly one start, so every number is walked once and the total is O(n). On the example that was {{ runs.lookups }} lookups for {{ runs.unique }} distinct numbers.

Your hash set has 7 buckets and ends up with one chain of {{ buckets | map("length") | max }} keys. What went wrong and how do real tables avoid it?

Too many keys for too few buckets (or a poor hash function). Real tables track the load factor and resize, doubling the bucket count and re-hashing so chains stay short.

Why can't a list be a dict key, and what do you use instead?

Lists are mutable, so their hash could change while they sit in a bucket and the key would be lost. Convert to a tuple (or a string, or a frozenset) first.
