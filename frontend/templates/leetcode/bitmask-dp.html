Bitmask DP

Some problems ask you to pick an order or an assignment for a small set of items, say up to 20, and trying every order costs n!, which is hopeless past about 11. Bitmask DP notices that the future usually depends only on which items are already used, not on the order they were used in. So it stores one answer per subset, writes each subset as the bits of an integer, and replaces n! orders with 2n sets. That turns 20 items from 2.4 × 1018 orders into about a million states. It is rare in interviews and no list problem needs it, but when the input is tiny and the obvious search is factorial, it is the tool to reach for.

Problem

The questions look like search problems: give each worker one job at the lowest total cost, visit every city once on the shortest tour, split numbers into k groups of equal sum, cover a list of skills with the smallest team. Each choice uses up an item, and later choices are only limited by what is used up. The constraint that gives it away is a tiny n, usually 12 to 20, which is too small for a polynomial algorithm to be the point and too big for n! to finish.

Intuition

Three workers, {{ workers[0] }}, {{ workers[1] }} and {{ workers[2] }}, must each take one of jobs 0, 1 and 2. Trying every order means 3! = 6 assignments, and for 20 workers, 20! of them. Look at what those orders have in common. Once {{ workers[0] }} and {{ workers[1] }} have taken jobs 0 and 1, between them, {{ workers[2] }} must take job 2, whichever of the two orders put them there. Both partial assignments face the same future, so only the cheaper one can be part of the best answer. Keep that one and throw the other away.

That is the whole idea: for every set of jobs already given out, remember only the cheapest way to give them out. A set of jobs is a row of yes/no answers, and a row of yes/no answers is an integer written in binary. Set {0, 1} is 011 = 3, set {0, 2} is 101 = 5. The DP table is then a plain list indexed by those integers, and adding job j to a set is one bit operation.

Greedy reasoning does not survive this. If each worker in turn takes their cheapest free job, {{ workers[0] }} grabs job {{ assign.greedy[0] }} for {{ cost[0][assign.greedy[0]] }}, and the total is {{ assign.greedy_cost }}. The best total is {{ assign.best }}, because the DP also keeps the partial assignments that look worse early on.

Green masks lie on the cheapest path from 000 to 111, and the labels give the cost each step adds. Every mask keeps one number, however many paths reach it.

Mechanics

The bit idioms

With n items numbered 0 to n − 1, the set is an integer whose bit j is 1 when item j is in it. Test membership with mask >> j & 1, add an item with mask | 1 << j, remove one with mask & ~(1 << j), and count members with mask.bit_count() (Python 3.10+; bin(mask).count("1") before that). The empty set is 0 and the full set is (1 << n) − 1. These are the tricks from the bit manipulation page, used as a data structure.

State and transition

For the assignment problem, dp[mask] is the lowest cost of giving the jobs in mask to the first popcount(mask) workers. Worker i = popcount(mask) is next, and for each free job j, dp[mask | 1 << j] may improve to dp[mask] + cost[i][j]. Start from dp[0] = 0 and read the answer at the full mask. Adding a bit always makes the integer bigger, so looping over masks in increasing numeric order handles every mask after all the masks it is built from.

Why it is correct. Take any best complete assignment and stop it after k workers; the jobs they hold form some mask. If a cheaper way to fill that same mask existed, swapping it in would leave the remaining workers exactly the same jobs to choose from, and give a cheaper complete assignment, which is impossible. So every prefix of a best answer is a best answer for its own mask, and the DP, which keeps the best answer for every mask, cannot lose it. The argument only works because the rest of the problem depends on the set and nothing else. That is the question to ask before using this pattern: is the set enough to describe the future?

When the set is not enough

On a tour, the next leg's cost depends on where you are standing, so the set of visited cities is not enough. Add the last city to the state: dp[mask][last] is the shortest path that starts at city 0, visits exactly the cities in mask and ends at last. It extends to dp[mask | 1 << c][c] through dist[last][c]. This is the Held–Karp algorithm (Bellman found it the same year), and it is still the best known exact method for the general travelling salesman problem in the worst case. A tour is a cycle, so its start can be fixed at city 0 without losing any tour, which saves a factor of n.

Implementation

def min_assignment_cost(cost):
    n = len(cost)
    dp = [math.inf] * (1 << n)
    dp[0] = 0
    for mask in range(1 << n):
        if dp[mask] == math.inf:
            continue
        worker = mask.bit_count()
        if worker == n:
            continue
        for job in range(n):
            if not mask >> job & 1:
                bigger = mask | 1 << job
                dp[bigger] = min(dp[bigger], dp[mask] + cost[worker][job])
    return dp[(1 << n) - 1]

Variations and edge cases

Top-down. The same recurrence with a cache is often quicker to write, and visits only the masks it needs:

from functools import cache

def min_assignment_cost(cost):
    n = len(cost)

    @cache
    def best(mask):
        worker = mask.bit_count()
        if worker == n:
            return 0
        return min(cost[worker][job] + best(mask | 1 << job)
                   for job in range(n) if not mask >> job & 1)

    return best(0)

Held–Karp. Two dimensions, the set and the last city:

def shortest_tour(dist):
    n = len(dist)
    dp = [[math.inf] * n for _ in range(1 << n)]
    dp[1][0] = 0
    for mask in range(1, 1 << n, 2):
        for last in range(n):
            here = dp[mask][last]
            if here == math.inf:
                continue
            for city in range(1, n):
                if not mask >> city & 1:
                    bigger = mask | 1 << city
                    dp[bigger][city] = min(dp[bigger][city], here + dist[last][city])
    full = (1 << n) - 1
    return min(dp[full][last] + dist[last][0] for last in range(1, n))

Groups of equal sum. Fill groups one at a time; fill[mask] is how full the open group is after using the items in mask, and an item may only join if it fits. The answer is yes when the full mask is reachable:

def can_partition_k(nums, k):
    total = sum(nums)
    if total % k:
        return False
    side, n = total // k, len(nums)
    fill = [-1] * (1 << n)
    fill[0] = 0
    for mask in range(1 << n):
        if fill[mask] < 0:
            continue
        for i in range(n):
            if not mask >> i & 1 and fill[mask] + nums[i] <= side:
                fill[mask | 1 << i] = (fill[mask] + nums[i]) % side
    return fill[-1] == 0

Every submask of a mask. Some recurrences split a set into two parts. The step sub = (sub − 1) & mask walks through every submask from largest to 0, skipping the integers that are not submasks.   • Unreachable states. Start every entry at infinity (or −1) and skip it when extending. Otherwise an unreachable state passes its default value along as if it were real.
  • Operator precedence. In Python, << and >> bind tighter than & and |, so mask & 1 << j means what it says. Write the brackets anyway if they help you read it.
  • Memory. dp[mask][last] with n = 20 is about 21 million entries. In Python that is too slow and too big; keep n at 16 or so for two dimensions, or store each row as an array.
  • Fixing a start. For a cycle, fixing city 0 is safe. For a path that may start anywhere, seed dp[1 << i][i] = 0 for every i instead.

Complexity and tradeoffs

The assignment DP has 2n masks and tries n jobs from each: O(n · 2n) time and O(2n) space. Held–Karp has n · 2n states and tries n next cities from each: O(n2 · 2n) time and O(n · 2n) space. The brute-force baseline tries every order, n!:

  • Where the limit sits. At about 107 to 108 simple steps per second, n · 2n is comfortable up to n = 20, n2 2n up to about 16, and 3n up to about 15. Constraints that stop just there are a hint.
  • Against backtracking. For yes/no questions like equal-sum groups, backtracking with good pruning often finishes much faster in practice; the DP's advantage is a guaranteed bound.
  • Against polynomial algorithms. Assignment is solvable in O(n3) by the Hungarian method, so for large n bitmask DP is the wrong tool. Travelling salesman is NP-hard, so nothing polynomial is known; for large n, real solvers use branch and bound or heuristics.
  • When the set is not enough. If the future depends on the order beyond a last element or two, the state grows past 2n · n and the pattern no longer pays.

Connections

{% include "leetcode/_connections.html" %}

Bitmask DP is DP whose state happens to be a set, stored through bit manipulation. It is what permutation backtracking becomes once you notice that many orders reach the same set: the cache merges them. Its yes/no cousins, Matchsticks to Square and Partition to K Equal Sum Subsets, live on the constraint backtracking page, where pruning usually beats the DP in practice. BFS over (node, mask) pairs is graph traversal on a state graph, and visiting every node once is the Hamiltonian cousin of the Eulerian path, which uses every edge once and is far easier.

Check yourself

The assignment state is only the mask. How does the DP know which worker is next?

Workers are handled in a fixed order, {{ workers[0] }} then {{ workers[1] }} then {{ workers[2] }}, and each takes exactly one job, so a mask with k bits set means the first k workers are done. The next worker is popcount(mask), which is why it does not need its own dimension.

Why does the greedy order cost {{ assign.greedy_cost }} when the best is {{ assign.best }}?

{{ workers[0] }} takes job {{ assign.greedy[0] }} for {{ cost[0][assign.greedy[0]] }}, which looks cheapest, but that pushes the others onto jobs {{ assign.greedy[1:] | join(" and ") }} for {{ assign.greedy_cost - cost[0][assign.greedy[0]] }} more. The DP keeps the best value for every set, including sets that look worse after one step, so a cheaper finish is never thrown away.

Why can Held–Karp always start at city 0, and why does it need the last city in its state?

A tour is a cycle, so any tour can be read starting from city 0 without changing its length. The last city matters because the next leg's length depends on it: two paths through the same cities but ending in different places have different futures.

Looping over every mask and then every submask of it: why 3n steps rather than 4n?

Each (mask, submask) pair gives every item one of three roles: not in the mask, in the mask but not the submask, or in both. An item cannot be in the submask without being in the mask, so the fourth combination never happens, and there are exactly 3n pairs.
