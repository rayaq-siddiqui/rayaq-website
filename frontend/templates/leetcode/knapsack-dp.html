Knapsack DP

Knapsack DP adds a second thing to remember besides "how many items so far": a budget, a target sum or a length. The state is a number between 0 and the target, and each item either uses part of it or does not. Coin change, partition, target sum and word break are all this one table with different combining rules.

Problem

You have a collection of items (numbers, coins, dictionary words) and a target (a sum, an amount, a string length). The question is whether the target is reachable, how cheaply, or in how many ways. Trying every subset is exponential. The way out is to notice that only the total so far matters, not which items made it, so you track a table indexed by totals from 0 to the target.

Intuition

Imagine a row of boxes labelled 0 up to the target, each one lit if that exact total is possible. Start with only box 0 lit (the empty selection). Each new number lets you move from any lit box up by that number, lighting the box you land on. When the numbers are used up, you just check whether the target box is lit. You never need to remember which numbers lit a box, because anything that completes the sum from there looks the same.

The only real choice is whether an item may be used once or many times. If each number can be used once, you process numbers one at a time and each can only act on the boxes that were lit before it. If a coin can be reused, the new box it lights may immediately be used by the same coin again. That single difference decides the direction of the inner loop, and it is where most knapsack bugs live.

Each row is the set of lit boxes after one more number. Green boxes are reachable; the blue box is the target. The diagram scrolls sideways on a narrow screen.

Mechanics

0/1: each item once

Let can[s] say whether sum s is reachable. For each number v, set can[s] = can[s] or can[s - v]. To use v at most once, the right-hand side must read the table as it was before v. Updating a one-dimensional array from the high end down to v guarantees that: when you write can[s], the entry can[s - v] is lower and has not been updated yet. Going upward would let v feed itself and turn the problem into the unbounded one.

Unbounded: items reused

For coins with unlimited supply, fewest[a] = 1 + min(fewest[a - c]) over every coin c not above a, with fewest[0] = 0. The last coin used could be any denomination, so the table takes the best. Here an upward inner loop is correct, because fewest[a - c] may already include another copy of c.

Counting: the loop order decides what is counted

For the number of ways, the update is a sum: ways[a] += ways[a - c]. With denominations in the outer loop and amounts inside, each coin is introduced once and the order inside a selection is fixed, so {{ ways_coins | join(", ") }} making 7 counts {{ ways.combinations[7] }} combinations. Swap the loops (amounts outside, coins inside) and every amount tries every last coin, so 1+2+... and 2+1+... count separately: {{ ways.orders[7] }} ordered sequences for the same coins.

Strings: the table runs over lengths

For splitting a string into dictionary words, reach[i] is true when the first i characters split. It holds if some earlier position j has reach[j] true and text[j:i] is a word. The "items" are words and the "amount" is the length, which is why the problem is a knapsack in disguise.

Invariant

After processing the first k items, the table holds the exact answer for every total using only those k items (and, for the 0/1 case, each at most once). Induction on k: an optimal selection either leaves item k out, covered by the previous table, or includes it, in which case the rest is an optimal selection of the first k - 1 items for the smaller total. The table is a bounded set of such sub-answers, which is what makes the cost pseudo-polynomial.

Implementation

def can_partition(nums):
    total = sum(nums)
    if total % 2:
        return False
    target = total // 2
    can = [True] + [False] * target
    for value in nums:
        for s in range(target, value - 1, -1):    # downward: each number once
            can[s] = can[s] or can[s - value]
    return can[target]


def coin_change(coins, amount):
    inf = amount + 1
    fewest = [0] + [inf] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                fewest[a] = min(fewest[a], fewest[a - c] + 1)
    return -1 if fewest[amount] == inf else fewest[amount]


def word_break(s, words):
    vocabulary = set(words)
    reach = [True] + [False] * len(s)
    for end in range(1, len(s) + 1):
        reach[end] = any(reach[start] and s[start:end] in vocabulary
                         for start in range(end))
    return reach[-1]

Variations and edge cases

def coin_change_ways(coins, amount):
    ways = [1] + [0] * amount
    for c in coins:                       # coins outside: combinations
        for a in range(c, amount + 1):    # upward: unlimited copies
            ways[a] += ways[a - c]
    return ways[amount]


def combination_sum_ordered(nums, target):
    ways = [1] + [0] * target
    for a in range(1, target + 1):        # amounts outside: ordered
        for v in nums:
            if v <= a:
                ways[a] += ways[a - v]
    return ways[target]


def find_target_sum_ways(nums, target):
    total = sum(nums)
    if abs(target) > total or (total + target) % 2:
        return 0
    goal = (total + target) // 2
    ways = [1] + [0] * goal
    for v in nums:
        for s in range(goal, v - 1, -1):
            ways[s] += ways[s - v]
    return ways[goal]


def can_partition_bits(nums):
    total = sum(nums)
    if total % 2:
        return False
    bits = 1
    for v in nums:
        bits |= bits << v                # every reachable sum in one integer
    return bits >> (total // 2) & 1 == 1
  • Direction of the inner loop. Downward for use-once, upward for reuse. Reversing either silently solves a different problem.
  • Unreachable amounts. Fill with a sentinel larger than any real answer (amount + 1), not float("inf") arithmetic you forget to test, and map it to -1 at the end.
  • Zero amount. There is exactly one way (take nothing) and zero coins are needed; seed [0] or [1] accordingly.
  • Zeros in the number list. A zero doubles the count of target-sum assignments, since + 0 and - 0 are both valid. The table handles this only if the inner loop reaches 0, so check it.
  • Negative targets. Take the absolute value; the signs mirror.
  • Words longer than the string. Skip them, or cap the lookback to the longest word, for a faster word break.

Complexity and tradeoffs

  • Time: O(n × T) for n items and target T. Word break is O(L × W) with a set of words and a lookback limited to the longest word, otherwise O(L2) substring checks.
  • Space: O(T) with a single array; the two-dimensional version (items by totals) is O(n × T) and only needed to recover which items were used.
  • Pseudo-polynomial. T is a value, not an input length. If the target is a billion, the table is unusable and the problem is NP-hard in general. Interview constraints keep T small on purpose.
  • Baseline. Trying all subsets costs 2n. Meet-in-the-middle halves the exponent when n is about 40 and T is huge.
  • When it fails. Greedy works only for special denominations (like US coins), so use the table when in doubt. If the items have two budgets (weight and volume), the table gains a dimension. If you need the items and not just the count, keep the table and walk back, or keep parent pointers.

Knapsack is linear DP with a second axis. The same take-or-skip structure appears in subsets and permutations, where backtracking enumerates what the table counts. Word Break II is the enumeration partner of Word Break: the table prunes, and a backtracking pass lists the splits. Two-string DP and grid DP use the same idea with two indices instead of an item index and a total.

Check yourself

Why does the 0/1 knapsack loop run the totals from high to low?

So that can[s - v] still reflects the table before this number was added. Going upward would let the same number be reused in one pass. In the example, 15 is reached by {{ items | join(", ") }} with each number at most once.

Why is greedy wrong for coin change?

Taking the largest coin first can leave a remainder that needs many small ones. For {{ coins | join(", ") }} and 13, greedy uses {{ greedy | length }} coins but 4 + 4 + 5 uses {{ change.answer }}.

How do you count combinations rather than ordered sequences?

Put the coins in the outer loop and the amounts inside, so each denomination is introduced once. For {{ ways_coins | join(", ") }} and 7 that gives {{ ways.combinations[7] }}; swapping the loops gives {{ ways.orders[7] }}.

How does Target Sum become a subset count?

If P is the sum of numbers given a plus and N the sum of those given a minus, P + N is the total and P - N is the target, so P = (total + target) / 2. For the example that is {{ tsum.subset_target }}, and {{ tsum.answer }} subsets reach it.
