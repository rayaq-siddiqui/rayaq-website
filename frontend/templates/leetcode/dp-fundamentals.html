Dynamic programming fundamentals

Dynamic programming is recursion that refuses to repeat itself. When a problem splits into smaller versions of itself and those versions overlap, you solve each distinct one once and reuse the answer. The whole craft is choosing the right "state", the small description that fully captures a subproblem.

Problem

Plain recursion on some problems takes exponential time, not because the problem is hard but because the same sub-question is asked again and again. Counting ways, finding a best total or deciding whether something is possible, where every choice leaves a smaller problem of the same kind, fits this shape. Dynamic programming (DP) removes the repetition, turning exponential work into a number of steps proportional to the number of distinct sub-questions.

Intuition

Take the Fibonacci numbers, where each is the sum of the two before it. Written as plain recursion, fib(k) calls fib(k - 1) and fib(k - 2). Computing fib({{ n }}) makes {{ total_calls }} calls, yet only {{ n + 1 }} different arguments exist: fib(1) alone is computed {{ tally[1] }} times. For fib(30) the same recursion makes over two and a half million calls ({{ 2 * big[31] - 1 }}), still only 31 different questions.

Two ideas fix it, and every DP solution uses one of them. Memoization keeps the recursion and adds a cache: before computing a state, check whether you already have it. Tabulation drops the recursion and fills a table of answers in an order where everything a cell needs is already filled. They compute the same values.

Mechanics

The recipe

  1. State. What few numbers pin down a subproblem? (An index, a remaining amount, a pair of positions.) If two different histories lead to the same numbers and the future is identical, they are the same state.
  2. Meaning. Say in one sentence what dp[state] stores, for instance "the cheapest cost to finish from here". Most wrong DPs fail here, not in the code.
  3. Transition. Express dp[state] using states that are smaller. Try every choice available at this state and combine the results with min, max or a sum.
  4. Base cases. The states with no smaller state: the empty input, the last cell.
  5. Order. Fill states so that each one's dependencies come first. Recursion with a cache handles this for you; a table needs it worked out.
  6. Answer. Which state, or which combination of states, is the question?

Top-down and bottom-up

Top-down is the brute-force recursion with @functools.cache. It computes only the states reachable from the question, and it is the easy way to get a correct solution first. Bottom-up is a loop over a table. It avoids recursion depth limits and call overhead, and lets you see when old rows can be thrown away. In Python, both are accepted; start with top-down if the order of filling is unclear.

Why it is correct

The method relies on optimal substructure: the best answer for a state is built from best answers to smaller states, because what happens after a choice depends only on the state it leads to, not on how you got there. If the future depended on the history, the history would belong in the state. The running time is then the number of states times the work per state, since each state is solved exactly once.

Why not just be greedy?

A greedy rule commits to the locally best choice and never looks back. That works only when you can prove it. DP is the safe default because it compares every choice, and its cost is the size of the state space. The triangle below is a case where greedy loses.

Implementation

from functools import cache

def fib(n):
    @cache
    def go(k):
        if k < 2:
            return k
        return go(k - 1) + go(k - 2)
    return go(n)


def min_triangle_path(triangle):
    best = list(triangle[-1])            # bottom row
    for row in reversed(triangle[:-1]):
        best = [row[j] + min(best[j], best[j + 1]) for j in range(len(row))]
    return best[0]

The triangle solution keeps only one row of answers, since each row needs just the one below it. That is the usual space trim for DP: keep as many previous rows as the transition reads.

Variations and edge cases

def fib_iter(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a
  • Rolling variables. If dp[i] reads only the previous one or two entries, keep two variables instead of an array (as in fib_iter).
  • Reconstruction. To print the choice, not just its value, keep the table and walk it forward, or store the chosen move beside each value.
  • Dictionary state. If a state is not a small integer (a tuple, a string), memoize on a dictionary; @cache does so for you.
  • Recursion depth. Top-down on a long input can exceed Python's recursion limit (1000 by default). Go bottom-up, or raise the limit.
  • Mutable arguments. Never memoize on a list; convert to a tuple or use indices.
  • Edge cases: empty input, a single element, and the base cases written for the wrong offset, which is the most common slip.

Complexity and tradeoffs

  • Time: the number of states times the work to evaluate one. Fibonacci has n states with O(1) work, so O(n); the triangle has about n²/2 states, also O(1) each.
  • Space: the table, or the cache; often reducible to the last few rows or entries.
  • Baseline. The unmemoized recursion is exponential here: {{ total_calls }} calls for n = {{ n }}, roughly 1.6 times more for each step up.
  • When it fails. If the number of states is itself enormous (values up to a billion, or subsets of many items), the table is too big. Look for a greedy proof, a closed form or a smaller state. If the future depends on the whole history, the state is not capturing it.

Check yourself

Why does plain recursion for Fibonacci take exponential time?

The same sub-calls repeat. For fib({{ n }}), fib(1) alone is called {{ tally[1] }} times, and the total is {{ total_calls }} calls for {{ n + 1 }} distinct arguments.

What makes a state sufficient?

Two histories that reach the same state must have exactly the same set of possible futures and the same best future value. If something from the history changes the future, that thing belongs in the state.

On the triangle, why does the greedy walk give {{ dp.greedy }} rather than {{ dp.answer }}?

It chooses the smaller child at each step, but a small child can lead to expensive cells below. The DP compares the cheapest finish from each child, not the child's own number.

When can you replace the table with a few variables?

When each entry reads only a fixed number of earlier entries. Fibonacci reads the last two, so two variables are enough; the triangle reads one row, so one row is enough.
