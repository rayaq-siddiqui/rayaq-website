Heaps

A heap is a pile that always lets you grab the smallest (or largest) item first. It does not keep everything sorted, only the one thing that matters: the next item out. By giving up full order it makes both adding an item and removing the best one cost O(log n), which beats re-sorting after every change. Whenever a problem keeps asking "what is the most urgent thing right now?" while new things keep arriving, a heap is the tool.

Problem

You process items in priority order, but the set of items changes as you go: new tasks arrive, a finished task produces a new one, or a simulation needs "the earliest free machine" over and over. Sorting once does not help because the order changes; sorting again after each change costs O(n log n) per step. Scanning for the minimum costs O(n) per step. A binary heap does both operations, insert and take-the-best, in O(log n). Python ships one as the heapq module, which is a min-heap stored in a plain list.

Intuition

Picture a tournament bracket where the winner is always the smallest number. The winner sits at the top; below it are the winners of each half; and so on down. You do not know the exact order of the losers, but you know each parent beats its children. To add a new item you put it at the bottom and let it climb past any parent it beats. To remove the winner you take the top, put the last item in its place, and let it sink until it fits. Climbing and sinking each touch one item per level, and a tree of n items has only about log₂ n levels, which is why both are O(log n).

The trick that makes this fast in practice is that the tree needs no pointers. Store it as a list in level order: the children of the item at index i sit at 2i + 1 and 2i + 2, and its parent sits at (i - 1) // 2. The shape is always "full on every level but the last, filled from the left", so the list has no gaps.

Mechanics

The invariant

Two rules hold at all times. Shape: the tree is complete, meaning every level is full except possibly the last, which fills from the left; this is what lets a list store it. Order: every item is less than or equal to its children (for a min-heap). The order rule only relates parent and child, so siblings and cousins are in no particular order. That is the "partial order" a heap keeps and a sorted array does not need to.

Push and pop

Push appends the item at the end of the list, which keeps the shape, and then sifts up: while the item is smaller than its parent, swap them. Only the order along one root-to-leaf path can be wrong, and sifting repairs exactly that path. Pop removes the root, which is the minimum. To keep the shape, it moves the last item into the root, then sifts down: swap with the smaller child while that child is smaller than the item. At every step the item is the smallest of itself and its two children after the swap, so the order rule is restored below it. Each loop moves one level, so each operation is O(log n).

Building a heap from n items

Pushing n items one at a time costs O(n log n). Better: put all items in the list as they are and sift down every non-leaf, from the last parent back to the root. Half of the items are leaves and need no work, a quarter sift at most one level, an eighth at most two, and so on, so the total is the sum n/2 · 0 + n/4 · 1 + n/8 · 2 + …, which is O(n). That is what heapq.heapify does.

Implementation

import heapq


heap = []
heapq.heappush(heap, 5)          # O(log n)
smallest = heapq.heappop(heap)   # O(log n)
peek = heap[0] if heap else None # O(1), never heap[-1]

items = [7, 3, 9, 1, 5, 2]
heapq.heapify(items)             # O(n), in place

# Max-heap: negate on the way in, negate back on the way out.
def last_stone_weight(stones):
    heap = [-s for s in stones]
    heapq.heapify(heap)
    while len(heap) > 1:
        first = -heapq.heappop(heap)
        second = -heapq.heappop(heap)
        if first != second:
            heapq.heappush(heap, -(first - second))
    return -heap[0] if heap else 0


# Priority by a key: push tuples; ties compare the next field.
def single_threaded_cpu(tasks):
    order = sorted((enqueue, duration, i) for i, (enqueue, duration) in enumerate(tasks))
    ready, result, now, i = [], [], 0, 0
    while i < len(order) or ready:
        if not ready and now < order[i][0]:
            now = order[i][0]                      # idle: jump to the next arrival
        while i < len(order) and order[i][0] <= now:
            enqueue, duration, index = order[i]
            heapq.heappush(ready, (duration, index))
            i += 1
        duration, index = heapq.heappop(ready)
        now += duration
        result.append(index)
    return result


# Earliest free resource: a heap of finish times.
def min_rooms(intervals):
    ends = []
    for start, end in sorted(intervals):
        if ends and ends[0] <= start:
            heapq.heapreplace(ends, end)           # reuse the room that freed up
        else:
            heapq.heappush(ends, end)
    return len(ends)

heapq has no peek method and no max-heap; heap[0] is the minimum, and negation turns it into a max-heap. heapreplace pops then pushes in one step and is faster than doing the two separately.

Variations and edge cases

  • Tuples as priorities. (priority, tiebreak, payload) compares field by field. If two entries tie on every field before the payload, Python compares the payloads and may raise a TypeError for objects that cannot be ordered, so include a unique counter or index as the tiebreak.
  • Lazy deletion. A binary heap cannot cheaply remove an arbitrary item. Mark it dead in a set and discard it when it reaches the top. The heap can then hold stale entries, so count live items separately.
  • Two heaps. A max-heap for the lower half and a min-heap for the upper half expose the median; a later page covers it.
  • Heap of lists or streams. Push (value, stream, position) to merge sorted inputs.
  • Edge cases: an empty heap (heappop raises IndexError, so check first), a single element, duplicates, and values that are floats or negative numbers when negating for a max-heap. Time arithmetic in simulations needs a rule for idle gaps, as in the CPU example.

Complexity and tradeoffs

  • Time: push and pop are O(log n); peek is O(1); heapify is O(n). A simulation that does n pushes and n pops is O(n log n).
  • Space: O(n) for the list; sifting is in place, so no extra memory.
  • Baseline. A plain list scanned with min costs O(n) per extraction, O(n²) for a run of n; a sorted list costs O(n) per insertion. A heap balances the two at O(log n) each.
  • When it fails. If every item is known up front and you only need them in order, sorting is simpler and has a smaller constant. If you need search by value, updates to priorities, or removal from the middle, a balanced search tree or an indexed heap fits better. A heap cannot list its contents in order without popping every item.

Check yourself

Why does the heap keep the tree complete instead of letting it take any shape?

A complete tree has no gaps, so it fits in a list where the children of index i are 2i + 1 and 2i + 2. That removes pointers, keeps memory compact and keeps the height at about log₂ n, which bounds every sift.

Why does pop move the last item to the root instead of promoting a child?

Removing the last slot is the only removal that keeps the tree complete. Moving that item to the root breaks only the order rule along one path, and sifting down repairs it. In the example the moved value {{ popped.moved }} sank {{ popped.swaps }} level{{ "" if popped.swaps == 1 else "s" }}.

Why is building a heap by heapify O(n) when each sift is O(log n)?

Most nodes are near the bottom and sift only a level or two. Half are leaves and cost nothing; a quarter cost at most one swap; the sum of work over levels converges to a constant times n. Pushing in descending order cost {{ cmp.push_swaps }} swaps in the example against {{ cmp.heapify_swaps }} for heapify.

How do you get the largest item first from heapq?

Push the negation of each value and negate again when popping, as in the stone example: the smallest negative is the largest original. For tuples, negate the numeric field that should be maximised.
