Binary search

Binary search finds a position in a sorted range by throwing away half of what is left after every comparison. The skill is not the idea but the bookkeeping: a clear invariant for what the range still guarantees, and a loop that always shrinks it. Get those right and the same few lines find a value, an insertion point, the pivot of a rotated array, or the first element that satisfies any yes-or-no test.

Problem

Given a sorted array, is a value in it, and where? Scanning from the left costs O(n). The array being sorted is information you are not using: one comparison with the middle element tells you which half can hold the answer and which half cannot. Repeat on the surviving half and a million elements take about twenty comparisons. The same idea applies whenever the data has a hidden order: a rotated array is two sorted runs glued together, and a "good, good, bad, bad, bad" sequence is sorted by the yes-or-no answer even if nothing looks like numbers.

Intuition

It is the number-guessing game. You pick a number between 1 and 100 and say "higher" or "lower" after each guess. Guessing the middle every time is the best strategy because whatever you hear, half of the remaining numbers are gone. After seven guesses at most one number is left.

What makes this safe to code is to say in words what the range promises. In the version used here the range is half-open, from lo up to but not including hi, and it promises "the answer is somewhere in this range, and if no element qualifies the answer is hi". Every line of the loop exists to keep that sentence true while making the range smaller.

Blue cells are the live range, amber is the midpoint just examined and green the final answer. The live range starts at all {{ sorted_nums | length }} cells and shrinks every row.

Mechanics

The invariant

Search for the first index whose value is at least the target in the half-open range [lo, hi), starting at lo = 0 and hi = len(nums). The invariant: every index below lo holds a value less than the target, and every index at or above hi holds a value at least the target (or does not exist). The answer therefore sits in [lo, hi].

While lo < hi, take mid = (lo + hi) // 2, which is always inside the range. If nums[mid] < target, then mid and everything below it are too small: set lo = mid + 1. Otherwise mid qualifies and so does everything after it, but something earlier might also qualify: set hi = mid. Both moves keep the invariant, and both shrink the range by at least one element, so the loop ends with lo == hi, and the invariant says that index is the answer.

Finding a value, and why this form is safer

Lower bound does not ask "is this the target?" in the loop. When it ends, check once whether lo is in range and nums[lo] == target. This single shape answers three questions: membership, insertion point (lo itself, even when the value is missing) and first occurrence among duplicates. An early return on nums[mid] == target gives up the last two and invites off-by-one bugs, so use it only for plain membership.

Any monotone yes-or-no test

Nothing above needed numbers. All it used was a predicate ok(i) that is false for a prefix of the indices and true for the rest. Replace nums[mid] < target with not ok(mid) and the loop finds the first true. "First bad version" is exactly that. The next page uses the same loop over answers rather than positions.

Rotated arrays

Rotating a sorted array of distinct values makes two ascending runs, with a drop between them. For any midpoint, at least one of [lo, mid] and [mid, hi] does not contain the drop and is therefore sorted. Test which: if nums[lo] <= nums[mid] the left half is sorted. Then check whether the target lies within that sorted half's bounds; if so keep it, otherwise discard it and keep the other half. To find the minimum, compare nums[mid] with nums[hi]: if the midpoint is larger the drop is to its right, otherwise the minimum is at mid or before it.

Implementation

from bisect import bisect_left


def lower_bound(nums, target):
    lo, hi = 0, len(nums)                        # answer is in [lo, hi]
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid
    return lo


def search(nums, target):
    i = lower_bound(nums, target)
    return i if i < len(nums) and nums[i] == target else -1


def first_true(lo, hi, ok):
    """Smallest i in [lo, hi) with ok(i), or hi if none; ok must be False for a prefix, then True."""
    while lo < hi:
        mid = (lo + hi) // 2
        if ok(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo


def search_rotated(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[lo] <= nums[mid]:                # left half is sorted
            if nums[lo] <= target < nums[mid]:
                hi = mid - 1
            else:
                lo = mid + 1
        else:                                    # right half is sorted
            if nums[mid] < target <= nums[hi]:
                lo = mid + 1
            else:
                hi = mid - 1
    return -1


def rotated_minimum(nums):
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] > nums[hi]:
            lo = mid + 1
        else:
            hi = mid
    return nums[lo]

bisect_left(nums, target) from the standard library is lower_bound; in an interview write the loop out, and use bisect at work. Python integers do not overflow, so (lo + hi) // 2 is safe here; in a fixed-width language write lo + (hi - lo) // 2.

Variations and edge cases

  • Last position instead of first. Find the first index greater than the target (nums[mid] <= target moves right) and subtract one. This is bisect_right.
  • Matrix as one array. Search indices 0 to rows × cols − 1 and read the cell at divmod(mid, cols).
  • Search for a window, not an element. For the k closest elements, search the left edge of the window over [0, n − k] and compare how far x is from nums[mid] and nums[mid + k].
  • Duplicates in a rotated array. When nums[lo] == nums[mid] == nums[hi] you cannot tell which half is sorted, so shrink both ends by one; the worst case degrades to O(n).
  • Edge cases: an empty array (the loop never runs and lower bound returns 0), a target smaller than everything (index 0), larger than everything (index n), a single element, duplicates, and a rotation by zero, where the array is simply sorted.

Complexity and tradeoffs

  • Time: O(log n). The range loses at least half its elements per step. This array of {{ sorted_nums | length }} needed {{ lb.steps | length }} steps.
  • Space: O(1) for the loop.
  • Baseline. A linear scan is O(n) and needs no ordering. If you search once in unsorted data, scanning beats sorting first (O(n log n)); binary search wins when the data is sorted already or searched many times.
  • When it fails. The data must have order that a single comparison can exploit. Unsorted data, or a predicate that flips more than once, breaks the invariant. A rotated array with many duplicates loses the guarantee that one half is sorted.

Check yourself

Why does the lower-bound loop use hi = mid but lo = mid + 1?

When nums[mid] is too small, mid itself is ruled out, so lo can skip past it. When it qualifies, mid might be the answer, so it has to stay inside the range as the new hi. Using hi = mid - 1 could throw away the answer, and lo = mid could loop forever once the range has two elements.

What does the loop return for a missing value, and why is that useful?

It returns the insertion point, the index where the value would go to keep the array sorted. For 20 here that is index {{ gap.index }}, between 16 and 23.

In a rotated array, how do you know which half is sorted?

Compare nums[lo] with nums[mid]. If the left end is at most the midpoint, there is no drop between them, so the left half is ascending. Otherwise the drop is on the left and the right half must be ascending.

The first search of this page took {{ lb.steps | length }} steps on {{ sorted_nums | length }} elements. How many would an array of about a million need?

About twenty, since 220 is just over a million and each step halves the range. Doubling the data adds one step.
