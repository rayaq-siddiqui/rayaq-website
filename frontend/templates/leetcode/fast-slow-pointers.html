Fast and slow pointers

Send two pointers down the same sequence, one taking a step while the other takes two. If the sequence loops, the fast one must lap the slow one, which detects a cycle without remembering anything. If it does not loop, the slow one is standing in the middle when the fast one runs out. The same trick finds where a cycle begins, and it works on any sequence where each item says what comes next, including an array of indices and the digits of a number.

Problem

Some questions are about the shape of a sequence you can only walk forward: does it loop, where does the loop start, where is its middle. The obvious answer is to write down every node you visit and stop when you see one twice. That costs memory proportional to the walk. The interview version adds "in constant space", and the answer is to let two walkers carry the memory for you: their distance apart.

Intuition

Two runners start together on a track. If the track is a straight line, the faster one finishes first and that is the end of the story. If the track has a circular section, the faster runner enters it first and goes round, and the slower runner enters later. On a circle, speed differences always become meetings: the faster runner closes the gap by one position per turn, so it cannot jump over the slower one, and sooner or later it catches up from behind. A runner who finishes tells you there is no loop; a meeting tells you there is.

The middle works the same way without a loop. If one pointer moves twice as fast as the other, then at the moment the fast one steps off the end, the slow one has made exactly half as many steps, which is half the list. You never needed to know the length.

The shape the algorithm is analysed on: a tail, then a loop. The last node's arrow returns to node {{ fl.entrance }}, the entrance of the cycle.

Mechanics

Detecting a cycle

Start both pointers at the head. Each turn, slow moves one node and fast moves two. If fast ever reaches the end (it is null, or its next is null), the list is straight and there is no cycle. If slow and fast are ever the same node, there is a cycle.

Why they must meet. After both pointers are inside the loop, say the loop has L nodes. Each turn fast gains exactly one node on slow, so the gap, measured round the loop, shrinks by one per turn. A gap that goes down by one each time from some value under L passes through zero, and zero means they are on the same node. Fast never steps over slow, because the gap would have to skip from 1 to −1, and it only ever changes by exactly one. Slow enters the loop after the tail's {{ fl.tail_length }} nodes, and fast has entered earlier, so they meet within L more turns of slow arriving.

Finding where the cycle begins

Let μ be the number of nodes before the cycle (the tail length) and L the cycle length. When they meet, slow has taken k steps and fast has taken 2k. Both are in the loop and fast has gone round some whole number of extra laps, so 2k − k = k is a multiple of L. Slow's position is k − μ steps past the entrance, and since k is a multiple of L that is the same place as −μ steps past it. So walking μ more steps from the meeting point lands exactly on the entrance, going round the loop as needed.

That gives the second phase. Put one pointer at the head and keep one at the meeting point. Move both one step at a time. The head pointer needs μ steps to reach the entrance, and so does the other, so they meet there, and the place they meet is the answer. It also hands you μ as the number of steps taken and, by walking once round from the entrance, L.

Finding the middle

Same movement, no loop. Stop when fast has no node or no next node. For a list of length n, slow is then at index ⌊n / 2⌋: the exact middle when n is odd and the second of the two middles when n is even. If you test fast.next and fast.next.next instead, slow stops one node earlier on even lengths, at the first middle. Which one you want depends on whether the first half should be the longer one when you split.

Implementation

def has_cycle(head):
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast:
            return True
    return False


def cycle_start(head):
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast:
            break
    else:
        return None                               # fast fell off the end
    slow = head
    while slow is not fast:
        slow, fast = slow.next, fast.next
    return slow


def middle(head):
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
    return slow


def find_duplicate(nums):
    slow = fast = 0
    while True:
        slow, fast = nums[slow], nums[nums[fast]]
        if slow == fast:
            break
    slow = 0
    while slow != fast:
        slow, fast = nums[slow], nums[fast]
    return slow


def is_happy(n):
    def step(x):
        return sum(int(d) ** 2 for d in str(x))

    slow, fast = n, step(n)
    while fast != 1 and slow != fast:
        slow, fast = step(slow), step(step(fast))
    return fast == 1

find_duplicate uses a do-while shape because the pointers start equal, so the first check must come after the first move. Index 0 is a safe start: every value is at least 1, so nothing points back at index 0, which makes it part of the tail and guarantees the entrance is a real repeated value.

Variations and edge cases

  • Palindrome list. Find the first middle (while fast.next and fast.next.next), reverse the list after it, then compare the two halves node by node. Reverse the second half back afterwards if the problem says not to damage the input.
  • Reorder list. Split at the first middle, reverse the second half, then weave: first, last, second, second to last, and so on. This is three earlier patterns in a row: find the middle, reverse, merge.
  • Cycle length. After they meet, hold one pointer still and count steps until the other returns to it. Here that count is {{ fl.cycle_length }}.
  • Happy number. The "list" is the sequence of digit-square sums. It cannot grow forever, because the sum of squared digits of a large number is far smaller than the number, so it either reaches 1 (which maps to itself) or repeats.
  • A set is fine too. A hash set of visited nodes is simpler and runs in O(n) time and space. Say that first in an interview, then offer Floyd's version when asked for constant space.
  • Edge cases: an empty list, a single node (with and without a self-loop), two nodes, a cycle that includes the head (the entrance is the head, phase two takes zero steps), a straight list such as 1 → 2 → 3 → 4, where fast falls off the end after {{ no_cycle.steps | length - 1 }} turn{{ "" if no_cycle.steps | length - 1 == 1 else "s" }}, and comparing nodes with is, not values, because two different nodes can hold equal values.

Complexity and tradeoffs

  • Time: O(n). Slow enters the loop after μ steps, and fast catches it within L more, so detection is at most μ + L turns, each constant work. Phase two adds at most μ steps. In the example that was {{ fl.steps | length - 1 }} turns plus {{ fl.tail_length }} steps for {{ nxt | length }} nodes.
  • Space: O(1), two pointers. This is the whole point; a visited set is O(n).
  • Baseline. Marking visited nodes (a set, or a flag written into the node) is also O(n) time but spends memory, or modifies the input.
  • When it fails. The sequence must be a deterministic function of the current item, since the argument depends on two walkers following the same path. If steps depend on history, or the structure is a graph where each node has several successors, there is no single "next", and you use a visited set with depth-first search. When the values live in a sorted array, binary search on the answer can also find the duplicate in O(n log n) without changing the array; Floyd gets O(n).
  • Constants. Fast does about twice the moves of slow, so it makes roughly three times as many pointer steps as a single walker. Brent's variant, in the references, reduces that.

Check yourself

Why can fast never jump over slow inside the loop?

Each turn the gap from fast back to slow, counted round the loop, changes by exactly one: fast moves two, slow moves one. A gap that falls one at a time from any starting value reaches 0, and it cannot jump from 1 to −1. If fast moved three nodes per turn the gap would change by two and could skip a loop of even length forever, which is why the speeds are one and two.

The pointers met after {{ fl.steps | length - 1 }} turns on a loop of {{ fl.cycle_length }} nodes. Why is that no accident?

At the meeting, fast has travelled twice as far as slow, so the extra distance (equal to slow's total) is a whole number of laps. Slow's total is therefore a multiple of {{ fl.cycle_length }}. Here it is {{ fl.steps | length - 1 }}.

Why does restarting one pointer from the head find the cycle's entrance?

Slow's total steps are a multiple of the loop length, so the meeting point is μ steps before the entrance when counted going round the loop (μ is the tail length). The head is also μ steps from the entrance. Moving both one node at a time, they arrive at the entrance together after {{ fl.tail_length }} steps in the example.

In find-the-duplicate, why is the repeated value the entrance of the cycle?

Treat each index as a node pointing at the index its value names. The repeated value appears at two indices, so the node with that number has two arrows into it. In a walk that starts outside the loop, a node with two incoming arrows is exactly where the tail joins the loop. For {{ dup_nums }} that is {{ dup.entrance }}.
