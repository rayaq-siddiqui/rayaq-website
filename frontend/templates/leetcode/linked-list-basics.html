Linked list basics

A linked list is a chain of nodes, each knowing only the next one, so every operation is a matter of rewiring pointers in the right order. Three habits cover most of the basic problems: save what you are about to overwrite, put a dummy node in front so the head is not a special case, and draw the pointers before writing the code.

Problem

An array gives you any element by index. A linked list gives you the head, and everything else is reached one hop at a time. In exchange, a node can be spliced in or out in constant time once you hold the node before it. Interview problems ask you to reverse a list, merge two, remove a node, add two numbers digit by digit, rotate, or reorder, all in place. They are rarely hard in idea; they are hard because one wrong assignment order silently loses the rest of the list.

Intuition

Picture a train of cars, each coupled only to the car behind it. To reverse the train you can only work at the coupling you are standing at. You uncouple the car in front of you, but first remember which car was behind it, because once the coupling is gone nothing else tells you where the rest of the train is. Reverse the first coupling, step to the remembered car, repeat. That is the whole algorithm: remember, then rewire, then step.

The dummy node is a cheap trick with a big payoff. If the operation might change the head (removing the first node, merging where the second list starts smaller), attach a throwaway node in front and work with "the node before" uniformly. At the end return dummy.next.

Mechanics

The invariant

For reversal, keep two pointers, prev (the head of the already-reversed part, initially null) and cur (the head of the rest). The invariant: prev heads a correctly reversed list of everything before cur, and cur heads the untouched remainder. One step saves cur.next, points cur.next at prev, then advances both. Each step keeps the invariant and moves one node across, so when cur is null prev heads the whole reversed list.

Dummy head and tail

To build or edit a list from the front, create dummy = Node(0) and a tail that starts at it. To append a node, set tail.next to it and move tail. For merging, the invariant is that everything from dummy.next to tail is the sorted merge of the nodes already consumed. When one list runs out, point tail.next at the other, whole, because the rest of a sorted list is already sorted.

Two pointers with a fixed gap

To remove the nth node from the end in one pass, advance a leader so it is n + 1 steps ahead of the dummy, then move leader and trailer together. When the leader reaches null, the trailer is exactly one node before the one to cut. The dummy covers the case where the cut is the first node, because then the trailer is the dummy itself.

The leader starts n + 1 steps ahead of the trailer and they move in lockstep. At the end the amber node, the one after the trailer, is the one to cut; the leader is off the right edge, at null.

Implementation

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next


def reverse(head):
    prev, cur = None, head
    while cur:
        nxt = cur.next                           # save before overwriting
        cur.next = prev
        prev, cur = cur, nxt
    return prev


def merge(a, b):
    dummy = tail = ListNode()
    while a and b:
        if a.val <= b.val:
            tail.next, a = a, a.next
        else:
            tail.next, b = b, b.next
        tail = tail.next
    tail.next = a or b                           # attach the rest whole
    return dummy.next


def remove_nth_from_end(head, n):
    dummy = ListNode(0, head)
    lead = trailer = dummy
    for _ in range(n + 1):
        lead = lead.next
    while lead:
        lead, trailer = lead.next, trailer.next
    trailer.next = trailer.next.next
    return dummy.next


def add_two_numbers(a, b):
    dummy = tail = ListNode()
    carry = 0
    while a or b or carry:
        total = carry + (a.val if a else 0) + (b.val if b else 0)
        carry, digit = divmod(total, 10)
        tail.next = ListNode(digit)
        tail = tail.next
        a = a.next if a else None
        b = b.next if b else None
    return dummy.next

In merge, the tuple assignment tail.next, a = a, a.next evaluates the right side first, so a.next is read before a changes. Reordering such a line is a classic way to lose the rest of a list.

Variations and edge cases

  • Reverse part of the list. Walk to the node before position left, then repeatedly move the node after the sublist's first node to the front of the sublist, right − left times.
  • Reverse in groups of k. First check that k nodes remain; if so, reverse exactly that block and reconnect it between the previous group's tail and the next group's head. Leave a short final block as is.
  • Rotate. Count the length, join the tail to the head to make a ring, and break the ring at length minus (k mod length).
  • Swap in pairs. Behind a dummy, rewire two nodes at a time and save the next pair first.
  • Recursive reverse. Elegant, but it uses O(n) stack; for lists of 105 nodes it reaches Python's recursion limit.
  • Edge cases: an empty list, a single node, removing the head, removing the tail, n equal to the length, unequal list lengths in addition, a final carry that needs one more node, and forgetting to set the last node's next to null (which creates a cycle).

Complexity and tradeoffs

  • Time: O(n) for a single pass; each node is touched a constant number of times. Reversal here took {{ rev.steps | length }} rewrites for {{ rev_in | length }} nodes.
  • Space: O(1) for in-place rewiring. Copying values into an array and rebuilding is O(n) space and usually acceptable in practice, but it is not what the problem is testing.
  • Baseline. Counting the length first, then walking to position length − n, is two passes and also O(n). The gap trick is one pass for the same asymptotic cost.
  • When it fails. Lists have no random access, so binary search and indexing are out. If you need cycles or the middle, the next page's fast and slow pointers apply; if you need O(1) lookup by key along with order, the list design page combines a list with a hash map.

Check yourself

In the reversal loop, what goes wrong if you write cur.next = prev before saving cur.next?

The only reference to the rest of the list was cur.next, so after overwriting it the remaining nodes are unreachable and the loop ends after one node. Saving it first is what makes the invariant "cur heads the untouched remainder" hold.

Why does a dummy node simplify removing the nth node from the end?

Cutting a node needs the node before it. For the first node there is none, so you would special-case the head. With a dummy in front, the trailer is the dummy in that case and the same line, trailer.next = trailer.next.next, works. Here the cut node held {{ rm.removed }}, and removing the head would use the same code.

Why can merge attach the leftover list with one assignment?

The leftover is the rest of a list that was sorted to begin with, and every value in it is at least as large as everything already merged. Here the leftover was {{ mer.leftover | join(", ") }}, attached in one step rather than {{ mer.leftover | length }} comparisons.

Addition loops while a or b or carry. Why include carry?

Adding 5 and 5 leaves both lists empty with a carry of 1 still owed, which needs one more node. Without carry in the condition the result would drop a digit.
