Subsets, permutations and combinations

Some questions ask for every answer, not the best one: every subset, every ordering, every valid arrangement. The tool is one small recursive routine that chooses an item, explores everything that follows from the choice, then unchooses it so the next option starts from a clean slate. Subsets, permutations, combinations and well-formed parentheses differ only in which items the loop is allowed to offer next.

Problem

You are given a small collection and asked to list or count by listing every selection that fits a rule. The input size is tiny (usually 20 or fewer items) because the answer itself is exponential: a set of n items has 2n subsets and n! orderings, so no algorithm can print them faster than they exist. What matters is generating each exactly once, with no repeats, and without building thousands of throwaway copies.

SignalPatternWhy
"Return all subsets" or "the power set"Include-or-skip recursion, or a loop from a start indexEvery node of the search is itself an answer, and the start index prevents the same subset in a different order.
"All orderings" or "all arrangements"Permutation search with a used markerOrder matters, so any unused item may come next.
"Choose k of n"Combinations with a start index and an early stopOrder does not matter, and the path stops growing at length k.
"Input may contain duplicates, no repeated answers"Sort, then skip a value equal to its left siblingTwo equal choices at the same depth lead to identical subtrees.
"Generate all valid strings of some shape"Build character by character, offer only moves that keep the prefix validThe rule is enforced while building, so dead prefixes are never extended.
"Maximum or minimum of something over all selections"Dynamic programming if subproblems overlapIf you need one number rather than the list, listing everything is wasted work.

Intuition

Picture packing a bag from three items on a table. You decide about the first item, then the second, then the third. Each decision splits the future in two, so after three decisions you have visited every one of the eight possible bags. That is a tree of decisions, and backtracking is simply a walk over that tree.

The only trick is to use one shared bag instead of a new bag per branch. Put an item in, walk everything that can follow, then take the item back out. Taking it back out is the "backtrack" step, and it is what restores the bag to the state the parent expected. Whenever the search reaches a spot that counts as an answer, you copy the bag into the results, because the bag itself will keep changing.

Subsets and permutations are the same walk with different offers at each node. For subsets you only offer items after the last one you took, so {1, 2} is reached once rather than also as {2, 1}. For permutations you offer every item you have not used yet, so order creates distinct answers.

Mechanics

The template in words

Keep a shared path list and a recursive function explore. On entry, decide whether the current path is an answer and, if so, copy it into the results. Then loop over the options that are legal here. For each one: append it to the path (choose), call explore (explore), pop it off again (unchoose).

The invariant

When explore returns, the path is exactly what it was when the call began. That holds by induction: each iteration of the loop pushes one item and pops one item, and the recursive call in between leaves the path unchanged by the same argument on a shorter remaining problem. Because of that invariant, the caller can keep looping without any cleanup, and the whole search uses one list for its path.

Why each answer appears exactly once

Every answer corresponds to one root-to-node path in the tree, and the tree is built so that path is unique. For subsets, the loop starts at start, so items are always taken in increasing position, which gives each subset one canonical order. For permutations, nothing is skipped except what is already on the path, so each distinct ordering of the input positions is exactly one path. Counting nodes confirms it: the subset tree has 2n nodes and the permutation tree has n! leaves.

Repeated values

If the input has equal values, two different choices at the same depth can produce the same subtree, and the answers repeat. Sort first so equal values sit together, then inside the loop skip index i when i > start and nums[i] == nums[i - 1]. The first of a run of equal values is allowed at any depth; a later one in the run may only be used after the earlier one is already on the path. That condition i > start is the whole subtlety: it says "this value was already offered to this parent".

Green leaves are complete permutations. Each level removes one item from the pool, so the fan-out is 3, then 2, then 1: 3! = {{ perm.results | length }} leaves in all.

Implementation

def subsets(nums):
    results, path = [], []

    def explore(start):
        results.append(path[:])          # every node is an answer; copy, because path keeps changing
        for i in range(start, len(nums)):
            path.append(nums[i])
            explore(i + 1)
            path.pop()

    explore(0)
    return results


def permutations(nums):
    results, path = [], []
    used = [False] * len(nums)

    def explore():
        if len(path) == len(nums):
            results.append(path[:])
            return
        for i in range(len(nums)):
            if used[i]:
                continue
            used[i] = True
            path.append(nums[i])
            explore()
            path.pop()
            used[i] = False

    explore()
    return results

Variations and edge cases

def subsets_with_dup(nums):
    nums.sort()
    results, path = [], []

    def explore(start):
        results.append(path[:])
        for i in range(start, len(nums)):
            if i > start and nums[i] == nums[i - 1]:
                continue
            path.append(nums[i])
            explore(i + 1)
            path.pop()

    explore(0)
    return results


def combine(n, k):
    results, path = [], []

    def explore(start):
        if len(path) == k:
            results.append(path[:])
            return
        for value in range(start, n - (k - len(path)) + 2):
            path.append(value)
            explore(value + 1)
            path.pop()

    explore(1)
    return results


def generate_parentheses(n):
    results = []

    def explore(text, opened, closed):
        if len(text) == 2 * n:
            results.append(text)
            return
        if opened < n:
            explore(text + "(", opened + 1, closed)
        if closed < opened:
            explore(text + ")", opened, closed + 1)

    explore("", 0, 0)
    return results
  • Copying the path. results.append(path) stores a reference to the one shared list, which ends up empty. Always store path[:] or list(path).
  • Duplicates in permutations. Sort the input and, in the loop, skip index i if nums[i] == nums[i - 1] and nums[i - 1] is not currently used. That keeps equal values in their original relative order, so each distinct ordering is built once.
  • Start index versus used array. A start index is for choices where order does not matter (subsets, combinations); a used array is for orderings. Mixing them up either loses answers or repeats them.
  • Bitmask alternative. For subsets only, counting from 0 to 2n - 1 and reading the bits of each number enumerates all of them without recursion.
  • Edge cases: an empty input (one subset, the empty one; one permutation, the empty list), k equal to 0 or n, k greater than n (no answers), and a phone-digit style input where some choice lists are empty.

Complexity and tradeoffs

  • Time: proportional to the number of tree nodes times the cost of copying an answer. Subsets are O(n · 2n), permutations are O(n · n!), combinations of k from n are O(k · C(n, k)). Output size sets a floor you cannot beat.
  • Space: O(n) for the recursion stack and the shared path, not counting the results.
  • Baseline. Building a new list at every call is easier to write and costs an extra copy per node; the shared path with push and pop avoids that.
  • Pruning pays. For combinations, the early stop cut the calls from {{ comb_raw.calls }} to {{ comb.calls }} for choosing 2 of 4, and the saving grows quickly with n. Stopping when no valid completion exists is the idea the next page builds on.
  • When it fails. If the input is large (say 30 items) or you need only a count, a maximum or a yes/no, enumerating everything is hopeless. Use dynamic programming or a formula instead.

Check yourself

Why must the results store a copy of the path?

The path is one shared list that the search keeps pushing to and popping from. Storing the list itself would store a reference, so every recorded answer would end up showing the final (empty) state. A copy freezes the contents at that moment.

How many calls does the subset search make for {{ items | length }} items, and why?

{{ sub.calls }}. Every call corresponds to exactly one subset, and there are 2{{ items | length }} of them, so the call count equals the number of answers.

What does the test i > start do in the duplicate-skipping rule?

It restricts the skip to siblings: values offered by the same parent. The first item in a run of equal values (at i == start) is always allowed, so {{ dup_input | sort | join(", ") }} can still produce a subset with both 2s. Without that test, you would also skip a legitimate deeper use of the second 2 and lose answers.

Why is the early stop in combinations safe?

If fewer numbers remain than the path still needs, no completion can reach length k, so those branches contain no answers. Stopping there changed the calls from {{ comb_raw.calls }} to {{ comb.calls }} for choosing 2 of 4 without changing the answers.
