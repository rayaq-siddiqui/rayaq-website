Segment trees

A segment tree answers "what is the sum, minimum or maximum of this range?" while the array keeps changing. It stores the answer for the whole array at the root, for each half below it, for each quarter below those, down to single elements. Any range is then a handful of stored pieces, and changing one element only touches the pieces that contain it, so both operations cost O(log n). It rarely comes up in interviews: none of the four lists needs it. It is here because it is the general answer whenever prefix sums break.

Problem

Prefix sums answer any range sum in O(1), but only on an array that never changes: one update shifts every prefix after it, costing O(n). Recomputing each query from the raw array is the opposite trade, O(1) to update and O(n) to ask. When a problem interleaves the two, up to 105 of each, both are quadratic. A segment tree meets in the middle at O(log n) for each, and it works for any operation that combines two neighbouring answers into one, such as sum, min, max, gcd or "count of values in a bucket".

Intuition

Imagine a tournament bracket over the array. Each leaf is one element. Each match above combines two neighbours into one result, so the node above leaves 2 and 3 holds their sum, the node above that holds the sum of 0 to 3, and the root holds everything. Every node is responsible for one contiguous block, and the blocks at each level tile the array without overlap.

To answer a range, walk down from the root. A block entirely inside the range is used whole, without looking inside it. A block entirely outside is ignored. Only a block that straddles one of the range's two ends needs opening, and since a range has only two ends, only two blocks per level can straddle. That is why a query touches a few nodes per level and never the whole array. To change an element, fix its leaf and then recompute every ancestor on the way up: one node per level.

Amber nodes straddle an end of the range and are opened; green nodes lie inside it and are used whole; red outlines are visited and rejected at once; plain nodes are never touched. The diagram scrolls sideways on a narrow screen.

Mechanics

Layout

Store the tree in a flat list, the way a heap is stored. Node 1 is the root and covers [0, n - 1]. Node v covering [lo, hi] has children 2v and 2v + 1 covering [lo, mid] and [mid + 1, hi] with mid = (lo + hi) // 2. A node whose range is one element is a leaf. Building is a post-order recursion: build both children, then set the node to their combination, which visits each of the 2n − 1 nodes once.

The invariant

Every node holds the combination of the array values in its range. Build establishes it bottom-up. A point update breaks it only at the nodes whose range contains the changed index, which are exactly the leaf and its ancestors, and recomputing them bottom-up restores it, since each depends only on its two children. The combining operation must be associative, so that splitting a range into pieces and combining the pieces gives the same answer in any grouping; it does not have to be commutative if pieces are combined left to right, and it needs an identity (0 for sum, infinity for min) to return for an empty piece.

The query

query(node) for a target range [left, right] has three cases. If the node's range is disjoint from the target, return the identity. If it is contained in the target, return the stored value: by the invariant it is exactly that block's answer. Otherwise it overlaps partly, so recurse into both children and combine. Correctness follows by induction on the node's size: the inside and outside cases are right by the invariant, and a partial node's range is the disjoint union of its children's, so combining their correct answers for the overlap is correct.

Why O(log n)

At any level, the nodes that partly overlap the target are the at most two that contain left or right without lying inside the range. Any node strictly between them lies inside, and the recursion never descends below an inside or outside node. So each level has at most two split nodes, they open at most four children on the next level, and the depth is ⌈log2 n⌉. A query therefore visits at most about 4 log2 n nodes. The table in the tradeoffs section checks that bound against every possible range.

Implementation

class SegmentTree:
    def __init__(self, nums):
        self.n = len(nums)
        self.tree = [0] * (4 * self.n)
        self._build(1, 0, self.n - 1, nums)

    def _build(self, node, lo, hi, nums):
        if lo == hi:
            self.tree[node] = nums[lo]
            return
        mid = (lo + hi) // 2
        self._build(2 * node, lo, mid, nums)
        self._build(2 * node + 1, mid + 1, hi, nums)
        self.tree[node] = self.tree[2 * node] + self.tree[2 * node + 1]

    def update(self, index, value, node=1, lo=0, hi=None):
        if hi is None:
            hi = self.n - 1
        if lo == hi:
            self.tree[node] = value
            return
        mid = (lo + hi) // 2
        if index <= mid:
            self.update(index, value, 2 * node, lo, mid)
        else:
            self.update(index, value, 2 * node + 1, mid + 1, hi)
        self.tree[node] = self.tree[2 * node] + self.tree[2 * node + 1]

    def query(self, left, right, node=1, lo=0, hi=None):
        if hi is None:
            hi = self.n - 1
        if right < lo or hi < left:
            return 0
        if left <= lo and hi <= right:
            return self.tree[node]
        mid = (lo + hi) // 2
        return (self.query(left, right, 2 * node, lo, mid)
                + self.query(left, right, 2 * node + 1, mid + 1, hi))

For min or max, replace the + in all three places and return the identity (math.inf for min) from the disjoint case.

Variations and edge cases

Bottom-up, in 2n slots. Put the leaves at tree[n:] and fill parents from the back. A query climbs from both ends at once, taking a node whenever the boundary is a right child on the left side or a left child on the right side. No recursion and half the memory:

class BottomUpTree:
    def __init__(self, nums):
        self.n = n = len(nums)
        self.tree = [0] * n + list(nums)
        for i in range(n - 1, 0, -1):
            self.tree[i] = self.tree[2 * i] + self.tree[2 * i + 1]

    def update(self, index, value):
        i = index + self.n
        self.tree[i] = value
        while i > 1:
            i //= 2
            self.tree[i] = self.tree[2 * i] + self.tree[2 * i + 1]

    def query(self, left, right):
        total, lo, hi = 0, left + self.n, right + self.n + 1
        while lo < hi:
            if lo & 1:
                total += self.tree[lo]
                lo += 1
            if hi & 1:
                hi -= 1
                total += self.tree[hi]
            lo //= 2
            hi //= 2
        return total

Lazy propagation for range updates. Adding v to every element of a range would touch up to n leaves. Instead, a node fully inside the update adds v × length to its own total and remembers v as pending; the pending value is pushed to its children only when a later call needs to look below it:

class LazyTree:
    def __init__(self, n):
        self.n = n
        self.total = [0] * (4 * n)
        self.pending = [0] * (4 * n)

    def _apply(self, node, lo, hi, delta):
        self.total[node] += delta * (hi - lo + 1)
        self.pending[node] += delta

    def _push(self, node, lo, mid, hi):
        if self.pending[node]:
            self._apply(2 * node, lo, mid, self.pending[node])
            self._apply(2 * node + 1, mid + 1, hi, self.pending[node])
            self.pending[node] = 0

    def add(self, left, right, delta, node=1, lo=0, hi=None):
        if hi is None:
            hi = self.n - 1
        if right < lo or hi < left:
            return
        if left <= lo and hi <= right:
            self._apply(node, lo, hi, delta)
            return
        mid = (lo + hi) // 2
        self._push(node, lo, mid, hi)
        self.add(left, right, delta, 2 * node, lo, mid)
        self.add(left, right, delta, 2 * node + 1, mid + 1, hi)
        self.total[node] = self.total[2 * node] + self.total[2 * node + 1]

    def query(self, left, right, node=1, lo=0, hi=None):
        if hi is None:
            hi = self.n - 1
        if right < lo or hi < left:
            return 0
        if left <= lo and hi <= right:
            return self.total[node]
        mid = (lo + hi) // 2
        self._push(node, lo, mid, hi)
        return (self.query(left, right, 2 * node, lo, mid)
                + self.query(left, right, 2 * node + 1, mid + 1, hi))

Over values instead of positions. To count, for each element, how many smaller values come after it, compress the values to ranks 0 to k − 1, walk the array from the right, query the sum of ranks below the current one, then add 1 at its rank. The same trick, with max instead of sum, gives the longest increasing subsequence ending at each value.

  • Array size. With the recursive layout, node indices can exceed 2n when n is not a power of two; 4n is always enough. The table below shows the largest index actually used.
  • Inclusive or half-open. Pick [left, right] or [left, right) once and use it in every comparison; mixing them drops or double-counts a boundary element.
  • Empty array. _build(1, 0, -1) never reaches a leaf and recurses until the stack overflows; guard n == 0 first.
  • Recursion depth. The depth is only about log2 n, so Python's recursion limit is not a problem here, unlike a DFS on a path-shaped graph.

Complexity and tradeoffs

Build is O(n) time and the tree uses O(n) space; a query or a point update is O(log n); a lazy range update is O(log n) as well. The query bound, checked by running every possible range:

  • Against the alternatives. With q queries and u updates, a plain array costs O(u + qn), prefix sums O(un + q), and a segment tree O((u + q) log n).
  • Against a Fenwick tree. A Fenwick (binary indexed) tree does prefix sums with point updates in fewer lines and less memory, but it needs an invertible operation to turn prefixes into ranges, so it cannot do range min or max directly. The segment tree is the general tool; the Fenwick tree is the compact special case.
  • Against a sorted container. "How many values below x" can also be answered by binary search over a sorted list, but inserting into a Python list is O(n). A segment tree over ranks keeps every operation at O(log n), at the cost of knowing all values up front for compression.
  • When it is overkill. If updates never happen, use prefix sums or a sparse table. If the queries are a sliding window, a monotonic deque gives O(1) amortized. In an interview, say that the tree exists and why before writing 40 lines of it.

Connections

{% include "leetcode/_connections.html" %}

A segment tree is prefix sums made dynamic, built by the divide-and-conquer recursion of merge sort, and stored with the index arithmetic of a heap. Over value ranks it answers the questions a balanced BST with subtree sizes would, and over coordinates it turns a sweep line into an online structure. Range max over values speeds up LIS-style DPs whose transition looks back over a band of values.

Which stored values make up the sum of indices 2 to 6 in the example, and why is node [4..7] opened instead of used?

{% for v in q.visits if v.kind == "inside" %}[{{ v.lo }}..{{ v.hi }}] = {{ v.contribution }}{{ ", " if not loop.last }}{% endfor %}, total {{ q.value }}. Node [4..7] includes index 7, which is outside the range, so its stored sum would count {{ nums[7] }} too many; it is split and its child [7] is rejected.

Why can at most two nodes per level partly overlap a query range?

A node at some level partly overlaps only if one of the range's two ends falls strictly inside it. The nodes at a level tile the array, so each end lies in exactly one of them. Every node between those two is wholly inside the range.

Why can a Fenwick tree do range sums but not range minimums, while a segment tree does both?

A Fenwick tree only stores prefixes, and gets a range as prefix(right) minus prefix(left − 1). Subtraction undoes addition, but nothing undoes min. A segment tree assembles the range from disjoint pieces, so it only needs to combine, never to undo.

With lazy propagation, what goes wrong if query forgets to call _push before recursing?

Children under a node with a pending add still hold their old totals. The parent's total is right, so a query that uses the parent whole is fine, but one that descends reads stale children and misses the pending addition.
