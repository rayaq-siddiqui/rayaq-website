Tree depth-first search

A binary tree is a root with two smaller binary trees hanging off it, so almost every tree question is a recursive function that asks the left subtree, asks the right subtree, and combines the two answers with the current node. Learn the three visiting orders, learn when information flows down as arguments and when it flows up as return values, and learn to separate "what I return to my parent" from "what I record as the answer". That covers most of the tree problems you will meet.

Problem

A tree gives you a root and, at each node, a left and a right child that may be missing. There is no index and no way to jump to a node. You reach everything by walking down from the root. Depth-first search walks one branch to its end before trying the next, which is exactly what a recursive function on a node does. The questions are about the whole shape: how deep is it, is it balanced, are these two trees equal, what is the best path, who is the common ancestor of two nodes.

Intuition

Imagine you are a manager of a team tree and you want the headcount. You do not count everyone yourself. You ask your two direct reports, "how many people are under you?", each of whom asks theirs, and you answer their numbers added together, plus one for me. Someone with no reports answers zero immediately. You never need to know how the work gets done below you; you only trust the contract that each report returns the correct answer for their own team. That trust is the entire technique, and the proof that it works is the same as for any recursion: if the answer is right for the smallest trees and the combine step is right whenever the children's answers are right, then it is right for every tree.

The only real decision is when to do your own work. Do it before asking the children and you can pass what you know down to them (preorder). Do it between the two questions and, in a search tree, you meet the values in sorted order (inorder). Do it after both answers arrive and you can use what the children found (postorder). Pick the order by asking which direction the information needs to travel.

Same tree three times; the number in a circle is when that node is visited. Preorder starts at the top, inorder starts at the leftmost node, and postorder ends at the root. The filled node is the first one visited.

Mechanics

The contract and the base case

Write down, in one sentence, what f(node) returns for the whole subtree at node, including node = None. The recursion is then forced: handle the empty tree, call f on both children, combine. Correctness is induction on subtree size: f(None) is right by the base case, and if f is right for both children then the combine step makes it right for the node. Bugs come from a vague contract: the height of an empty tree is 0 here, not −1, and mixing the two conventions between base case and combine is the most common error.

Information flowing down, information flowing up

Down is a parameter: the sum so far, the maximum on the path from the root, the remaining target. It describes the path from the root to this node, which only the ancestors know. Up is a return value: height, size, whether a target was found, the best total below. It describes the subtree, which only the descendants know. A problem that needs both passes them in both directions at once; counting good nodes only passes down, balance checking only returns up, and path sum with a target uses both.

Return one thing, record another

The trickiest family is where the best answer is a path that is allowed to bend at its highest node. A parent can extend a path that goes down through exactly one child, so that is what a node must return. But the best path overall may use both children at some node, so each node also computes the bent path and updates a running best. For the diameter, a node returns its height but records left + right; for the maximum path sum, a node returns its value plus the better child's gain (never less than zero) but records its value plus both gains. The two numbers answer different questions: one is for the caller, one is for the final result.

Iterative versions

Recursion uses the call stack, so each order can also use an explicit stack. Preorder pushes the root, then pops a node, visits it, and pushes its right child before its left (so the left comes off first). Inorder goes left as far as it can pushing nodes, then pops, visits and turns right. Postorder is easiest as preorder with the children swapped (root, right, left) and the result reversed. The need arises because Python's default recursion limit is about 1000 frames: a degenerate tree shaped like a list with 105 nodes overflows it even though the algorithm is correct.

Each node shows the height it returns (h) and the longest path bending there (bend, in edges). The amber node has the largest bend: that value is the tree's diameter.

Implementation

class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val, self.left, self.right = val, left, right


def preorder(root):
    out, stack = [], [root] if root else []
    while stack:
        node = stack.pop()
        out.append(node.val)
        if node.right:
            stack.append(node.right)                 # right first so left pops first
        if node.left:
            stack.append(node.left)
    return out


def inorder(root):
    out, stack, cur = [], [], root
    while cur or stack:
        while cur:
            stack.append(cur)
            cur = cur.left
        cur = stack.pop()
        out.append(cur.val)
        cur = cur.right
    return out


def postorder(root):
    out, stack = [], [root] if root else []
    while stack:
        node = stack.pop()
        out.append(node.val)
        if node.left:
            stack.append(node.left)
        if node.right:
            stack.append(node.right)
    return out[::-1]                                 # root, right, left reversed


def max_depth(root):
    return 0 if not root else 1 + max(max_depth(root.left), max_depth(root.right))


def diameter(root):
    best = 0

    def height(node):
        nonlocal best
        if not node:
            return 0
        left, right = height(node.left), height(node.right)
        best = max(best, left + right)               # record the bend
        return 1 + max(left, right)                  # return the straight part

    height(root)
    return best


def is_balanced(root):
    def height(node):
        if not node:
            return 0
        left = height(node.left)
        if left == -1:
            return -1
        right = height(node.right)
        if right == -1 or abs(left - right) > 1:
            return -1                                # sentinel for unbalanced
        return 1 + max(left, right)

    return height(root) != -1


def is_same(a, b):
    if not a or not b:
        return a is b
    return a.val == b.val and is_same(a.left, b.left) and is_same(a.right, b.right)


def is_subtree(root, sub):
    return bool(root) and (is_same(root, sub) or is_subtree(root.left, sub) or is_subtree(root.right, sub))


def is_symmetric(root):
    def mirror(a, b):
        if not a or not b:
            return a is b
        return a.val == b.val and mirror(a.left, b.right) and mirror(a.right, b.left)

    return not root or mirror(root.left, root.right)


def count_good(root):
    def go(node, top):
        if not node:
            return 0
        return (node.val >= top) + go(node.left, max(top, node.val)) + go(node.right, max(top, node.val))

    return go(root, float("-inf"))


def lowest_common_ancestor(root, p, q):
    if root is None or root is p or root is q:
        return root
    left = lowest_common_ancestor(root.left, p, q)
    right = lowest_common_ancestor(root.right, p, q)
    return root if left and right else left or right


def max_path_sum(root):
    best = float("-inf")

    def gain(node):
        nonlocal best
        if not node:
            return 0
        left, right = max(0, gain(node.left)), max(0, gain(node.right))
        best = max(best, node.val + left + right)
        return node.val + max(left, right)

    gain(root)
    return best


def path_sum_paths(root, target):
    paths, path = [], []

    def go(node, remaining):
        if not node:
            return
        path.append(node.val)
        remaining -= node.val
        if not node.left and not node.right and remaining == 0:
            paths.append(path[:])
        go(node.left, remaining)
        go(node.right, remaining)
        path.pop()                                   # undo on the way back

    go(root, target)
    return paths


def rob_tree(root):
    def go(node):
        if not node:
            return 0, 0
        take_l, skip_l = go(node.left)
        take_r, skip_r = go(node.right)
        return node.val + skip_l + skip_r, max(take_l, skip_l) + max(take_r, skip_r)

    return max(go(root))


def delete_leaves(root, target):
    if not root:
        return None
    root.left = delete_leaves(root.left, target)
    root.right = delete_leaves(root.right, target)
    if not root.left and not root.right and root.val == target:
        return None
    return root

is_same and mirror use a is b after the guard: if either node is missing, the trees agree only when both are missing. is_subtree assumes sub is not empty; an empty tree is trivially a subtree of anything, so handle that before the call.

Variations and edge cases

  • Pass the path down, record at the leaf. Path sums and root-to-leaf listings append to a shared list before recursing and pop afterwards. Copy the list (path[:]) when recording, or every stored path will be emptied by the later pops.
  • Return a pair. House robber on a tree returns (best with this node taken, best with it skipped). Any problem where the parent's choice depends on the child's choice returns one value per state.
  • Return a sentinel. Balance checking uses −1 for "already failed", which avoids a second pass that would recompute heights repeatedly (that version is O(n²) on a skewed tree).
  • Rebuild on return. Pruning, inverting and deleting reassign root.left and root.right from the recursive calls and return the node (or None to remove it).
  • Edge cases: an empty tree, a single node, a chain of nodes that is deeper than the recursion limit, negative values (the clamp to zero in the path sum), duplicate values (compare nodes with is when the problem gives you the node, not its value), and trees where a leaf is a node with both children missing, not merely one.

Complexity and tradeoffs

  • Time: O(n). Each node is visited once and does constant work besides the calls. The height trace above took {{ ht.steps | length }} steps for {{ ht.steps | length }} nodes. Checking whether one tree is a subtree of another is O(n·m) in the worst case, since is_same may run at every node.
  • Space: O(h), where h is the tree's height, for the call stack or the explicit stack: about log n for a balanced tree and n for a chain. Paths that are stored add the size of the output.
  • Baseline. Computing height separately at every node, as in a naive balance check, repeats work and costs O(n²) on a skewed tree. Returning the height from the same pass makes it O(n).
  • When it fails. Questions about distance from the root, level by level, or the nearest node to something are shortest-path questions on a tree and are cleaner with breadth-first search. Questions about a graph that may contain cycles need a visited set. And when the input is a search tree, use its order to skip half the tree (see the binary search trees page) instead of visiting every node.

Problems

The home problems fall into four groups: the traversals themselves (preorder, inorder, postorder); questions about shape computed by returning values up (depth, balance, diameter, maximum path sum, house robber III, deleting leaves); comparing trees (same, symmetric, subtree, invert); and carrying state down (good nodes, path sum II, lowest common ancestor). Check yourself

Why does the inorder traversal of a binary search tree come out sorted?

Inorder visits the whole left subtree, then the node, then the whole right subtree. In a search tree every left value is smaller than the node and every right value is larger, so by induction each subtree is output sorted and the node sits between them. In the example it prints {{ orders.inorder | join(", ") }}.

The diameter code returns 1 + max(left, right) but records left + right. Why not just return the larger?

The parent can only extend a path that comes up through one child, so the returned value must be the straight height. The bent path through both children can never be extended by a parent, so it is only recorded. Here node {{ bend.node }} returned {{ bend.height }} but recorded {{ bend.through }}, the diameter.

In the path-sum table, why does node {{ path_tree[1][0] }} return {{ (mp.steps | selectattr("node", "equalto", path_tree[1][0]) | list)[0].returns }} while its own bent path sum is {{ (mp.steps | selectattr("node", "equalto", path_tree[1][0]) | list)[0].through }}?

The bent path uses both children, which a parent could not extend, so only the better single side ({{ (mp.steps | selectattr("node", "equalto", path_tree[1][0]) | list)[0].left }} versus {{ (mp.steps | selectattr("node", "equalto", path_tree[1][0]) | list)[0].right }}) plus the node's own value, {{ path_tree[1][0] }}, is returned.

When should information be a parameter, and when a return value?

If it describes the path from the root to this node (a running sum, the maximum so far), only the ancestors know it, so pass it down. If it describes the subtree below (height, size, whether a target is inside), only the descendants know it, so return it up. Some problems need both.
