Variable-size sliding window

When the question is "the longest (or shortest) stretch that satisfies a condition", the window cannot have a fixed width, so it breathes: the right edge grows it one item at a time and the left edge shrinks it whenever the condition is broken (or, for shortest, whenever it still holds). Each edge only moves forward, so the whole scan is linear. This page covers the no-repeat window, the positive-sum window and the "at most k replacements" window, and why negative numbers break the pattern.

Problem

"Longest substring with no repeated letter", "shortest run of numbers adding to at least a target", "longest stretch that becomes uniform after k edits": every candidate is a contiguous range, and there are about n²/2 of them. Checking each from scratch is cubic or quadratic. The structure that rescues you is monotonicity: if a range is valid, shrinking it keeps it valid (or if it is invalid, growing it keeps it invalid), so you never need to look at a left edge again once it has been passed.

Intuition

Picture an inchworm on a number line. The head (right edge) always steps forward. The tail (left edge) only ever catches up. After every head step you ask whether the worm is still allowed to be this long, and if not, you pull the tail forward until it is. The worm never goes backwards, so head and tail together take at most 2n steps, however the condition behaves in between.

The skill is in two choices: what summary of the window lets you test the condition in O(1) (a set, a count map, a sum, a max count), and which direction of the condition is monotonic, which tells you whether to shrink while invalid (longest) or while valid (shortest).

Mechanics

The invariant

After each iteration, [left, right] is the longest valid window ending at right (for "longest" problems) or the shortest valid window ending at right (for "shortest" problems, whenever one exists). The proof has two halves. Safety: the left edge only moves past positions that cannot start a valid window ending at this or any later right edge, because validity is monotonic. Progress: left and right each only increase and are bounded by n, so the loop body runs O(n) times in total even though it contains an inner while. This is amortised analysis: the inner loop's total work is the total distance the left edge travels.

Two templates

Longest: add nums[right]; while the window is invalid, remove nums[left] and advance; then record the length. The record sits after the shrink because only then is the window valid.

Shortest: add nums[right]; while the window is valid, record the length, remove nums[left] and advance. The record sits inside the shrink because each valid state is a candidate and the shrink looks for a smaller one.

A window whose condition is a formula

Replacement problems turn "can I make this window all one letter with at most k edits" into arithmetic. The cheapest plan keeps the most common letter and rewrites the rest, so the cost is length − top count. The window is valid while that cost is at most k. Because the cost can only be computed from counts that update in O(1), no scan of the window is needed.

Bar height is the edit cost after shrinking; the first number under each bar is the window length, the second the letter that just arrived. The cost never crosses the limit.

Implementation

def longest_unique(s):
    last = {}
    left = best = 0
    for right, ch in enumerate(s):
        if ch in last and last[ch] >= left:
            left = last[ch] + 1                 # jump past the earlier copy
        last[ch] = right
        best = max(best, right - left + 1)
    return best


def shortest_at_least(target, nums):           # nums must be positive
    left = total = 0
    best = float("inf")
    for right, x in enumerate(nums):
        total += x
        while total >= target:
            best = min(best, right - left + 1)
            total -= nums[left]
            left += 1
    return 0 if best == float("inf") else best


def longest_after_replacements(s, k):
    counts = {}
    left = best = 0
    for right, ch in enumerate(s):
        counts[ch] = counts.get(ch, 0) + 1
        while (right - left + 1) - max(counts.values()) > k:
            counts[s[left]] -= 1
            left += 1
        best = max(best, right - left + 1)
    return best

Variations and edge cases

  • Covering a multiset. The "smallest window containing every needed letter" problem keeps a need-count map and a single integer, how many letters still lack their quota, like the mismatch counter of the fixed window. Shrink while that integer is zero, recording each state.
  • At most k distinct. Keep a count map; the window is invalid when len(counts) > k; delete keys that reach zero, or the length of the map lies.
  • Exactly k. Count windows with at most k, subtract those with at most k − 1.
  • Max-count shortcut. In the replacement problem the top count can be kept as a value that never decreases and the answer stays right, because only a larger top count can produce a longer window. Calling max over at most 26 counts is simpler and safe.
  • Jump versus step. The last-seen map lets the left edge leap; stepping one at a time with a set is also O(n) overall. Check last[ch] >= left, or an old copy outside the window will drag the edge backwards.
  • Edge cases: empty input, a target that is never reached (answer 0, not infinity), a single element that already meets the target, all elements equal, and negative numbers, which require prefix sums instead.

Complexity and tradeoffs

  • Time: O(n) edge moves in total, with O(1) work per move for sums, sets and count maps. The replacement version costs O(alphabet) per step if you recompute the max.
  • Space: O(1) for a sum, O(alphabet) or O(distinct values) for sets and maps.
  • Baseline. Trying every pair of edges with an O(n) validity check is O(n³); caching a running summary gets O(n²); the window gets O(n).
  • When it fails. Validity must be monotonic in the window's extent. A sum target with negative numbers is not, which is why those questions use prefix sums and a hash map. A condition that depends on the window's median or an arbitrary property needs a different structure, such as a sorted container or two heaps.

Check yourself

The shrink loop is nested inside the grow loop. Why is the algorithm still O(n)?

The left edge only moves forward and never passes n, so the inner loop runs at most n times in total across the whole scan, not n times per outer step. In the sum example the shrink fired {{ sub.steps | length }} times for {{ sub_nums | length }} elements.

Why does the "shortest" template record the length inside the shrink loop but the "longest" template records it after?

For shortest, every state where the window is valid is a candidate, and shrinking looks for smaller valid states. For longest, the window is valid only after the shrink loop has restored it, so the length is read there. Reading too early records an invalid window.

Why does "shortest subarray with sum at least target" fail on arrays with negative numbers?

Removing the left element may increase the sum, and adding a right element may decrease it, so a shrunk window can become valid again later and the left edge may not safely be skipped. Prefix sums with a monotonic structure or a hash map are needed.

In the no-repeat window, what goes wrong if you drop the check last[ch] >= left?

A copy of the letter from before the window would pull the left edge backwards and the window would include repeats. In "{{ text }}" the letter a at index 6 had an earlier copy at 0, which is already behind the left edge ({{ uniq.steps[6].left }}).
