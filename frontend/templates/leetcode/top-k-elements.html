Top-k elements

"Give me the k largest" sounds like a job for sorting, and sorting works, but it does far more than asked: it orders all n items when you only want k of them. The better way is to carry a small waiting room of size k. Each newcomer is compared with the weakest person inside; if it beats them, it swaps in. The waiting room is a heap, so the weakest member is always at the door, and the whole scan costs O(n log k).

Problem

You need the k best items by some measure: the k largest numbers, the k most frequent words, the k points closest to the origin, or just the k-th largest. The data may arrive as a stream you can see only once, or be too large to sort comfortably. In all cases the answer has size k, and k is usually far smaller than n. What you want is a structure of size k, not size n.

Intuition

Imagine a podium with k places and a doorkeeper who always knows who stands on the lowest step. The first k visitors step straight up. After that, a visitor only gets in by beating the person on the lowest step, who is then sent away. Visitors who do not beat the lowest step are turned away at the door at once. At the end the podium holds exactly the k best, because anyone who was ever evicted was beaten by k other people who stayed or were themselves beaten by better ones.

The surprise is the direction of the heap. To keep the largest k you use a min-heap: the item you need quick access to is the weakest of the strong, since that is the one to compare against and to throw out. Keeping the smallest k uses a max-heap for the same reason. Getting this backwards, a max-heap for the largest, is the classic mistake, and it forces a full sort.

Mechanics

The invariant

After processing any prefix of the input, the heap holds exactly the k best items of that prefix (or all of them, if fewer than k have been seen), and its root is the weakest of those. This is true at the start (empty) and survives each step. If the heap has room, adding the item keeps it true. If the heap is full and the newcomer beats the root, then the root is not among the k best of the longer prefix, since k items now beat it, so replacing it keeps the invariant. If the newcomer does not beat the root, then at least k kept items are at least as good, so the newcomer is not in the k best and is dropped. When the input ends, the heap is the answer, and its root is the k-th best.

Why O(n log k)

Each of the n items costs one comparison with the root, and at most one push or replace, each O(log k) because the heap never grows beyond k. Sorting costs O(n log n). When k is small the gap is large: for a million items and k = 10, a heap does about log₂ 10 ≈ 3 levels of work per item, a sort about 20. The heap also needs only O(k) memory, so it works on a stream that does not fit in memory.

Frequency and distance variants

The heap only needs a score for each item. For frequency, first count with a dictionary (one pass, O(n)), then run the same procedure over the distinct items with the count as the score. For distance, the score is the distance to a point; compare squared distances, which rank the same and avoid a square root. To keep the closest, you want to evict the farthest, so the heap root is the worst kept item and the heap is a max-heap on distance, usually stored as negated values in Python.

The bar is the weakest value kept. It rises only when a replacement happens, which is why the scan gets cheaper as it goes: more and more values are skipped with a single comparison.

Implementation

import heapq
from collections import Counter


def largest_k(nums, k):
    heap = []
    for x in nums:
        if len(heap) < k:
            heapq.heappush(heap, x)
        elif x > heap[0]:
            heapq.heapreplace(heap, x)      # pop the weakest and push x in one step
    return sorted(heap, reverse=True)


class KthLargest:
    def __init__(self, k, nums):
        self.k = k
        self.heap = []
        for x in nums:
            self.add(x)

    def add(self, x):
        if len(self.heap) < self.k:
            heapq.heappush(self.heap, x)
        elif x > self.heap[0]:
            heapq.heapreplace(self.heap, x)
        return self.heap[0]


def top_k_frequent_words(words, k):
    counts = Counter(words)
    # most frequent first, ties alphabetical: sort key (-count, word)
    return heapq.nsmallest(k, counts, key=lambda w: (-counts[w], w))


def k_closest(points, k):
    heap = []                                 # max-heap by distance, stored negated
    for x, y in points:
        d = x * x + y * y
        if len(heap) < k:
            heapq.heappush(heap, (-d, x, y))
        elif d < -heap[0][0]:
            heapq.heapreplace(heap, (-d, x, y))
    return [[x, y] for _, x, y in heap]

heapq.nlargest and heapq.nsmallest implement the same idea, and they take a key. Writing the loop by hand is worth it in an interview because the interviewer usually asks what happens inside.

Variations and edge cases

  • Ties. The word problem needs a deterministic order. Make the score a tuple, with the count negated so that smaller means better, and the word as the tiebreak. With the heap-of-size-k approach, a max-heap on (count, reversed word) is harder to write than nsmallest with a key.
  • Bucket by count. If scores are counts, an array of lists indexed by count, read from the high end, gives the top k in O(n) with no heap.
  • The k-th element only. A heap of size k gives the answer as its root; quickselect gives it in average O(n) time but changes the input.
  • Streams. Keep the heap as state between calls; each update is O(log k).
  • Edge cases: k equal to 0 (return empty, and guard heap[0]), k larger than n (return everything), duplicates in the input (equal values count separately for the largest k, so check what the problem means), negative numbers, and an empty heap when a stream is queried before k values arrive.

Complexity and tradeoffs

  • Time: O(n log k): n scans, each with at most one heap update on k items. Counting first, as for frequency, adds an O(n) pass, and then O(d log k) over d distinct items.
  • Space: O(k) for the heap, plus O(d) for a frequency table.
  • Baseline. Sort everything: O(n log n) time, O(n) space, three lines of code. It is the right answer when k is a large fraction of n or when n is small.
  • When it fails. Quickselect has better average time, O(n), for a one-off query on data you may rearrange. If you need the top k repeatedly under insertions and deletions, a balanced tree or a sorted container works better than a heap, which cannot delete arbitrary items cheaply. For small integer scores, buckets beat both.

Check yourself

Why do we use a min-heap to keep the k largest values?

Each newcomer must be compared with the weakest kept value, and that is the item to evict if the newcomer wins. A min-heap exposes its smallest value at the root in O(1). In the example the root after the scan is {{ trace.kth }}, the 3rd largest.

Why can a skipped value never belong to the answer?

When the heap is full and a value does not beat the root, k kept values are at least as large, so the value ranks below k others and cannot be among the k best. Values such as {{ steps[4].value }} and {{ steps[6].value }} in the example were skipped for this reason.

When is sorting the better answer?

When k is close to n, the heap does about n log n work with a larger constant than the built-in sort, so a one-line sort is as fast and simpler. It is also right when n is tiny or the whole ordering is needed anyway.

Why compare squared distances for the closest points?

Squaring is increasing for non-negative numbers, so it ranks distances identically and avoids a square root, which also keeps every comparison in exact integer arithmetic. In the example (1, 1) has squared distance {{ near.steps[3].dist2 }} and (0, 2) has {{ near.steps[4].dist2 }}.
