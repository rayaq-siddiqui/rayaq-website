Union-find

Union-find (disjoint sets) answers one question over and over while the facts keep changing: are these two things in the same group? Each group is a tree of parent pointers, the root names the group, and two operations, find and union, run in close to constant time. It is the right tool whenever edges arrive one at a time and the question is about connection, not about paths.

Problem

The input is a collection of items and a stream of "these two belong together" facts: edges of a graph, accounts that share an email, numbers that share a factor. You are asked how many groups there are, whether a new fact was redundant, whether everything ended up in one group, or what the groups are. The answer must not require rebuilding anything when the next fact arrives.

Intuition

Picture friend groups at a party. Each group has a spokesperson. To check whether two people are in the same group, ask each of them who their spokesperson is, passing the question up the line of "my friend X introduced me" until someone says "that's me". If the answers match, they are together. To join two groups, make one spokesperson report to the other. That is the whole data structure: parent[x] is who introduced x, and the root is its own parent.

Left alone, the chains of introductions can grow long, and asking becomes slow. Two cheap habits fix it. When you join two groups, hang the smaller one under the larger one's spokesperson, so no chain gets deeper unless the group at least doubles. And whenever you walk up a chain, repoint everyone you passed straight at the spokesperson, so the next question is one step. Together they make an operation cost the inverse Ackermann function of n, which is below five for any input that fits in a universe.

The same unions, run in the same order, can build a chain or a flat star depending on which root goes under which. The left tree makes a find from node 0 cost {{ naive_layout[0][0] }} steps; the right one costs {{ size_layout[0][0] }}. The diagram scrolls sideways on a narrow screen.

Mechanics

Find and union

find(x) follows parent pointers until a node is its own parent and returns it. union(a, b) finds both roots; if they are equal the pair was already connected (report it, that is the redundant edge), and otherwise one root is pointed at the other and the group count drops by one.

Invariants

Two facts hold after every operation. First, following parents from any node ends at a root and never loops, because a union only points a root at a different root. Second, two nodes share a root exactly when a chain of union calls connected them: a union merges two whole groups and nothing else changes membership. So find(a) == find(b) is the same as "a and b are connected by the edges seen so far".

Why it is fast

With union by size, a node's depth increases only when its group is attached under a group at least as large, which at least doubles the group it belongs to, so the depth is at most log₂ n. Path compression flattens whatever a find walked. Used together, Tarjan proved the amortized cost per operation is O(α(n)), the inverse Ackermann function. Either one alone already gives O(log n) amortized, which is plenty for interview limits.

Counting and redundancy

Keep components = n and subtract one on each successful union. A union that finds equal roots is a cycle edge in an undirected graph. A tree on n nodes has exactly n - 1 edges and a single component, so it is valid exactly when the edge count is n - 1 and no edge was redundant.

Implementation

class DSU:
    def __init__(self, n):
        self.parent = list(range(n))
        self.size = [1] * n
        self.components = n

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]
            x = self.parent[x]
        return x

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra
        self.size[ra] += self.size[rb]
        self.components -= 1
        return True


def count_components(n, edges):
    dsu = DSU(n)
    for a, b in edges:
        dsu.union(a, b)
    return dsu.components


def find_redundant_connection(edges):
    dsu = DSU(len(edges) + 1)
    for a, b in edges:
        if not dsu.union(a, b):
            return [a, b]
    return []

Variations and edge cases

def valid_tree(n, edges):
    if len(edges) != n - 1:
        return False
    dsu = DSU(n)
    return all(dsu.union(a, b) for a, b in edges)


def accounts_merge(accounts):
    index = {}
    dsu = DSU(len(accounts))
    for i, (_, *emails) in enumerate(accounts):
        for email in emails:
            if email in index:
                dsu.union(i, index[email])
            else:
                index[email] = i
    groups = {}
    for email, i in index.items():
        groups.setdefault(dsu.find(i), []).append(email)
    return [[accounts[root][0]] + sorted(emails) for root, emails in groups.items()]


def can_traverse_all(nums):
    n = len(nums)
    if n == 1:
        return True
    dsu = {}

    def find(x):
        dsu.setdefault(x, x)
        while dsu[x] != x:
            dsu[x] = dsu[dsu[x]]
            x = dsu[x]
        return x

    for i, v in enumerate(nums):
        if v == 1:
            return False
        p = 2
        while p * p <= v:
            if v % p == 0:
                dsu[find(("p", p))] = find(("i", i))
                while v % p == 0:
                    v //= p
            p += 1
        if v > 1:
            dsu[find(("p", v))] = find(("i", i))
    return len({find(("i", i)) for i in range(n)}) == 1
  • Compare roots, not parents. After unions a node's parent may be an interior node. Always call find before comparing two nodes.
  • Recursion. A recursive find on a long chain overflows Python's stack. The iterative path-halving version above never does.
  • Keys that are not 0..n-1. Use a dictionary for the parent map (emails, strings, tuples) or map the keys to integers first, as the account example does.
  • Grids. Number cells r * cols + c. For "add land, report islands" streams, union only with neighbors that are already land, and update the count on each add.
  • Directed edges. Plain union-find ignores direction, so it cannot detect a cycle in a directed graph; use a three-state DFS or Kahn's algorithm there. A directed variant of Redundant Connection needs extra care for nodes with two parents.
  • Edge cases: a self-loop (the root is always equal, so it is redundant), duplicate edges, zero edges, n of 1 (a lone node is a tree), and nodes that never appear in an edge but still count as components.

Complexity and tradeoffs

  • Time: O(α(n)) amortized per find or union with both optimizations, so O(E · α(n)) for E edges, in practice linear. With one optimization it is O(log n) amortized.
  • Space: O(n) for the parent array, plus O(n) for sizes. Dictionaries add a constant factor.
  • Baseline. Re-running a DFS after every added edge costs O(E · (V + E)). Union-find processes the same stream in near-linear time.
  • Versus DFS/BFS. For one static graph, a single traversal counts components just as fast and needs no new structure. Union-find wins when edges arrive over time, when you need to detect the first redundant edge, or when the graph is implicit in a rule (shared factors, shared emails).
  • When it fails. It cannot delete an edge, answer path or distance questions, or use edge direction. Offline deletions can sometimes be reversed into additions processed backwards. Minimum spanning trees use union-find inside Kruskal's algorithm.

Check yourself

Why does an edge whose endpoints share a root create a cycle?

Equal roots mean the earlier edges already connect the two nodes by some path. The new edge gives a second path between them, and two different paths between the same nodes contain a cycle. In the example, edge {{ demo.redundant[0] }}-{{ demo.redundant[1] }} is the first such edge.

What does union by size prevent, and what does path compression speed up?

Union by size keeps trees shallow: a node only goes deeper when its group at least doubles, so depth is at most log n. Path compression flattens the nodes a find walked so repeated queries cost one step. In the chain example the deepest find was {{ naive_layout[0][0] }} steps without union by size and {{ size_layout[0][0] }} with it.

A graph has 6 nodes, 5 edges and no redundant edge. Is it a tree?

Yes. No redundant edge means no cycle, and 5 edges on 6 nodes with no cycle must connect everything: each successful union reduces the component count by one, and 6 - 5 = 1.

Why can union-find not answer "was there a path from A to B that avoids edge e"?

It only remembers that two nodes are connected, not how, and it has no way to remove a union. Questions about specific edges or paths need a traversal, or an offline reordering that adds edges instead of removing them.
