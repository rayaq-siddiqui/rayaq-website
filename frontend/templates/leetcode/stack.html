Stacks

A stack lets you set something aside and come back to it in the reverse order you left it. That one rule is enough for matching brackets, evaluating expressions, undoing operations and remembering "the last thing still unresolved". This page shows the push-and-resolve loop, the min stack that carries extra information in each entry, and postfix evaluation.

Problem

Many inputs have nested structure: parentheses inside brackets, a sub-expression inside an expression, a path with .. steps that undo earlier ones. The most recently opened thing is always the first one to close. A stack stores exactly the set of things that are open right now, innermost on top, so each new item only needs to look at the top. Without a stack you end up scanning back and forth for the matching partner, which costs O(n²).

Intuition

A stack of plates in a cafeteria: you can only touch the top one. Parsing a nested structure has the same shape. Each opening symbol is a promise ("I still owe a closing partner"). Each closing symbol must settle the most recent unsettled promise, which is the top of the stack. If it names a different promise, the input is broken. If the input ends and promises remain, it is broken too.

The second idea is that a stack entry can hold more than one value. A min stack stores (value, minimum so far). Because the minimum at depth d depends only on entries 1 to d, popping the top automatically reveals the right minimum for the entries left behind.

The stack after each character. Amber is the item just pushed; a column that shrinks is a pop. The last column is empty: everything that opened was closed.

Mechanics

The invariant

After reading a prefix, the stack holds exactly the unresolved items of that prefix, oldest at the bottom. For brackets, that means the openers not yet closed, and the prefix is still a possible start of a valid string exactly when every closer so far matched the top at its moment. Pushing an opener keeps the invariant because the new opener is unresolved. Popping on a matching closer keeps it because that pair resolves the top. A closer that does not match the top (or arrives on an empty stack) can never be matched later, because the unresolved items beneath the top can only be reached after the top is gone. So the answer is: valid when no mismatch occurred and the stack is empty at the end.

Entries with memory

Anything computed from "the stack below me" can be stored in the entry at push time. The min stack stores the running minimum; a stack-based calculator stores the running result and sign when it enters a parenthesis; a decoder stores the string built so far and the repeat count. When the scope closes, the pop returns the stored outer state and you combine it with the inner result.

Postfix evaluation

In reverse Polish notation operators come after their operands, so there is no precedence to parse. Push numbers. On an operator, pop the right operand first (it was pushed last), then the left, apply, and push the result. The order of the two pops matters for subtraction and division. A valid expression ends with exactly one value on the stack.

Implementation

def is_valid(s):
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []
    for ch in s:
        if ch in pairs:
            if not stack or stack.pop() != pairs[ch]:
                return False
        else:
            stack.append(ch)
    return not stack


class MinStack:
    def __init__(self):
        self.items = []                     # (value, minimum at push time)

    def push(self, x):
        low = x if not self.items else min(x, self.items[-1][1])
        self.items.append((x, low))

    def pop(self):
        return self.items.pop()[0]

    def top(self):
        return self.items[-1][0]

    def get_min(self):
        return self.items[-1][1]


def eval_rpn(tokens):
    stack = []
    for t in tokens:
        if t in {"+", "-", "*", "/"}:
            right, left = stack.pop(), stack.pop()
            if t == "+": stack.append(left + right)
            elif t == "-": stack.append(left - right)
            elif t == "*": stack.append(left * right)
            else: stack.append(int(left / right))      # truncate toward zero
        else:
            stack.append(int(t))
    return stack[-1]

Variations and edge cases

  • Store indices, not values. When the answer is a distance or a length (the longest valid parentheses run), push indices; the value is always s[i] and the position is free. Seeding the stack with a sentinel index -1 removes the empty-stack special case.
  • Saving state at a scope boundary. A calculator with parentheses pushes the running total and sign on ( and pops them on ); a decoder pushes the string and repeat count. The pattern is identical to the bracket check with richer entries.
  • Multiplication and division without parentheses. Push signed terms and fold * and / straight into the top; the answer is the sum of the stack.
  • Collisions. Asteroids moving in opposite directions resolve against the top of the stack until one side is gone: a loop of pops, not a single comparison.
  • Queue from two stacks. An inbox and an outbox: refill the outbox from the inbox only when the outbox is empty. Each element moves at most twice, so every operation is amortised O(1).
  • Edge cases: a closer on an empty stack, openers left over at the end, an odd length (cannot be valid), division truncating toward zero (Python's // floors), popping an empty stack in a malformed expression, and a path that tries to go above the root.

Complexity and tradeoffs

  • Time: O(n). Each element is pushed once and popped at most once, so even a loop of pops is amortised constant per element.
  • Space: O(n) in the worst case (all openers). A bracket check with one bracket type needs only a counter, O(1), but with several types the stack is required.
  • Python: a list with append and pop is a fast stack. Do not use pop(0) or insert(0, x) for a stack or queue.
  • When it fails. If matching partners are not nested (crossing intervals), a stack is the wrong shape; if you need the next greater or smaller element, keep the stack ordered (monotonic stack); if you need the oldest item first, use a queue.

Problems

Most home problems are one of three shapes: match and cancel (parentheses, asteroids, path simplification), evaluate with saved state (calculators, decode string, postfix) or build a data structure out of stacks (min stack, queue from stacks, stack from queues). The longest valid parentheses problem also leans on dynamic programming; the stack version is the cleanest.

Check yourself

Why is it enough to look only at the top of the stack when a closing bracket arrives?

Everything below the top is an opener that was opened before the top one, so by nesting it can only be closed after the top has been. If the arriving closer does not match the top, it cannot match anything beneath it either, and the string is invalid. In {{ bad_text }} the top was {{ bad.failure.top }} when {{ bad.failure.char }} arrived.

Why must the stack be empty at the end, not just free of mismatches?

Leftover items are openers that never found a partner. The string "((" has no mismatch, but it finishes with {{ bracket_trace("((").left_over | length }} unresolved items.

How does a min stack return the old minimum after the current one is popped?

Every entry remembers the minimum of itself and everything beneath it at push time. Popping removes the top entry and its minimum together, and the new top already holds the right value. In the example the minimum goes {{ ms.steps | map(attribute="min") | join(", ") }}.

In postfix evaluation, why do you pop the right operand first?

It was pushed more recently, so it is on top. Subtraction and division are not commutative, so swapping the pops changes the answer; in the example "8 − 6" has to be computed in that order to reach {{ rpn.result }}.
