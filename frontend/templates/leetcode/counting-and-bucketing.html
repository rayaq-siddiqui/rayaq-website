Counting and bucket sort

When a problem cares how many times something occurs, not where, a frequency table replaces sorting and nested loops. This page covers counting letters and values, using a count (or sorted letters) as a canonical key for grouping, the Boyer-Moore voting trick that finds a majority in constant space, and bucket sort, which ranks values by frequency in linear time.

Problem

Many questions only depend on the multiset of items: "are these two words made of the same letters", "which value appears most", "can I build this message from those letters". Order is irrelevant, so sorting does unneeded work and comparing positions does the wrong work. Summarizing the input as counts removes the order and leaves exactly the information needed.

Intuition

A frequency table is a tally sheet: one mark per item, grouped by kind. Two sheets that match describe the same collection no matter how the items were arranged. That is why two anagrams look identical once counted and different when compared letter by letter.

The second idea is that a count can itself be a position. If you want values ordered by how often they appear, you do not need a comparison sort: no value can appear more than n times, so make n + 1 shelves labelled 0 to n, put each value on the shelf matching its count, and read the shelves from the top. That is bucket sort, and it runs in O(n) because it never compares two values.

A different element cancels one vote; when the counter hits zero the next element becomes the candidate.

Mechanics

The frequency table

Build it in one pass: for each item, add one to its entry. In Python, collections.Counter(items) does this. For lowercase letters an array of 26 ints indexed by ord(c) - ord("a") uses constant space. Comparing two tables is a loop over the keys; with an array it is a single list comparison.

Canonical keys for grouping

To group equivalent items, find a value that is identical for equivalent items and different for others, then use it as a dict key. For anagrams there are two choices: the sorted letters (O(L log L) per word of length L) or the tuple of 26 counts (O(L) per word). Either is a canonical form: a unique representative of the equivalence class. The same reasoning groups strings by shifting, numbers by digit multiset, or points by slope.

Boyer-Moore majority voting

Keep one candidate and one counter. For each element: if the counter is zero, make this element the candidate; then add one if the element equals the candidate, else subtract one. Why it works: every decrement cancels one occurrence of the candidate against one different element. If a value occurs more than n/2 times, it outnumbers all other values combined, so cancellation pairs can never use up all its occurrences and it must be the candidate at the end. The converse does not hold: the final candidate is only a possible majority, so a second pass must count it when the problem does not promise one exists. The same argument with k − 1 candidates finds everything above n/k; for n/3 that means two candidates and two counters.

Bucket sort by frequency

After counting, create n + 1 empty lists. Append each value to the list at index equal to its count. Scan the lists from index n down to 1 and collect values until you have k. Counting is O(n), filling the buckets is O(d) for d distinct values and the scan is O(n), so the whole thing is O(n), compared with O(n log n) for sorting by count and O(n log k) for a heap.

The shelf index is the count, so reading them in order needs no comparisons.

Implementation

from collections import Counter, defaultdict


def is_anagram(a, b):
    return len(a) == len(b) and Counter(a) == Counter(b)


def can_construct(note, magazine):             # spend counts, fail on a negative
    supply = Counter(magazine)
    for letter in note:
        supply[letter] -= 1
        if supply[letter] < 0:
            return False
    return True


def group_anagrams(words):                     # canonical key: 26-count tuple
    groups = defaultdict(list)
    for word in words:
        counts = [0] * 26
        for letter in word:
            counts[ord(letter) - ord("a")] += 1
        groups[tuple(counts)].append(word)     # tuples are hashable, lists are not
    return list(groups.values())


def majority_element(nums):                    # Boyer-Moore, O(1) space
    candidate, count = None, 0
    for x in nums:
        if count == 0:
            candidate = x
        count += 1 if x == candidate else -1
    return candidate                           # verify with a second pass if no majority is guaranteed


def top_k_frequent(nums, k):                   # bucket sort, O(n)
    buckets = [[] for _ in range(len(nums) + 1)]
    for value, count in Counter(nums).items():
        buckets[count].append(value)
    result = []
    for bucket in reversed(buckets):
        result.extend(bucket)
        if len(result) >= k:
            return result[:k]
    return result

Variations and edge cases

  • Elements above n/3. Keep two candidates with two counters; when an element matches neither and both counters are non-zero, decrement both. Always verify afterwards, because the survivors are only possible answers.
  • Palindrome from letters. Count letters: every even count is usable in full, each odd count contributes its largest even part, and one centre letter may be added if any count was odd.
  • Difference of counts. A single Counter with +1 for one string and −1 for the other checks an anagram in one table; it works if every value ends at zero.
  • Counting with a sliding window. Sliding-window pages keep a count table for the window and update it as the edges move.
  • Edge cases: strings of different lengths (reject immediately), uppercase or non-letter characters breaking a 26-slot array, counts missing from a dict (use .get or Counter), ties in frequency (the problem usually says any order is fine), and skipping the verification pass after Boyer-Moore.

Complexity and tradeoffs

  • Time: counting is O(n); anagram checks are O(L); bucket sort for top-k is O(n). Canonical keys cost O(L log L) per word with sorting and O(L) with a count tuple (plus 26 per key to hash).
  • Space: a table of d distinct keys is O(d); over a fixed alphabet that is O(1). Boyer-Moore uses O(1) regardless of input. Bucket sort needs O(n) for the shelves.
  • Baselines. Sorting both strings is O(L log L) and uses no hash table, which can be the right answer when memory is tight. Top-k by sorting counts is O(d log d), by a heap O(d log k).
  • When it fails. Counts discard order, so they cannot answer questions about subarrays or adjacency by themselves; combine them with a window. If frequencies are not bounded by a small number (weighted scores, real-valued keys) the bucket shelves disappear; use a heap.

Check yourself

Why can bucket sort rank values by frequency in O(n) when comparison sorting needs Ω(n log n)?

The keys are integers between 1 and n, so the count is itself an array index. Placing values on shelves needs no comparisons, which is how it escapes the comparison-sort lower bound.

After Boyer-Moore on [2, 2, 1, 1, 1, 2, 2] the candidate is {{ vote.candidate }}. When must you still verify it?

Whenever a majority is not guaranteed. The candidate is only the sole possible majority; here a second pass counts {{ vote.occurrences }} of {{ vote.steps | length }}, enough. On [1, 2, 3] it would return 3, which is not a majority.

Which canonical key groups anagrams faster for long words, sorted letters or a 26-count tuple?

The count tuple: O(L) per word versus O(L log L) for sorting. For short words the difference is tiny and sorting is simpler.
